## 0. 소유자 프레이밍과 전체 그림

소유자 프레이밍은 다음과 같다.
- **daemon(saba-core)이 서비스의 주인이다.** 모든 기능은 daemon을 거쳐 실행된다.
- **인터페이스(GUI/CLI)는 스스로 아무것도 하지 않는다.**
- **modules / plugins(=extensions)는 Python으로 만든다.**
- **server-chan은 daemon과 함께 Discord bot을 돌리고, 그 bot에 추가 기능을 제공한다.**

코드에서 확인한 실제 연결 구조는 아래와 같다. `cloud` 모드 기준이다.

```
 Discord 사용자
    │ (prefix 메시지 / 슬래시 /사바쨩)
    ▼
[server-chan relay 프로세스] ── 내장 Discord bot (discord.js, BOT_ENABLED=true)
    │  bot → POST /api/command (x-internal-secret, SELF_URL 루프백)
    │  PostgreSQL command_queue 에 적재 → pollWaiters.wake(hostId)
    ▼
GET /poll (long-poll 25s, 노드 토큰)  ◄──── [saba-core 안의 relay agent (src/relay_agent.rs)]
POST /result/:id                     ────►   (Discord에 로그인하지 않음)
POST /heartbeat (60s)                         │ plan·run_plan·query → crate::actions (같은 프로세스)
POST /events (알림, I3)
                                              ▼
                                       daemon 핸들러를 직접 호출 (IPC 경유 없음)
                     노드 토큰이 있으면 daemon 기동 때 자동 시작
                     (relay_agent.rs:178-189, ipc/mod.rs:860-866), /api/relay/agent/start·stop

[GUI/CLI] ──► daemon /api/relay/* (pairing·host/node 조회 proxy, relay.rs) ──► relay /api/pair/*, /api/hosts/*, /api/nodes/*
```

- 로컬 Discord bot(`discord_bot/`, local 모드)은 없어졌다. Discord bot은 server-chan 쪽 중앙 bot 하나뿐이다(`server-chan/relay-server/src/bot/`).
- saba-chan 쪽 실행기는 daemon 안의 relay agent다. 받은 명령을 action별로 처리해 답한다(`relay_agent.rs` `handle_payload`). 문장 명령은 문장 계획(`plan {text}`)으로 와서 `crate::actions::plan_text`가 채팅 처리기(`crate::chat`)로 해석한다.
- 운영 쪽 부가 구성요소(music-server, chatbot-server)는 server-chan 비공개 문서에서 다룬다(§5).

### 1.2 컴포넌트 모델

`enum Component` (`updater/src/lib.rs:75-83`)와 manifest key의 대응(`lib.rs:87-120`):

| Component | manifest key | 적용 방식 | 적용 우선순위 (`lib.rs` `component_apply_priority`) |
|---|---|---|---|
| `Updater` | `updater` | `apply_binary_update("saba-chan-updater")` | 0 |
| `Module(name)` | `module-{name}` | `modules_dir/{name}`을 zip 내용으로 교체. 백업은 `staging/{name}_backup` (`apply.rs:7-13`, `replace_dir` 24-62) | 2 |
| `Extension(name)` | `ext-{name}` | `extensions_dir`에 교체. 하이픈은 언더스코어로 변환(`lib.rs:426-442`, `apply.rs:16-22`). 백업은 `{name}_ext_backup` | 2 |
| `Locales` | `locales` | `install_root/locales`에 해제(`lib.rs:855-858`) | 2 |
| `Installer` | `installer` | 설치 폴더의 `saba-chan-installer.exe`를 받은 exe로 교체(`apply.rs` `apply_installer_update`) | 2 |
| `CoreDaemon` | `saba-core` | `apply_binary_update("saba-core")` | 1 |
| `Gui` / `Cli` | `gui` / `cli` | 프로세스가 돌고 있으면 5, 아니면 4 | 4/5 |

- `DiscordBot` 컴포넌트는 로컬 bot과 함께 없어졌다. 우선순위 3은 비어 있다.
- 코어가 모듈·익스텐션보다 먼저다(0.1.9). 0.1.9 모듈부터 `requires`로 새 코어를 요구할 수 있어서, 같은 묶음의 코어를 먼저 적용해 installed-manifest에 새 버전이 적힌 뒤 모듈을 적용한다. 데몬 `apply_updates`의 정렬도 이 함수를 쓰고(`updates.rs`), 업데이터의 `apply_target_keys`는 받은 키 목록을 이 순서로 다시 세운다(옛 데몬은 모듈을 코어 앞에 적는다. 같은 순위는 받은 순서). 그 위에 `apply_order`가 같은 묶음 안에서 `requires`하는 키를 앞으로 당긴다(순환하면 남은 것 중 맨 앞부터). 데몬 `apply_updates`, 목록 없는 적용, `pending_keys_in_apply_order`가 모두 이 함수를 쓴다. 코어를 먼저 적용하므로, 뒤의 모듈이 실패하면 코어만 새것이고 남은 것(GUI·CLI 포함)은 건너뛴 채 옛것으로 남는다(첫 실패에서 멈추는 규칙. 결과에 건너뛴 키가 남는다).
- 알 수 없는 key는 업데이트 대상에서 빠진다(`lib.rs` `try_from_manifest_key`). `installer`는 `Component::Installer`로, 설치 폴더의 `saba-chan-installer.exe`(제거기)를 받은 exe로 바꾸고 복사가 실패하면 원래 사본을 되돌린다(`apply.rs` `apply_installer_update`). `from_manifest_key`는 모르는 key를 `Module`로 폴백한다(`lib.rs:118-120`).
- 설치하지 않은 모듈·익스텐션은 업데이트 목록에 넣지 않는다. 새로 받는 것은 목록 화면의 몫이다(`lib.rs:515-518`).
- **설치 구성**(`updater/src/profile.rs`, 0.1.9): installed-manifest 옆(데이터 폴더)의 `install-profile.json`(`{"profile":"headless"}`)이 `"desktop"`|`"headless"`를 적는다(`Profile::load`/`save`. 없거나 읽지 못하거나 모르는 값이면 `desktop`, 0.1.8까지의 설치). 컴포넌트가 어느 구성에 드는지는 `versions.toml` `[components.<키>] profiles = [...]` 한 곳에서 정하고(빌드에 묶여 `versions::profiles`로 읽는다), 표시가 없으면 모든 구성에 든다. 지금은 `gui`만 `profiles = ["desktop"]`이다. `check_for_updates`는 설치 구성에 들지 않는 manifest 키를 건너뛰어 헤드리스 설치에 GUI가 끌려 들어오지 않는다. requires 검사에 쓰는 버전 맵(`dependency_versions_for`)도 같은 구성으로 걸러, 헤드리스에서는 번들 GUI 버전이 requires를 채우지 않는다. installed-manifest는 구성요소 → 버전 맵 그대로 두어 섞지 않는다(0.1.8이 그 맵을 구성요소 목록으로 보인다).
- **로컬 버전 판정 순서**(`collect_local_versions`, `lib.rs:585-624`): 먼저 `installed-manifest.json`(`<data_dir>/installed-manifest.json`)을 본다. 앱 컴포넌트가 거기 없으면 빌드에 묶인 `versions.toml` 버전을 쓰고(설치기는 빼고. 0.1.7까지 기록하지 않아 깔려 있는데 기록이 없으면 옛 사본으로 보고 바꾼다, `fill_bundled_versions`·`unknown_version_needs_update`), 모듈은 `module.toml`, 익스텐션은 `manifest.json`의 id·version을 읽는다.
  - ~~`saba-core` 폴백이 updater-lib의 `CARGO_PKG_VERSION`이다~~ → 해결: 폴백은 `versions.toml`의 컴포넌트별 버전이다(`lib.rs:589-592`, `versions.rs`). daemon은 기동할 때 자기 버전을 installed-manifest에 적는다(`launch_ticket.rs:28-30` `record_core_version`).
  - "설치돼 있는데 버전을 모르면 최신으로 간주하고 installed-manifest에 기록"하는 로직이 있다(`lib.rs:519-523`). 거짓 양성을 막으려는 것이지만, 실제로 구버전이어도 영구히 최신으로 표시될 수 있다.

### 1.3 Release manifest 형식

릴레이가 주는 서명된 manifest 하나가 유일한 출처다(`updater/src/relay.rs:52-88`). 형식:

```jsonc
{
  "manifest": {
    "version": "0.1.1", "channel": "stable", "platform": "windows-x64",
    "released_at": "...", "is_critical": false,
    "components": {
      "saba-core":        { "version": "0.1.1", "asset": "saba-core-windows-x64.zip", "size_bytes": 0, "sha256": "…", "url": "<R2 공개 URL>", "install_dir": "." },
      "module-palworld":  { "version": "…", "asset": "module-palworld.zip", "sha256": "…", "url": "…", "install_dir": "modules/palworld", "meta": { "display_name": "…" } },
      "ext-steamcmd":     { "version": "…", "asset": "ext-steamcmd.zip", "sha256": "…", "url": "…", "meta": { "name": "…", "min_app_version": "…" } }
    }
  },
  "keyId": "saba-updater-v1", "signature": "<Ed25519>"
}
```

- 컴포넌트 키는 `saba-core`, `cli`, `gui`, `updater`, `installer`, `locales`, `module-<name>`, `ext-<id>`다. 업데이터가 모르는 키는 건너뛴다.
- 다른 플랫폼 몫(D3c): 한 서명 manifest의 맨 위 `platform`·`components`는 `windows-x64` 그대로 두고(0.1.10까지의 업데이터는 이것만 읽는다), 다른 플랫폼은 `platforms.<플랫폼>.components`에 그 플랫폼의 목록 전체를 싣는다(`"platforms": {"linux-x64": {"components": {"saba-core": {"asset": "saba-core-linux-x64.zip", …}, "locales": …, "module-…": …}}}`). 업데이터·설치기·데몬 카탈로그는 서명을 검증한 뒤 자기 플랫폼이 맨 위가 아니면 그 목록으로 바꿔 읽고, 어디에도 없으면 플랫폼이 다르다고 거부한다(`ReleaseManifest::for_platform`). 모듈·익스텐션·`locales`는 같은 파일을 모든 플랫폼 목록에 싣는다. 릴레이 등록 본문의 `assets`는 플랫폼마다 한 줄씩 적어(같은 파일이면 같은 `r2Key`) 릴레이가 `platform=linux-x64` 확인에 이 릴리즈를 고른다(R2에는 한 번만 올린다).
- `installer`는 0.1.5부터 zip이 아닌 `saba-chan-installer.exe` 그대로다(`versions.toml`, `.github/scripts/package-release.py`). 소개 페이지 다운로드(relay `/v1/updates/download/installer`)가 최신 stable manifest의 이 `url`로 보낸다. 설치기는 이 항목의 `version`만 읽고(2.5단계) 자기 자신을 설치 폴더에 복사하며 그 버전을 installed-manifest의 `installer`로 적는다. 업데이터는 이 기록이 manifest보다 낮으면 사본을 바꾼다. 0.1.4 이전 릴리스는 zip 그대로 둔다.
- `requires`(다른 컴포넌트 최소 버전)와 `meta`(목록 화면용)는 선택이다. `scripts/versions.py`가 모듈은 `[module.dependencies] saba-core`에서, 익스텐션은 `dependencies."saba-core"`(없거나 `"*"`이면 `min_app_version`을 `>=`로)에서 `requires.saba-core`를 만든다(`extension_core_requirement`). 0.1.9부터 지킨다: `check_for_updates`가 `requires`를 `ComponentVersion.requires`에 싣고 `pending.json`에도 실어(없으면 생략, 옛 업데이터는 무시) 업데이터 `--apply`도 네트워크 없이 본다. `apply_single_component`는 적용 전에 `check_dependencies`(앱 컴포넌트는 installed-manifest와 번들 버전, 모듈·익스텐션은 디스크에 실제로 있는 버전만. 설치 구성에 들지 않는 키(헤드리스의 `gui`)는 빼므로 그 키를 requires하면 not installed로 실패한다. 카탈로그 설치·삭제는 installed-manifest를 고치지 않기 때문이다. `dependency_versions`, `unmet_requires`)로 확인하고, 못 미치면 `"<key> requires saba-core >=0.1.9 but 0.1.8 is installed"`로 실패한다(첫 실패에서 멈추는 규칙에 따라 뒤는 건너뛴다). 데몬의 카탈로그 설치(`POST /api/modules/manifest/:id/install`)도 같은 함수로 데몬이 아는 버전(`component_versions`)과 비교해 받기 전에 `{ok:false, error}`로 거절한다. 0.1.8 이하 업데이터·데몬은 `requires`를 보지 않으므로 이 검사는 0.1.10 적용부터 효과가 있다.
- 서명 검증 공개키는 바이너리에 들어 있다(`signature.rs:21`). 검증을 통과하지 못하거나, 플랫폼이 요청과 다르거나 고른 채널이 받지 않는 채널이거나, 현재보다 낮은 버전이면 거부한다(`relay.rs` `verify_release`). 서명이 맞아도 컴포넌트 키, `asset` 파일 이름, `install_dir`의 각 칸이 영문·숫자·`.`·`_`·`-`만으로 되어 있지 않거나 `.`으로 시작하면(`..`, 절대 경로, 드라이브 `:`) manifest 전체를 거부한다(`check_manifest_paths`). `module-`·`ext-` 키는 접두사를 뗀 이름도 같은 규칙을 지켜야 한다(`module-..`, `ext-` 거부). 이 값들은 그대로 모듈·익스텐션 폴더, 받을 파일, 설치 폴더 경로에 붙는다. 단 이미 최신이라 버전만으로 manifest를 받은 경우에는 채널이 달라도(같은 버전이 stable·beta 둘 다에 있으면 릴레이는 늦게 등록한 행을 준다) 그 버전이 지금 깔린 버전과 같으면 받아서 컴포넌트를 비교한다. 그렇게 받은 manifest에 이 플랫폼 몫이 없으면(그 버전에 아직 그 플랫폼 빌드가 없음, 예: 0.1.11의 `linux-arm64`) 확인 실패가 아니라 받을 것이 없다고 본다(`fetch_verified_release`). check 응답의 `latest`는 서명 밖이라, 그 `version`이 서명된 manifest의 `version`과 다르면 거부한다(`bind_release`). 그래서 적용 결과에 싣는 릴리즈 버전은 서명된 값이다. 패치노트(`notes`)는 릴레이에 등록하는 값이라 서명 밖에 있다.

### 1.4 어디서 가져오는가

| 용도 | 요청 | 근거 |
|---|---|---|
| 새 버전 확인 | `GET {relay_url}/v1/updates/check?channel&platform&current&client_id`. 아무것도 설치되지 않았으면(설치기, 목록) `current=0.0.0`을 보낸다 | `relay.rs:117-120, 163-179` |
| manifest | `latest.manifestUrl` 또는 `GET /v1/updates/manifest/:version` | `relay.rs:181-188` |

| 모듈·익스텐션 목록 | 같은 manifest의 `module-*`/`ext-*` (`relay::latest_catalog`) | `relay.rs:109-115` |

- 기본 릴레이 주소는 `relay::DEFAULT_RELAY_URL`, 채널은 `stable`이다(`relay.rs:21-23`). 채널은 정식(`stable`) ⊂ 미리보기(`rc`) ⊂ 베타(`beta`) ⊂ `nightly` 순으로 쌓이고, 위 채널을 고른 클라이언트는 아래 채널 릴리즈도 받는다(`relay::CHANNELS`·`channel_includes`, 릴레이 `routes/updates.ts` `CHANNEL_ORDER`와 같은 규칙). 앱에서는 정식·미리보기·베타만 고른다(GUI 사바 스토리지의 업데이트 채널, CLI `update config channel=beta`, 데몬 `PUT /api/updates/config`). 모듈·익스텐션 카탈로그(`relay::latest_catalog`)도 고른 채널을 쓴다. 같은 번호대의 시험판은 프리릴리스 번호로 낸다(`0.1.11-beta.1` < `0.1.11-rc.1` < `0.1.11`). `versions.toml`의 `[release] channel`은 이 셋 중 하나여야 하고 정식은 프리릴리스 번호를 쓸 수 없다(`scripts/versions.py` `load`). 채널 규칙이 없는 0.1.10 이하 업데이터는 고른 채널의 manifest만 받는다. `relay_url`에 `scripts/mock-release-server.js` 주소를 넣으면 모의 릴레이로 시험할 수 있다(`lib.rs:246-249`). 다만 모의 릴레이 서명 키는 `mock-relay` 기능으로 빌드한 개발용 바이너리만 믿는다(`signature.rs:26-28`, `updater/Cargo.toml` `[features]`). 설치기(`saba-chan-cli install`)는 `saba-chan-cli`의 `mock-relay` 기능으로 빌드하면 `SABA_RELAY_URL`을 따르고(`installer/core` `release::relay_url`), 모의 릴레이에 `--zips <폴더>`를 주면 그 폴더의 실제 릴리즈 zip(`package-linux.py` 출력 등)을 그대로 싣고, 그 폴더에 없는 앱 컴포넌트는 싣지 않는다(GUI 없는 `linux-arm64`처럼. 모듈은 글자 zip 그대로).
- 코어가 최신이어도 같은 릴리즈 manifest를 받아 컴포넌트별로 비교한다(GUI·CLI·모듈이 뒤처졌을 수 있으므로, `relay.rs:198-223`).

### 1.5 무결성 검증

- `UpdateManager::verify_integrity` (`lib.rs:469-473`)는 `integrity::verify_installed`를 부른다. 업데이터가 적용할 때 zip에서 푼 파일마다 SHA-256을 `<data_dir>/installed-files.json`에 적어 두고(`record_install`, `integrity.rs:104-121`), 검사는 그 기록과 지금 파일만 비교한다. 네트워크를 쓰지 않는다(`integrity.rs:1-6`).
- 결과 상태는 `Verified`, `Tampered`, `FileNotFound`, `Error` 중 하나다(`integrity.rs:45-55`). 설치기로 처음 깐 코어 컴포넌트(모듈·익스텐션 밖)는 기록이 없어 결과에 나오지 않는다. 0.1.6까지의 설치기가 기록 없이 둔 모듈·익스텐션은 업데이트 확인이 같은 버전이라도(로컬이 더 새 버전이면 빼고) 업데이트 대상으로 올려(`UpdateManager::reinstall_from_catalog`), 적용하면 기록과 공식 표시가 생긴다.
- `installed-files.json`, `official-components.json`, `installed-manifest.json`은 같은 폴더의 임시 파일에 쓴 뒤 이름을 바꿔 통째로 바꾼다(`lib.rs` `write_atomic`). 고쳐 쓸 때 내용이 깨진 기록은 `<이름>.corrupt-<시각>`으로 옮겨 두고 새로 쓴다(`lib.rs` `read_json_for_update`, 그대로 두면 기록이 영영 안 되고, 빈 표로 덮어쓰면 다른 컴포넌트의 기록이 흔적 없이 사라진다). 파일을 읽지 못하면(권한 등) 덮어쓰지 않고 오류를 낸다. 설치기도 `read_installed_manifest_for_update`로 읽는다. 업데이터의 적용 결과 기록은 `UpdateManager`가 가진 기록 경로(`installed_manifest_file`)에 쓴다. `installed-manifest.json`을 해석할 수 없으면 업데이터는 표 없는 `--apply`를 옛 데몬 전환 경로로 받아 주지 않는다(`launch_ticket.rs` `installed_core_predates_tickets`). 기록하는 쪽은 경고만 남기고 적용·설치는 그대로 성공한다.
- ~~**해시 의미 불일치**: manifest의 zip 해시를 압축을 푼 파일과 비교해 항상 `Tampered`가 된다~~ → 해결: manifest 해시는 다운로드 검증에만 쓰고, 무결성 검사는 설치 때 기록한 파일 해시를 본다(`integrity.rs:1-6`).
- 다운로드는 해시를 확인한다: `download_verified`가 받은 파일의 sha256을 manifest 값과 대조하고(`lib.rs:673, 727`), 적용 직전에 staging 파일을 다시 대조한다(`lib.rs:876-886`). 응답 머리나 다음 조각이 30초(`download::IDLE_TIMEOUT`) 동안 오지 않으면 끊고, manifest의 `size_bytes`보다 많이 오면 끊는다. `<이름>.part`에 받아 다 맞을 때만 이름을 바꾸므로, 다시 받다 실패해도 이미 받아 둔 파일은 그대로다(`download.rs`).
- daemon API는 `GET /api/updates/integrity`이다(`src/ipc/updates.rs:115, 814`).

### 1.6 다운로드 → apply → swap → rollback 흐름

1. **확인**: `POST /api/updates/check`와 daemon의 주기 확인이 같은 `check_and_follow_up`을 거친다(`updates.rs:169, 217-253`) → `check_for_updates()` (`lib.rs:482-557`). 릴레이 manifest 하나로 모든 컴포넌트를 비교한다. 이미 받아 둔 파일이 있고 최신 버전이 그대로면 적용 대기 상태를 이어 간다(`keep_staged`, 다운로드 사이에 주기 확인이 끼어도 적용할 것이 사라지지 않는다). Locales 업데이트가 있으면 사용자에게 알리지 않고 백그라운드에서 다운로드·적용한다(`updates.rs:225-231`, `silent_apply_locales` 279). Locales도 모듈처럼 백업한 뒤 폴더를 통째로 바꾼다(`replace_dir`, 실패하면 되돌린다). `auto_download`이면 나머지 업데이트도 미리 받아 두고 pending manifest를 저장한다(`updates.rs:234-250`). 여러 개를 받다 하나가 실패해도 나머지는 받고, 받은 것은 pending에 남긴 뒤 오류를 돌려준다. 상태의 `release_notes`는 GUI 언어(`config.json` `gui.language`, 없으면 OS 언어, 그것도 없으면 영어)로 완료 마커와 같은 규칙(`notes_for`)으로 고른다. 적용은 언제나 사용자가 고른다.
2. **다운로드**: `POST /api/updates/download` → staging 디렉터리로 받는다.
   - Windows: `%APPDATA%/saba-chan/updates/`
   - Unix: `~/.cache/saba-chan/updates/` (`constants.rs:148-167`)
   - 진행률은 `GET /api/updates/download/progress`로 본다(`updates.rs:450`).
3. **apply 분기**: `POST /api/updates/apply {components:[…]}` (`updates.rs:475-596`). 본문이 없거나 공백이면 전체 대상, 깨진 JSON이면 400 `invalid_body`다(`:348-357`). download도 같다
   - 대상에 `Gui`, `Updater`, `CoreDaemon` 중 하나라도 있으면 **전부 updater exe에 맡긴다**(`updates.rs:511-520`). 이때 daemon은 `staging/pending.json`(`state.rs:19-45`)과 `staging/apply-targets.json`(`state.rs:109-116`)을 쓰고 `{requires_updater:true, needs_updater:[…]}`를 응답한다.
   - 그렇지 않으면 daemon이 직접 `apply_single_component`를 실행한다. 그 뒤 모듈은 `supervisor.refresh_modules()`, 익스텐션은 `extension_manager.rescan()`으로 hot-reload한다(`updates.rs:559-587`).
4. **updater exe 실행**은 데몬이 한다: `POST /api/updates/launch-updater {relaunch}` → 데몬이 일회용 실행 표를 끊고(`launch_ticket.rs:1-5`) `saba-chan-updater --apply --wait-pid <데몬 PID> --launch-token <표> [--relaunch …]`를 분리 실행한 뒤 스스로 종료한다(`src/ipc/updates.rs:609-675`). 그사이 다시 불리면 409 `updater_already_launched`로 거절한다. 표를 새로 끊으면 먼저 띄운 업데이터의 표가 무효가 되어 아무것도 적용되지 않은 채 데몬만 끝나기 때문이다. 그 전에 데몬에 등록된 GUI가 떠 있으면 끄고(GUI가 부른 경우는 스스로 끝날 3초를 기다린다), `--relaunch`를 그 GUI로 바꾼다. CLI·자동 업데이트로 시작해도 GUI 파일이 잠겨 교체가 실패하지 않는다. GUI(Tauri 셸 `updater_launch_apply`, `saba-chan-gui/src-tauri/src/native.rs:81-102`. `relaunch`는 자기 exe 경로 `current_exe()`)와 CLI(PR #6 기준 `update apply`, `saba-chan-cli/src/cmd/update.rs:249`, `client.rs:785-789`)는 이 API만 부른다.
5. **updater exe** (`updater/gui/src-tauri/src/lib.rs`)
   - 인자는 `--apply [--wait-pid <pid>] --launch-token <t> [--headless] [--relaunch <exe> [extra…]]`다(`lib.rs` `run`). `--relaunch` 앞의 인자만 업데이터의 것이다. `--headless`(헤드리스 설치에서 데몬이 붙인다. 다시 띄울 것을 받지 않았으면 데몬은 자신을 `--spawned`로 넘긴다, `updates.rs` `updater_args`, 06 §9)면 Tauri를 시작하지 않고 같은 적용(`apply_staged`)을 돌린 뒤 `--relaunch`로 받은 것만 다시 띄우고(설치된 GUI를 찾는 예비 동작은 쓰지 않는다) 적용이 다 됐고 받은 것을 다시 띄웠으면 0, 아니면 1로 끝난다(다시 띄우기가 세 번 다 실패해도 1. `--relaunch`가 없으면 아무것도 띄우지 않고 로그에 경고를 남긴다). 진행은 `%TEMP%/saba-updater.log`에만 남는다. 표가 없거나 맞지 않으면 적용하지 않고 끝낸다. 표를 모르는 옛 데몬(0.1.2 미만)이 띄운 경우만 표 없이 받는다(`lib.rs:427-448`). `--wait-pid`가 있으면 그 PID가 끝나기를 최대 30초 기다린다(`lib.rs:450-467`). install_root는 자기 exe 위치로 정한다(`lib.rs:471-477`).
   - 적용 흐름은 updater-lib `UpdateManager::apply_staged`(`updater/src/apply_session.rs`) 하나이고, 창 업데이터는 그 진행(`ApplyProgress`)을 `apply:progress` 이벤트로 그대로 보낸다: `load_pending_manifest()` → `apply-targets.json`의 key를 차례로 `apply_single_component()`(`apply_target_keys`. 목록이 없을 때의 전체 적용처럼 첫 실패에서 멈추고, 남은 key는 `failed`에 "skipped after an earlier failure"로 적는다. 목록이 없으면 받아 둔 것 전체를 `pending_keys_in_apply_order()` 순서로 같은 `apply_target_keys`에 넘긴다. 매니페스트를 못 읽으면 실패 1건으로 알린다) → 성공·실패 모두 `UpdateCompletionMarker`(`<data_dir>/update-complete.json`, 실패 목록 `failed` 포함)를 저장 → 마커의 `release`는 다운로드 때 데몬이 `pending.json` 옆에 남긴 `pending-release.json`(릴리즈 버전·언어별 패치노트)에서 온다(`state.rs` `save_pending_manifest`/`pending_release`) → `clear_pending_manifest()`가 `pending.json`/`apply-targets.json`/`pending-release.json`과 받아 둔 압축 파일(`.zip`, `.tar.gz`, `.part`, 실패한 것 포함)을 지움(updater-lib `state.rs:84-104`) → 2초 뒤 `--after-update`를 붙여 relaunch(`lib.rs:73-216`, 312-350). 진행 상황은 Tauri 이벤트 `apply:progress`(`step`·`message`·`percent`·`applied`·`failed` 수)로 알린다. `message`는 진단용 영어 원문이고, 실패 화면은 `applied`·`failed` 수로 번역한 요약을 보인다. 다음 데몬이 결과를 `GET /api/updates/last-result`로 보여 준다(`updates.rs:787-792`).
   - relaunch는 Windows에서 `CREATE_BREAKAWAY_FROM_JOB`으로 띄우고, Job이 허용하지 않으면(os error 5) 그 플래그 없이 다시 띄운다(`lib.rs:346-362`). `--relaunch`가 없으면 설치 폴더의 GUI exe(`saba-chan-gui.exe`, 0.1.1 zip의 `Saba-chan.exe`)를 찾는다(`lib.rs:290-292`, updater-lib `lib.rs:279-285`). `--relaunch`가 GUI exe 이름(`saba-chan-gui.exe`, `Saba-chan.exe`)인데 그 파일이 없으면(적용 중 `.exe.old`로 비켜 난 경우) 설치 폴더의 GUI exe를 대신 띄우고 받은 인자를 그대로 넘긴다. 설치 폴더에서도 못 찾으면 받은 경로를 기다린다(`lib.rs` `relaunch_command`). GUI를 적용하면서 exe 이름이 바뀌면(0.1.1 `Saba-chan.exe` → `saba-chan-gui.exe`) 예전 exe는 `.exe.old`로 비켜 두고(다음 정리 때 지운다) 바탕화면·시작 메뉴 바로가기를 새 exe로 돌린다(`apply.rs` `retire_other_gui_exes`). 0.1.1 업데이터는 `saba-chan-gui.exe`만 찾으므로 0.1.1에서 올릴 때는 GUI가 첫 적용에서 빠지고, 새 데몬으로 한 번 더 적용해야 GUI까지 바뀐다(0.1.1 코드라 고칠 수 없다).
   - Tauri 커맨드: `get_apply_mode`, `start_apply`, `get_preferred_language`, `get_theme`, `check_after_update`.
6. **바이너리 swap** (`apply_binary_update` `apply.rs:94-177`, gui 184-230)
   - 대상 프로세스가 끝나기를 최대 15초 기다린다. 시간이 지나도 "attempting update anyway"로 그냥 진행한다.
   - Windows는 실행 중인 `X.exe`를 `X.exe.old`로 rename하고(재시도 5회, `apply.rs:64-92`, 366-382) zip에서 새 파일을 쓴다. `X.exe.old`가 아직 잡혀 있어 지울 수 없으면(지난 업데이트 뒤로 계속 도는 서버의 `saba-runner` 등) `X.exe.old.1`, `.old.2` … 중 비울 수 있는 이름을 쓴다(`apply.rs` `free_backup_path`). Linux는 알려진 바이너리만 `X.old`로 rename한다.
   - `cleanup_old_files()`는 install_root 바로 안의 사바쨩 실행 파일 `*.exe.old`·`*.exe.old.<n>`만 지운다. 적용 직후에 한 번, 아직 잡혀 있어 못 지운 것은 다음 `UpdateManager` 생성 때 지운다(`lib.rs:410-411, 837-840, 919-939`).
7. **rollback**
   - 모듈·익스텐션은 staging에 `*_backup` 복사본을 만들고, 교체 도중 실패하면 그 백업으로 되돌린다. 성공하면 백업을 지운다(`replace_dir`, `apply.rs:24-62`).
   - 바이너리와 GUI(설치 폴더 바로 안의 exe든 폴더 모드든)는 압축 해제 도중 실패하면 새로 생긴 파일을 지우고 비켜 둔 `.old`·`.update-bak`을 원래 이름으로 되돌린다. zip과 tar.gz가 같은 경로를 쓴다(`apply.rs` `extract_or_restore`). 적용이 끝난 뒤에 이전 판으로 돌아가는 경로는 없다.
   - ~~`prepare_daemon_update`는 호출하는 곳이 없다(죽은 코드)~~ → 해결: 함수가 지워졌다(grep 0건).
8. **설치 버전 기록**: `update_installed_versions_batch` → `installed-manifest.json`(`state.rs:173-193`). 코어가 바뀌면 Windows "설치된 앱" `DisplayVersion`도 갱신하는데, 이 설치 폴더의 항목만 고친다(`state.rs:199-207`, `uninstall_entry.rs:76-85`).

### 1.7 daemon, GUI, CLI가 updater를 부르는 방식

**daemon HTTP API** (`saba-chan/src/ipc/updates.rs:106-118`, `ipc/mod.rs:812`에서 merge):

| Method | Path | 동작 |
|---|---|---|
| GET | `/api/updates/status` | 캐시된 상태. Locales는 숨긴다 |
| POST | `/api/updates/check` | 릴레이를 조회한다 |
| POST | `/api/updates/download` | body `{components:[]}`. 본문이 없으면 전부 받는다 |
| GET | `/api/updates/download/progress` | 진행률 |
| POST | `/api/updates/apply` | body `{components:[]}`(없으면 전부). 직접 적용하거나 updater 위임을 판단한다 |
| POST | `/api/updates/launch-updater` | body `{relaunch:[exe, …]}`. 데몬이 updater를 띄우고 스스로 종료한다(`updates.rs:609-675`). 이미 띄웠으면 표를 새로 끊지 않고 409 `updater_already_launched` |

## 2. Installer (`saba-chan/installer/gui`, Tauri, v0.1.2)

크레이트 둘로 나뉜다(0.1.9 릴리즈부터, 무인 설치 설계 1단계. 크레이트 버전은 릴리즈 때 올린다).
- `saba-chan-installer-core`(`installer/core`, Tauri 없음, 버전은 `versions.toml` installer와 같이 간다): 설치 순서 `install(InstallOptions, &dyn InstallHooks) -> InstallProgress`(마지막 진행을 돌려준다)와 `release.rs`(릴리즈 받기, 업데이터와 같은 relay 경로), `runtime_bootstrap.rs`, `registry.rs`, `shortcuts.rs`, `uninstall.rs`(`do_uninstall(Keep, on_progress) -> 남은 항목`, 창·명령창 공통). 진행은 `InstallHooks::progress`로 알리고(받기와 같은 작업에서 불리므로 막지 않는다), 쓸 수 없는 폴더는 `InstallHooks::elevate_create_dir`로 만든다. 기본 구현은 상승하지 않고 `elevation_failed`로 멈춘다(창 없는 설치). 릴리즈는 `release::fetch_latest`가 서명을 검증해 돌려주는 `VerifiedRelease`만 `InstallOptions.release`로 받는다(호출자가 만든 manifest로 검증을 건너뛸 수 없다. 모듈·익스텐션 하나를 받아 공식으로 기록하는 `release::install_addon`도 같은 이유로 크레이트 밖에 열지 않는다). 받은 zip(본체·모듈·익스텐션)은 프로세스마다 따로인 `%TEMP%/saba-chan-installer-<pid>`에 둔다(`release::work_dir`, 창 인스톨러와 CLI가 함께 돌아도 서로 지우지 않는다). 설치가 어느 경로로 끝나든 그 폴더를 지우고, 도중에 끊겨 남은 폴더는 제거기가 `remove_temp_files`에서 지운다(그 PID가 아직 프로세스 목록에 있으면 두고, 목록을 못 읽으면 하나도 지우지 않는다. `stale_work_dirs`). `InstallOptions.uninstaller_exe`가 있으면 그 exe를 설치 폴더의 `saba-chan-installer.exe`로 복사해 제거기로 등록하고 installed-manifest의 `installer`에 버전을 적는다. 없으면 둘 다 건너뛰고, Windows의 설치된 앱 항목도 만들지 않는다(실행할 제거 명령이 없다). 설치기 GUI와 `saba-chan-cli install`(04 §3.1)이 이 crate를 쓴다. CLI는 `uninstaller_exe` 없이 부르므로 CLI로 처음 설치한 사본은 Windows 앱 목록에 나오지 않고, 지울 때는 그 설치의 `saba-chan-cli uninstall`(04 §3.1)을 쓴다.
- `saba-chan-installer`(`installer/gui/src-tauri`, Tauri): 화면 상태와 Tauri 커맨드, UAC 상승(`--elevate-mkdir`), 로그 초기화. `WindowHooks`가 진행을 `install:progress`·`uninstall:progress` 이벤트로 보내고 상승을 UAC로 한다. 제거기로 자기 exe를 넘긴다.

아래 `lib.rs` 근거는 따로 적지 않으면 `installer/core/src/lib.rs`다.

**설치 위치**
- 기본 경로는 이미 설치된 폴더가 있으면 그 폴더, 없으면 `constants::default_install_dir`(Windows `%ProgramW6432%`·`%ProgramFiles%`(없으면 `C:\Program Files`) 아래 `Saba-chan`, Unix `~/.local/share/saba-chan`)(`default_install_path`, `existing_install`). 설정 > 고급과 `saba-chan-cli config paths`가 이 기본값을 함께 보인다.
- 상대 경로, 드라이브 루트·홈 폴더, 데이터·모듈·익스텐션 폴더와 겹치는 폴더에는 설치하지 않는다(`check_install_dir`, `invalid_install_dir`).
- 모듈·익스텐션 위치(`InstallOptions.components_dir`, 창 인스톨러의 "모듈·익스텐션 위치", CLI `--components-dir`)를 고르면 1단계에서 검사하고(`components_dir_invalid`), 3.4단계에서 데몬과 같은 `component_dirs::move_to`로 옮긴 뒤(`components_dir_failed`, 01 §1.5) 이후 모듈·익스텐션·공유 모듈을 그 폴더에 푼다.
- 한 PC에는 설치본 하나만 둔다(설치본들이 데이터 폴더를 함께 쓴다). 설치 목록(`<data_dir>/installs.json`)과 Windows 설치된 앱 항목 중 `saba-core`가 남은 다른 폴더가 있으면 설치를 시작하지 않고 `installed_elsewhere`로 그 폴더를 알린다(`other_install`). 데이터 폴더를 따로 정한 설치(`SABA_DATA_DIR`)는 그 폴더의 설치 목록만 본다. CLI `install`은 받기 전에 같은 검사로 거절한다.
- 고른 폴더가 비어 있지 않고 사바쨩 설치(`saba-core`나 GUI exe)도 아니면 그 아래 `Saba-chan` 폴더에 설치한다. 찾아보기·직접 입력 모두 `set_install_path`가 바꾼 경로를 돌려줘 화면에 보인다(`lib.rs` `dedicated_install_dir`).
- 설치기가 새로 만든 폴더에만 `.saba-chan-install` 표시 파일을 둔다(원래 있던 빈 폴더는 나중에 다른 파일이 생길 수 있어 표시하지 않는다). 제거기는 이 표시가 있을 때만 폴더를 통째로 지우고, 없으면(0.1.4 이전 설치, 사용자 파일이 있던 기존 설치 폴더) 사바쨩 실행 파일·`locales` 폴더·공유 모듈 파일만 지운 뒤 폴더가 비었을 때만 지운다(`uninstall.rs` `remove_install_dir`).
- 쓰기에 실패하면 창 인스톨러는 UAC로 권한을 올려 디렉터리를 만든다(`installer/gui/src-tauri/src/lib.rs` `elevate_create_dir`). 창 없는 설치는 상승하지 않고 멈춘다.
- 데이터는 `%APPDATA%/saba-chan`에 둔다(updater constants와 같다).
- 로그는 `%TEMP%/saba-chan-installer.log`에 남는다(`log_file_path`, 초기화는 `installer/gui/src-tauri/src/lib.rs` `init_logging`).

**`install` 단계** (`installer/core/src/lib.rs` `install`)

| 단계 | 내용 |
|---|---|
| 1 (0-5%) | 다른 폴더의 설치본 검사(`installed_elsewhere`), install dir 생성, 쓰기 probe, 필요하면 권한 상승 |
| 2 (5-10%) | 릴레이에서 서명된 최신 manifest를 받아 검증한다(`release.rs` `fetch_latest`) |
| 2.5 | manifest의 `installer.version`이 현재 `CARGO_PKG_VERSION`보다 높으면 설치를 차단한다(`install`의 `installer_outdated`) |
| 3 (10-40%) | 업데이터가 아는 키 중 모듈·익스텐션을 뺀 컴포넌트(`installer` 제외)를 모두 R2에서 받아 SHA-256을 확인하고, 임시 폴더에 한 번 풀어 본다(`release.rs` `installable`, `fetch_all`). 하나라도 실패하면 설치 폴더를 건드리지 않고 멈춘다(`download_failed`·`extract_failed`) |
| 3.2 | 받기와 검증이 모두 끝난 뒤, 덮어쓰기 전에 이 설치 폴더의 프로세스를 끈다(`uninstall.rs` `stop_daemon_before_install`). `saba-core`는 실행 파일 경로(받은 경로와 실제 경로 둘 다)로 찾고, 못 찾으면 설정된 포트의 `/health` PID를 보고 그 exe가 이 폴더 안일 때만 대상으로 삼는다. 경로를 못 읽어 어느 설치의 것인지 모르면 끄지 않고 `daemon_running`으로 멈춰 사용자가 먼저 끄게 한다(`port_daemon_to_stop`). `/api/daemon/shutdown`은 설정된 포트의 `/health` PID가 찾은 데몬일 때만 보낸다(다른 데이터 폴더·포트로 도는 다른 설치의 데몬이 그 포트에 답할 수 있다. `asks_to_shut_down`). 보낸 뒤 20초 안에 안 끝나면(보내지 않았거나 거절되면 바로) 그 PID만 kill. 이어서 이 폴더의 GUI exe와 `saba-chan-cli`를 그 PID만 끈다(트리째 끄면 데몬이 남았을 때 그 아래 게임 서버까지 죽는다). 포터블 GUI는 실행기가 임시 폴더에 풀어 띄우므로, 실행기를 끄기 전에 그 자손(`descendants_in`)을 찾고, 데몬을 끄기 전에 `GET /api/clients`에서 `installRoot`가 이 폴더인 GUI PID를 받아 둔다. 그 PID가 아직 GUI 이름의 프로세스일 때만 끈다. 단계마다 `%TEMP%\saba-chan-installer.log`에 남긴다 |
| 3.5 (40-45%) | 3.2 뒤에 받은 zip을 `install_dir/<install_dir>`에 푼다. 푸는 중에 실패하면(디스크 부족 등) `extract_failed`로 멈춘다 |
| 3.6 | 공유 모듈(`i18n.py`, `daemon_rcon.py`)을 데몬 데이터 폴더의 `python-shared/`로 복사(`install_shared_modules`. 모듈 폴더는 Python import 경로가 아니다) |
| 4 (45-55%) | 선택한 모듈을 manifest의 `module-<id>`에서, `requires_extensions`에 따른 익스텐션을 `ext-<id>`에서 R2로 받아 SHA-256을 확인하고 설치한다(`install`의 4단계, `install_required_extensions`). 받은 익스텐션은 `config.json`의 `extensions.enabled`에 더해 켜 둔다(`enable_extensions`). 푼 폴더는 데몬 카탈로그 설치와 같이 `installed-files.json`에 해시를, `official-components.json`에 키를 적어 신뢰 표시가 `verified`가 된다(`release.rs` `install_addon_zip`). 새 zip은 옆의 `.<이름>.new-<pid>`에 다 푼 뒤에 있던 폴더와 바꾸므로, 풀다가 실패하면(깨진 zip, 디스크 부족) 있던 모듈·익스텐션이 그대로 남는다. 기록하지 못하면 그 구성요소는 `unverified`로 격리되므로 설치 경고로 보인다. 실패는 경고로 남긴다 |
| 5 (55-70%) | portable Python(python-build-standalone, 판과 SHA-256은 `updater/src/python_pin.rs`에 고정)과 venv (`runtime_bootstrap.rs:42-51`). 실패해도 치명적으로 처리하지 않는다 |
| 6 | 없음: 로컬 Discord bot이 없어져 portable Node·npm install 단계도 지워졌다 |
| 7-8 | `setup_config`, 언어 설정을 `config.json`의 `gui.language`에 저장(`setup_config`, `save_language_setting`) |

레지스트리·바로가기·모듈·익스텐션처럼 실패해도 계속하는 단계는 완료 이벤트의 `warnings`·`log_path`로 보내고, 완료 화면이 목록과 로그 경로를 남겨 보여 준다(`installer.js` `enterComplete`). 설치를 멈추는 실패는 `step:'error'`에 `error_code`(`installed_elsewhere`·`elevation_failed`·`fetch_failed`·`installer_outdated`·`release_incomplete`·`download_failed`·`daemon_running`·`extract_failed`·`profile_failed`)와 `log_path`를 싣고, 화면은 코드별 번역 문구와 원문·로그 경로, [다시 시도](설정 시트로)를 보인다. "사바쨩 실행"이 실패하면 창을 닫지 않고 안내한다.

코어 zip을 풀 때 덮어쓸 exe가 잠겨 있으면(켜진 서버의 `saba-runner` 등) 업데이터와 같은 `move_aside_binary`로 `.exe.old`로 비켜 두고 계속한다.

Tauri 커맨드(`installer/gui/src-tauri/src/lib.rs`): `get_installer_state`, `set_install_path`, `set_language`, `set_shortcut_options`, `set_selected_modules`, `get_available_modules`(같은 manifest의 `module-*`, 폴백 없음), `fetch_latest_release`, `start_install`, `start_uninstall`, `get_app_mode`, `launch_app`, `get_preferred_language`, `browse_folder`. GUI는 `--uninstall` 인자로 installer를 uninstall 모드로 실행한다(`saba-chan-gui/src-tauri/src/native.rs:149-184`).

설치와 제거는 한 번에 하나만 돈다. 이미 돌고 있으면 `start_install`·`start_uninstall`이 `busy`로 거절하고 화면은 진행 중인 것을 그대로 둔다(`installer/gui/src-tauri/src/lib.rs` `WorkGuard`. 프로세스 안에서만 막는다). 설치기가 새로 만든 폴더의 전용 표시(`uninstall::INSTALL_MARKER`)는 폴더를 만든 바로 뒤에 쓴다(받다 실패한 뒤 다시 시도해도 전용 폴더로 남는다). Python 런타임 준비나 공유 모듈(`i18n.py`·`daemon_rcon.py`) 복사가 실패하면 설치는 이어 가되 완료 화면 경고에 띄운다.

**제거** (`uninstall.rs`): 대상은 제거기 자신이 든 설치 폴더 하나다(`uninstall.rs` `target_dir`). 설정된 포트의 데몬이 이 폴더의 것이면 먼저 `GET /api/servers`에서 꺼져 있지 않은 서버마다 `POST /api/instance/:id/stop`으로 정상 종료를 요청해 기다린다(서버마다 최대 90초). 이어서 데몬 아래 프로세스(러너 없이 띄운 서버 등. 제거기 자신과 그 위, 부모보다 먼저 시작한 프로세스는 뺀다, `tree_of`)를 적어 두고 데몬에 `/api/daemon/shutdown`을 보내, 요청이 받아들여졌으면 끝날 때까지 최대 20초(마지막 목록 조회가 걸리면 그만큼 더) 기다린다. 목록을 못 읽으면 자식을 모르므로 정상 종료 대신 데몬을 트리째 끊는다. 그다음 그 폴더에서 실행 중인 사바쨩 프로세스만 끝내고(`uninstall.rs` `stop_saba_processes`), 적어 둔 데몬 아래 프로세스 중 같은 PID·이름·시작 시각으로 남은 것도 트리째 끝낸다. 끈 프로세스(GUI 포함)는 PID·이름·시작 시각으로 적어 두고 실제로 끝났는지 최대 10초 확인하며(기다리는 사이 PID가 다른 프로그램에 다시 쓰였으면 끝난 것으로 본다), 아직 같은 프로세스로 남았으면 한 번 더 끊고 다시 최대 10초 기다린다(`wait_for_exit`). 프로세스 목록을 못 읽은 회차는 끝나지 않은 것으로 센다. 목록 조회(PowerShell)와 `taskkill`은 한 번에 10초까지만 기다린다(`output_within`). 끝나기 전에 지우면 끝나는 중인 프로세스가 파일을 잡고 있거나 다시 쓴다. 포터블 GUI 실행기가 임시 폴더에 풀어 띄운 실제 GUI(실행기의 자손, 제거기 자신은 뺀다, `descendants_in`)와 데몬에 이 설치로 등록된 GUI(`GET /api/clients`)도 끝낸 뒤, 그 폴더의 레지스트리 항목만 지운다(`registry.rs:78-93`). 로그인할 때 자동 실행 항목(01 §2.2 `/api/system/autostart`)은 이 설치 폴더의 실행 파일을 가리킬 때만 지운다(`autostart::remove_if_in`, 다른 설치본으로 켜 둔 것은 둔다). `%APPDATA%/saba-chan`과 모듈 폴더는 설치본들이 함께 쓰므로 다른 설치본이 남아 있으면 지우지 않는다(`uninstall.rs` `last_install`). 다른 설치본은 레지스트리 항목(`uninstall_entry.rs` `is_last_install`)과, 설치기·`saba-chan-cli install`이 설치를 마칠 때 적는 폴더 목록 `%APPDATA%/saba-chan/installs.json`에서 데몬 실행 파일이 남은 다른 폴더(`other_listed_install`)로 본다. 제거 항목이 없는 CLI 설치(`--dir`)도 이 목록으로 셈에 든다. 지우는 폴더는 목록에서 뺀다. 제거기 옆에서 설치 폴더를 찾지 못하면 마지막 설치본으로 치지 않아 사용자 데이터를 지우지 않는다. `SABA_DATA_DIR`·`SABA_MODULES_PATH`·`SABA_EXTENSIONS_DIR`로 데이터 폴더를 바꿔 두었으면 그 폴더는 남의 것일 수 있어 지우지 않는다(`owned_data_dir`). 마지막 설치본이면 `config.json` `paths`로 옮긴 모듈·익스텐션 폴더도 `.saba-chan-dir` 표시가 있을 때만 데이터 폴더 항목보다 먼저 지우고, 남은 `.<이름>.saba-moving`과 그래서 빈 위 폴더도 지운다(`remove_moved_component_dirs`, 남길 것과 무관하게 런타임 항목으로 본다). 앱이 만들지 않는 `.keys`(릴리스 서명 키)는 어느 경우에도 지우지 않는다(지우면 되돌릴 수 없다). 남길 것은 `Keep { settings, instances }`로 따로 고른다(`uninstall_entry.rs` `removable_data_entry`). 다시 받거나 만들 수 있는 런타임·캐시·상태 파일(모듈, 익스텐션, Python 런타임, 업데이트, 로그, 무결성·검사 기록, `installs.json` 등, `RUNTIME_ENTRIES`)은 무엇을 남기든 지운다. `instances/`(서버 파일, 월드, 백업, 인스턴스별 설정, `INSTANCE_ENTRIES`)는 인스턴스를 남기지 않을 때만, 그 밖의 것(설정, 토큰, 감사 기록, 앞으로 생길 파일)은 설정을 남기지 않을 때만 지운다. 아무것도 정하지 않으면 둘 다 남긴다(사용자 지정 10-22). 인자는 `--uninstall [--silent] [--remove-settings] [--remove-instances]`다(`keep_from_args`). 창 제거기는 두 체크박스(게임 서버 남기기, 설정 남기기)를 인자에서 정한 값(기본 켜짐)으로 띄우고(`get_app_mode`의 `keepSettings`·`keepInstances`), `start_uninstall(keepSettings, keepInstances)`로 시작한다. 실행 방식은 부르는 쪽이 정한다: 데스크톱 앱 설정의 제거는 창(`launch_uninstaller`가 `--uninstall`만 붙인다), Windows 앱 목록도 창(`UninstallString`), `saba-chan-cli uninstall`은 명령창이다. 명령창 제거(`--silent`, CLI)는 창과 같은 `do_uninstall`을 돌리고 단계 문구를 표준 오류로 적는다(`do_silent_uninstall`). CLI로 지울 때는 그 CLI 자신을 끄지 않는다(`stop_saba_processes`가 자기 PID를 뺀다). 프로세스를 끈 뒤 설치 폴더를 지우기 전에 그 설치의 `saba-core sandbox reset`으로 격리 실행의 프로필과 폴더 권한·표시를 거둔다(Windows, 최대 10분, 02 §격리 실행. 실패 줄은 남은 항목으로 보인다, `reset_sandbox`). 데이터 폴더 밖의 흔적은 `installer/core/src/traces.rs` 한 곳에 적고 무엇을 남기든 지운다: 임시 폴더의 이름이 정해진 항목(`TEMP_NAMES`: 설치기·업데이터 작업 폴더와 기록 파일), 끊긴 설치기의 `saba-chan-installer-<pid>`(그 PID가 아직 돌면 두고, 목록을 못 읽으면 고르지 않는다), 창 앱(Tauri) 식별자 폴더(`APP_IDENTIFIERS`: `%LOCALAPPDATA%\com.saba-chan.{app,installer,updater}`의 WebView 데이터, 리눅스는 `~/.local/share`·`~/.cache` 아래), 리눅스 `~/.cache/saba-chan`(업데이트 받기)과 `~/.local/share/applications/saba-chan.desktop`. 창 제거기가 끝날 때까지 쥐고 있는 자기 WebView 폴더와 `saba-chan-installer.log`는 정리 스크립트가 제거기 자신과 함께 지운다(`held_by_self`, `cleanup_script`). 새 임시 항목을 만들면 이 목록에 더한다: 테스트가 소스의 `temp_dir().join(...)` 이름을 모아 목록에 없으면 실패한다(`every_temp_name_in_the_source_is_listed`). 모듈·익스텐션 실행과 pip는 시스템 임시 폴더·사용자 pip 캐시 대신 데이터 폴더의 `temp`·`pip-cache`를 쓴다(`plugin::daemon_env`의 `TEMP`·`TMP`·`TMPDIR`·`PIP_CACHE_DIR`, `python_env::run_pip`. 격리 실행은 자기 임시 폴더로 덮는다). 둘 다 런타임 항목이라 늘 지운다. 지운 뒤 지울 항목이 남아 있으면 1초 간격으로 두 번 더 지우고, 그래도 남은 것은 로그에 남기고 결과에 알린다. 설치 폴더에서 지우지 못한 항목(전용 폴더면 남은 것 전부, 아니면 사바쨩 항목만, 실행 중인 제거기 자신은 정리 스크립트가 지우므로 뺀다, `install_leftovers`)도 같은 결과에 들어간다: 화면은 완료 문구 대신 "일부 파일이 남았습니다"와 남은 경로를 보여 주고(`UninstallProgress.left`), 조용한 제거(`--uninstall --silent`)는 남은 경로를 찍고 종료 코드 1로 끝난다.

**문제점**
- 기본 설치 경로가 `Program Files`(관리자 권한 필요)인데 레지스트리는 HKCU에 쓴다. 더 큰 문제는 updater exe와 daemon이 **권한 상승 없이** `install_root`에 쓴다는 점이다. 기본 경로에 설치하면 업데이트 적용이 권한 문제로 실패할 수 있다(추정, 매니페스트의 requestedExecutionLevel은 확인하지 않음).
- 모듈·익스텐션 소스는 하나다: 설치기, 데몬 목록, 업데이터가 모두 같은 릴리즈 manifest를 본다.

- GitHub Release는 사람이 raw 파일을 올리는 **입력 칸**으로만 쓴다. 업데이터·설치기는 GitHub를 보지 않는다.
- 배포용 Windows 빌드는 `build-windows.yml`이 한다(위 표). SignPath Foundation은 서명하는 모든 실행 파일의 제품 이름을 프로젝트 이름으로 묶으므로 데몬·러너(`build.rs`·`runner/build.rs`의 rc), CLI(`saba-chan-cli/build.rs` winres), 업데이터·인스톨러·GUI(`tauri.conf.json` `productName`)의 `ProductName`은 모두 `Saba-chan`이다. 데몬·러너·CLI는 `FileDescription`으로 구분되지만, tauri-build는 `FileDescription`에도 `productName`을 넣으므로 GUI·업데이터·인스톨러는 작업 관리자·UAC 창에서 모두 `Saba-chan`으로 보이고 창 제목으로만 구분된다. 로컬 Windows의 `scripts/build-windows.ps1`은 같은 순서의 개발·시험용 빌드로 남는다(서명하지 않는다). 버전은 `versions.toml`에서 읽고, 빌드 전에 `versions.py check`가 실패하면 멈춘다. 실제로 도는 Python(`py -3`, `python` 순, Store 스텁은 건너뜀)이 없으면 경고만 남기고 넘어가며, 발행 때 `versions.py manifest`가 exe 버전을 다시 대조한다(`build-windows.ps1:27-28`, 그 아래 check). GUI 화면을 `npm run build`(vite)로 먼저 만들고(`:59-72`, Tauri GUI가 `build/`를 exe에 넣는다), 이어서 `cargo build --release --workspace`(`:98`)가 데몬·CLI·업데이터·인스톨러와 함께 `target/release/saba-chan-gui.exe`를 만든다(`:127`).
- `package-release.py`는 **windows-x64 asset만** 만든다(staging에서 이름 끝이 `-<os>-<arch>.zip`인데 `windows-x64`가 아닌 것, 곧 `-linux-x64.zip`·`-linux-arm64.zip`·`-windows-arm64.zip`·`-macos-*.zip`은 Windows 원본으로 집지 않는다, `PLATFORM`·`PLATFORM_ASSET`). 화면 없는 리눅스 zip(D3c)은 `release.yml`이 그 실행에서 main 소스로 빌드한다: `cargo build --release --locked`로 `saba-core`·`saba-runner`·`saba-chan-cli`와 창 없는 업데이터(`-p saba-chan-updater --no-default-features`: `window` 기능을 빼면 Tauri·GTK·WebKit 없이 `--headless` 적용만 한다)를 만들고 `.github/scripts/package-linux.py`가 `saba-core-linux-x64.zip`(saba-core·saba-runner·공유 모듈)·`saba-chan-cli-linux-x64.zip`·`saba-chan-updater-linux-x64.zip`로 묶는다(실행 파일은 zip에 0755로 적는다. `extract_zip`은 zip에 실행 비트가 있으면 0755로 푼다). GUI는 같은 실행에서 GTK·WebKitGTK 개발 패키지를 깔고 프런트엔드(`npm run build`)를 묶어 `-p saba-chan-gui`로 빌드하고, `saba-chan-gui-linux-x64.zip`(saba-chan-gui와 앱 메뉴 아이콘 `saba-chan-gui.png`)으로 싣는다. `gui`는 `profiles = ["desktop"]`라 헤드리스 설치·업데이트는 받지 않는다. 업데이터는 리눅스에서 창 없이 하나만 빌드한다(데스크톱에서도 `--headless` 적용 뒤 `--relaunch`로 GUI를 다시 띄운다). 설치기는 리눅스 zip이 없다(`saba-chan-cli install`이 설치한다). manifest는 `--platform windows-x64 --also-platform linux-x64`로 만든다(§1.3). `{platform}`이 없는 asset은 `versions.toml`의 `platforms`(없으면 모든 플랫폼)에 드는 플랫폼에만 싣는다(`installer`는 `["windows-x64"]`). 리눅스 실행 파일은 OpenSSL 3 공유 라이브러리를 쓴다(Ubuntu 22.04·Debian 12 이상). 그래서 `release.yml`은 ubuntu-22.04 러너에서 빌드하고, glibc 2.35보다 새 기호를 요구하는 실행 파일이 있으면 멈춘다. ARM64(aarch64) 리눅스는 0.1.12부터 `linux-arm64` 작업이 GitHub의 ubuntu-22.04-arm 러너에서 같은 조건(glibc 2.35)으로 x64와 같은 구성(데몬·러너·CLI·창 없는 업데이터, 0.1.12 두 번째 베타부터 GUI도)을 빌드해 `package-linux.py --platform linux-arm64`로 묶고, `package-and-manifest`가 그 zip을 받아 `--also-platform linux-arm64`로 싣는다(`{platform}` asset은 파일이 없으면 그 플랫폼 목록에서 빠진다. 0.1.12-beta.1의 linux-arm64에는 GUI가 없다). ARM 작업은 OpenSSL과 GTK·WebKitGTK 개발 패키지를 깔고 프런트엔드를 묶어 빌드하며, 체크아웃한 main 커밋을 넘겨 `package-and-manifest`도 그 커밋을 빌드한다(기다리는 동안 main이 움직여도 x64·arm64·manifest가 같은 소스). R2 업로드는 등록 본문의 `assets`를 따르므로 따로 고칠 곳이 없다.
- 한 줄 설치(`install.sh`, 저장소 루트): `curl -fsSL https://raw.githubusercontent.com/WareAoba/saba-chan/main/install.sh | sh [-s -- <saba-chan-cli install 인자>]`. 릴레이에서 정식 채널 `linux-x64`(`uname -m`이 `aarch64`·`arm64`면 `linux-arm64`, 그 밖의 CPU는 멈춘다) 릴리즈의 manifest를 받아 CLI zip만 내려받고 manifest의 sha256·크기와 대조한 뒤(필요한 도구는 `curl`·`sha256sum`·`python3`. zip은 python3로 푼다: 클라우드 서버 이미지에는 `unzip`이 없는 일이 많다), 그 CLI로 `saba-chan-cli install`을 돌린다(묻는 말은 `/dev/tty`에서 받는다. 화면(`DISPLAY`·`WAYLAND_DISPLAY`)이 있고 SSH 세션이 아니면 데스크톱 구성, 아니면 헤드리스 구성이고 `--gui`·`--no-gui`로 정할 수 있다, 04 §3.1). 나머지는 CLI가 서명된 manifest를 번들 공개키로 검증해 설치한다(스크립트 자체는 서명을 보지 않는다: Windows 설치기 exe를 HTTPS로 받는 것과 같은 믿음). 기본 폴더는 `$XDG_DATA_HOME`(없으면 `~/.local/share`)`/saba-chan`. 끝나면 `~/.local/bin/saba-chan-cli` 링크를 건다. 데스크톱 구성(설치 폴더에 `saba-chan-gui`가 있음)이면 GUI가 데몬을 띄우므로 서비스를 걸지 않고, WebKitGTK(`libwebkit2gtk-4.1.so.0`, `ldconfig -p`. PATH에 없으면 `/sbin`·`/usr/sbin`의 것, 그마저 없으면 있다고 본다)가 있으면 GUI를 띄우고, 없으면 배포판별 설치 명령을 안내하고 데몬만 켠다(CLI를 쓸 수 있게). 헤드리스 구성이면 systemd 사용자 세션이 있을 때 `config autostart daemon`으로 서비스를 등록해(데몬을 잠깐 띄웠다 끈다) `systemctl --user start saba-chan.service`로 켠다. 세션이 없으면 데몬만 켠다. `linux-x64`에서 32비트 C 라이브러리(`ld-linux.so.2`)가 없으면 SteamCMD 게임에 필요하다고 안내만 한다(SteamCMD는 32비트라 없으면 설치가 "required file not found"로 실패한다). 안내 문구는 `LANG`이 한국어면 한국어, 아니면 영어다(받기 전이라 locales를 쓸 수 없다).
- 필수 구성요소는 `versions.toml`의 `[components.<키>] required = true`(지금은 `saba-core`, `gui`, `updater`) 한 곳에서 정한다. 설치기는 설치 구성(`InstallOptions.profile`)에 들지 않는 것(`profiles`)을 필수에서도 받을 목록에서도 뺀다: 헤드리스는 `saba-core`·`updater`만 필수이고 GUI를 받지 않으며 바로가기를 만들지 않는다. 고른 구성은 `install-profile.json`에 적는다(헤드리스는 적지 못하면 `profile_failed`로 실패한다. 기록이 없으면 데스크톱으로 읽히기 때문이다. 데스크톱도 남은 기록이 데스크톱이 아니면 같은 이유로 실패한다). 데스크톱 설치 폴더에 헤드리스로 덮으면 GUI 실행 파일·바로가기와 installed-manifest·`installed-files.json`의 `gui` 기록을 지운다(`drop_parts_outside`). GUI 실행 파일을 지우지 못하면 기록을 그대로 두고 `profile_failed`로 실패한다(남은 GUI를 업데이터가 더는 바꾸지 않게 되기 때문이다). 창 인스톨러는 늘 `desktop`이다. `package-release.py`의 필수 검사는 구성과 무관하게 그대로다(데스크톱 설치에 필요하다). 이번 릴리즈에도 이전 릴리즈에도 없으면 `package-release.py`가 실패한다(`missing_required`). 설치기는 같은 파일을 빌드에 담아 읽고, manifest에 하나라도 없으면 기존 데몬을 끄기 전에 `release_incomplete`로 멈춘다(`installer/core/src/release.rs`의 `required_components`).
- `package-release.py`는 zip을 표준 형태로 다시 담는다: 경로 구분자를 `/`로 바꾸고, GUI zip 루트의 앱 exe를 `saba-chan-gui.exe`로 바꾸며(Tauri 빌드는 이미 `saba-chan-gui.exe`라 그대로다. `Saba-chan.exe` 개명은 옛 Electron zip에만 해당한다), 다른 컴포넌트의 exe는 뺀다(`package-release.py:147-184`). 다만 컴포넌트의 `bundles`에 적은 exe는 남기므로 raw saba-core zip에 든 `saba-runner.exe`가 재포장에서 빠지지 않는다(`:58-59, 166-169`). saba-core zip에는 `saba-runner.exe`와 공유 모듈(`i18n.py`, `daemon_rcon.py`)이 같이 들어간다(`package-release.py:48-60`).

## 4. Relay server (server-chan, 비공개 저장소)

> server-chan `main` 기준(2026-10-18). 프레임워크는 **Fastify 5**, DB는 PostgreSQL + drizzle이고, 기동할 때 `./drizzle`(0000–0023)을 자동 migrate한다(`src/index.ts`). 앱 조립은 `src/app.ts` `buildApp`, 디스코드 봇은 같은 프로세스의 `src/bot/`, 챗봇은 `src/chatbot/`이다. **단일 인스턴스 전제**다: poll·result 대기열, ack를 보낸 호스트 목록(`services/redelivery.ts`), 노드 토큰 검증 캐시, 레이트리밋 카운터, 봇 캐시(prefix·잠자기·언어), 음악·공지·챗봇 진행 상태는 프로세스 메모리에 있고 재시작하면 DB에서 다시 채우거나 사라진다(`src/index.ts` 머리 주석).

### 4.1 전역 동작

- 클라이언트 게이트(`app.ts` `clientGate`): 클라이언트(`X-Saba-Client: 1`, 맞는 `x-internal-secret`, 맞는 `x-admin-key`)가 아닌 접속은 Oops 페이지다. 보안 장치가 아니라 안내용이다. 브라우저도 쓰는 `/admin*`, `/api/bot-invite`, `/remote/ws`, `/v1/updates/download/installer`, 컨테이너 프로브용 `/health`, 원격 MCP(`/mcp`, `/oauth/*`, `/.well-known/oauth-*`, §4.4 (l))는 통과한다. 원격 MCP 경로는 Oops 변환도 하지 않고(OAuth·MCP 오류 형식 그대로) CORS는 모든 출처에 연다(쿠키 없이 Bearer만 쓴다).
- 잘못된 요청은 모두 Oops 페이지(`app.ts` `oopsOnError`, 사용자 결정 2026-10-26): 클라이언트가 아닌 요청이 4xx·5xx로 끝나면 권한 없음·틀린 링크·한도 초과·값 오류 모두 없는 주소와 똑같은 404 HTML(웹사이트 `not-found.html`과 같은 그림·문구, 10개 언어)로 바꾸고 경로마다 다른 레이트리밋 헤더도 지운다. 사바쨩 웹(`/remote/`)과 컨테이너 프로브용 `/health`는 바꾸지 않는다. 클라이언트는 지금처럼 JSON 오류를 받는다. nginx도 `/health`는 404, 직접 거절한 405·429와 `X-Saba-Client` 없이 들어온 클라이언트 전용 경로(데몬 경로·`/node/ws`·`/node/tunnel`·`/v1/updates/`·`/api/`)는 404 `not-found.html`로 준다(차단 페이지는 없다).
- CORS는 `app://`, `tauri://`, 웹사이트 origin, dev 모드의 localhost, `CORS_ORIGINS`만 허용한다.
- 레이트리밋은 전역 100/min이고 라우트별 값은 `middleware/rateLimit.ts` `ROUTE_RATE_LIMITS`에 있다. 노드 경로(`/poll`, `/heartbeat`, `/events`, `/ack`, `/result/:id`)는 한 번 검증된 토큰이면 노드 단위로, 아니면 IP로 센다.
- 프로덕션 필수 env: `RELAY_INTERNAL_SECRET`, `RELEASE_REGISTER_SECRET`, `ADMIN_PAGE_KEY`, `DISCORD_TOKEN`, `DATABASE_URL`, `SELF_URL`, `RELEASE_SIGNING_KEYS`(릴리즈 manifest 서명 공개키 `keyId:base64,…`. 운영 compose 기본값은 업데이터 `TRUSTED_KEYS`와 같은 `saba-updater-v1` 키). 없거나, 이 값들이나 `MUSIC_API_KEY`에 예시 자리표시 `CHANGE_ME`가 남았거나, `RELEASE_SIGNING_KEYS`에서 공개키를 하나도 읽지 못하거나, `RELEASE_REGISTER_SECRET`이 `RELAY_INTERNAL_SECRET`과 같으면 기동하지 않는다.
- 프로덕션의 5xx 응답은 내부 메시지 없이 `INTERNAL_SERVER_ERROR`만 돌려준다.
- **인증 5종**
  - 노드 토큰 `authenticateNode`(`middleware/auth.ts`): `Authorization: Bearer sbn_<hostId>.<secret>`를 DB `hosts.token_hash`로 검증하고 5분 캐시한다. 비밀이 무작위 48자라 해시는 `sha256:<hex>`이고 `timingSafeEqual`로 비교한다(`services/nodeToken.ts`). 0.1.10까지 저장한 argon2id(PHC 문자열) 해시도 `node:crypto` argon2(Node 24.7+)로 맞고, 맞으면 그 행을 SHA-256 해시로 바꿔 저장한다(그사이 해시가 바뀌었으면 두지 않는다). 틀린 토큰은 60초 기억해 같은 토큰을 다시 검증하지 않는다(그 호스트의 토큰을 새로 발급하면 지운다). 예전 argon2 검증은 프로세스 전체에서 동시에 4개까지 돌고 256개까지 기다리며, 줄이 차면 503 `SERVICE_BUSY`(`retry-after: 5`)다. `req.node = {id: hostId, generation}`(`generation`은 그 호스트의 토큰을 바꾼 횟수, 메모리 기록). 검증하는 사이에 토큰이 바뀌었으면 DB를 한 번 다시 읽고 예전 결과는 캐시하지 않는다. 본문이 큰 `/heartbeat`·`/result/:id`는 레이트리밋 뒤, 본문을 읽기 전(`preParsing`)에 토큰을 보고, 본문을 받는 사이 재페어링으로 토큰이 바뀌었으면 401 `TOKEN_REPLACED`로 거절한다(`rejectReplacedToken`). 실패는 401 `MISSING_TOKEN`·`INVALID_TOKEN_FORMAT`·`NODE_NOT_FOUND`·`INVALID_TOKEN`이고, 같은 계정의 재페어링으로 토큰이 바뀐 지 7일 안이면 `INVALID_TOKEN` 대신 `TOKEN_REPLACED`다(메모리 기록이라 relay를 다시 켜면 `INVALID_TOKEN`으로 돌아간다). 데몬은 heartbeat나 poll에서 `TOKEN_REPLACED`를 받으면 에이전트를 멈추고 상태에 `lastErrorCode: "token_replaced"`를 남긴다(`relay_agent.rs`, CLI `bot status`가 현지화해 보인다). 요청마다 디스크의 토큰으로 서명하고 이 PC에서 다시 페어링하면 새 토큰 저장이 에이전트를 다시 띄우므로, 같은 PC의 재페어링은 따로 다루지 않는다. 토큰이 맞아도 그 호스트 주인이 릴레이 차단 목록(§4.4 (g))에 있으면 403 `HOST_BLOCKED`이고(토큰을 확인한 뒤에 가린다), 데몬은 다른 연결 오류처럼 기록하고 재시도한다. 다른 401은 기록하고 재시도한다. 데몬이 함께 보내는 `x-request-timestamp`·`x-request-nonce`·`x-request-signature`는 받아들이되 검증하지 않는다(키가 같은 요청의 토큰이라 TLS 위에서 더하는 보호가 없다).
  - 내부 시크릿 `verifyInternal`(`middleware/internalAuth.ts`): `x-internal-secret`을 `RELAY_INTERNAL_SECRET`과 상수시간 비교한다. 봇 상태 조회(`/bot-status`)·운영 점검용.
  - 릴리즈 등록 `verifyReleaseRegister`(`middleware/internalAuth.ts`): `x-internal-secret`을 `RELEASE_REGISTER_SECRET`과 상수시간 비교한다. `/admin/releases` 전용이고, 릴리즈 CI(`release.yml`, GitHub secret 이름은 `RELAY_INTERNAL_SECRET`)가 이 값을 보낸다.
  - 노드 API `authenticateNodeApi`: 노드 토큰만 받는다(내부 시크릿은 받지 않는다). 자기 호스트(`isForeignHost`)와 그 호스트의 길드만 다룬다. 길드 경로(`routes/node.ts` `loadAuthorizedNode`, `chatbot/routes.ts` `authorizedGuild`)는 노드 주인이 길드를 떠났으면(디스코드가 Unknown Member로 답할 때만) 연결을 풀고 404 `NODE_NOT_FOUND`로 답한다. 봇도 게이트웨이 `GUILD_MEMBER_REMOVE`(캐시에 없던 멤버 포함)에서 떠난 사람의 PC가 그 길드에 있으면(대표든 붙은 것이든) 뺀다(`services/nodeOwner.ts`, `/사바쨩 연결해제`와 같은 `unbindGuild`. 대표였으면 다음 PC가 대표가 된다). 떠난 사람의 PC가 길드 멤버의 명령·멤버 목록을 계속 받지 않게 하려는 것이다. 길드에 붙은 PC(§4.4 (i))는 `GET /api/nodes/:g/discord-members`·`settings`·`channels`를 읽을 수만 있고, 쓰기(`PATCH settings`, `PUT channels`)와 `members`는 대표 PC만 한다.
  - 관리자 키 `verifyAdmin`: `x-admin-key`를 `ADMIN_PAGE_KEY`와 비교한다. 키가 비어 있으면 항상 거부한다.
- 토큰 형식: `sbn_{hostId}.{nanoid(48)}`(`services/nodeToken.ts`). 코드에서 "node"와 "host"가 같은 대상을 가리키는 곳이 남아 있다(`req.node.id`는 hostId다).
- zod 스키마는 `middleware/schemas.ts` 한 곳에 있다.

### 4.4 프로토콜 흐름

**(a) 페어링** (GUI → daemon proxy → relay → Discord 슬래시)
1. GUI `relay:initiatePairing` → daemon `POST /api/relay/pair/initiate` (`src/ipc/handlers/relay.rs`) → relay `POST /api/pair/initiate`. 응답은 `{code, pollSecret}`이다. 데몬은 https 릴레이(모의 릴레이는 루프백 http)와만 페어링한다. 아니면 relay에 보내지 않고 400 `invalid_relay_url`이다(`pairing_relay_url`, 상태 폴링도 같다).
2. 사용자가 Discord에서 `/사바쨩 연결 코드:<code>`를 실행한다 → relay 봇이 같은 프로세스에서 `claimPairingCode`를 부른다(`bot/commands/coreService.ts`, `services/pairing.ts`). users upsert, hosts 생성 또는 토큰 재발급(계정 하나에 PC 여러 대. 다시 연결할 PC는 확인 버튼에서 고른 내 PC(`replaceHostId`, 내 것이 아니면 아무것도 쓰지 않고 `HOST_NOT_FOUND`) → 코드의 `replace_host_id`(내 것일 때만) 순이고, 없으면 새 PC를 만든다. 확인 메시지는 이 계정에 PC가 있으면 "새 PC로 연결"과 최근 PC 3개의 "다시 연결" 버튼을 함께 보인다. 코드를 받은 PC가 지금 토큰을 보냈으면 고를 것이 없다. 다시 연결하면 그 PC의 예전 토큰은 `TOKEN_REPLACED`, 새 PC면 이 계정의 PC 수를 답에 붙인다. 차단된 사람이 새로 연결한 PC도 막는다(`blocklist.ts` `noteHostOwner`)), guild가 있으면 nodes 자동 생성, 이미 다른 PC가 대표인 길드면(내 다른 PC든 남의 PC든) 빼앗지 않고 이 PC를 붙인다(`guild_hosts`, 결과 `nodeAttached`, §4.4 (i). 코드 없는 연결의 수락도 같다). `pairing_codes.node_token`에 저장(수령 기한이 지나면 지운다). `/사바쨩 연결해제`는 누가 치느냐로 나뉜다(`unbindGuild`, 잠근 노드 행으로 다시 본다): 디스코드 서버 주인은 길드 전체를 풀어 노드와 그 길드의 대기 명령을 지운다. 대표 PC 주인은 자기 PC들을 빼고 남은 PC 중 가장 먼저 붙은 PC가 대표가 된다(옛 대표의 권한 캐시는 지우고 새 대표의 heartbeat가 다시 채운다. 남은 PC가 없으면 전체를 푼다). 붙은 PC 주인은 자기 PC만 뗀다. 그 밖의 사람은 `unpair_not_allowed`. 권한·배정·챗봇 설정은 cascade로 지워지고, 길드 슬래시 명령은 연결 전 자리의 `/사바쨩`(연결·도움말)만으로 다시 등록된다(`unbindGuild`, (e)). 데몬의 `nodeSettings`는 남는다.
   - 코드 없이 `/사바쨩 연결`(서버 관리 권한, 길드에서만)을 치면 친 사람의 켜진 PC(3분 안 heartbeat)에 수락을 묻는다(J1-b). PC가 없으면 코드 안내, 이 PC가 이미 그 길드에 있으면(대표든 붙은 것이든) 그렇다고 답하고, 다른 PC가 대표인 길드면 수락할 때 붙인다. 요청(`requestId`, 10분)은 relay 메모리에 두고(재시작하면 사라진다, `services/linkRequests.ts`) 그 호스트 큐에 `{action:'link_request', requestId, guildId, guildName, userName, expiresAt}`을 넣는다(노드가 아직 없어 큐 항목 `guildId`는 비우고 payload에 싣는다). 데몬은 이것을 `relay.link_request` 이벤트로 GUI에 보이고, 답은 `POST /api/link-requests/:id`다. 수락하면 페어링과 같이 길드를 묶거나 붙이고(토큰은 새로 만들지 않는다, 감사 `link_accept`, `pairing.ts` `linkGuildToHost`) 요청한 채널에 짧게 알린다.

**(b) 명령 실행** (cloud 모드)
1. Discord 사용자가 `<prefix> <text>`를 입력한다. 봇은 데몬에 보내기 전에 받았다는 답(`cmd_working`, ⏳)을 먼저 달고, 결과가 오면 그 메시지를 결과로 고친다(새 답을 따로 달지 않는다. 고치지 못하면 새 답으로. 해석기가 스스로 답했으면 받았다는 답을 지운다, `serverCommands.ts` `workingNote`). 원격 액션이 실패하면 데몬이 요청 언어의 짧은 이유 `reason`(봇 locales `reasons.<code>`)을 함께 주고, 릴레이는 영어 원문 대신 그것을 보인다(실행 결과의 `reason`, 거절(`ActionError`)은 문구가 있는 코드만). 접두사는 길드별 캐시(heartbeat `botConfig.prefixes`, 옛 데몬은 `prefix`)이고, 비어 있으면(옛 `"!saba"`도) 응답 언어의 기본값(ko `사바쨩`, ja `サバちゃん`, 그 밖 `Saba-chan`)이다(`bot/state/nodeState.ts`). 챗봇 채널에서는 접두사 뒤가 서버 명령이나 데몬 최상위 명령(help·list 등)이 아니면 챗봇이 받는다. 길드 슬래시 명령(`/<서버> <명령>`)과 챗봇 `run_command`도 같은 경로로 간다.
2. `dispatchCommand`·`sendToDaemon`(`bot/commands/dispatch.ts`)이 requestId를 먼저 만들고 `resultWaiters.wait(id, 55s)`를 등록한 뒤(실행 중인 명령은 더 기다린다, 아래 3) `submitCommand`(`services/commandSubmission.ts`)로 큐에 넣는다. 문장 명령의 payload는 `{action:'plan', text, via:'direct'|'chatbot', voiceChannelId?, confirmedBy?, userName?, guildName?, locale?}`이고(`locale`은 답 문구를 쓸 디스코드 길드 언어, 없으면 데몬 GUI 언어), 큐 항목에는 노드 주인 `ownerDiscordId`도 실린다(P1). 길드 없이 온 원격 MCP 명령(`via:'mcp'`)에는 그 PC 주인 `hostOwnerDiscordId`를 싣는다(§4.4 (l), `routes/poll.ts`). 그 길드의 대표 PC로 가는 명령에는 봇이 아는 디스코드 서버 주인 `guildOwnerDiscordId`도 실린다(R2b, §4.4 (i)). 데몬은 처음 받은 주인을 고정하고, 다른 값은 무시한다(`relay_agent.rs` `requester`, `chat::permissions::pin_owner`). `ownerDiscordId`가 있는데 `via`가 없으면 챗봇으로 본다. 두 이름은 감사 로그에 남길 디스코드 표시 이름·서버 이름(한 줄, 100자까지)이고, 권한 판단에는 쓰지 않는다(권한은 `requestedBy`·`guildId` id로만). `guildId`로 nodes를 조회해 hostId를 찾고, 큐에 INSERT한 뒤 `pollWaiters.wake(hostId)`를 호출한다. 데몬이 문장을 해석해 `planId`를 주면 `run_plan`으로 실행한다(아래 3, `dispatch.ts` `dispatchCommand`·`runText`). 길드 없이 온 문장 명령은 보낼 PC가 없어 `MISSING_HOST_OR_GUILD`로 답한다. 문장 계획을 모르는 0.1.10 이하 데몬은 `MIN_AGENT_VERSION`(0.1.11)이 연결부터 막는다. 여러 PC 길드는 첫 낱말의 서버가 있는 PC로 보낸다(`guildRouting.ts` `routeToHost`).
3. daemon의 relay agent(`src/relay_agent.rs` `poll_loop`)가 `GET /poll`을 계속 돌리고 있다. 서버는 즉시 가장 오래된 pending 1건을 꺼내 `delivered`로 표시하고 반환한다(`poll.ts` `CLAIM_PER_POLL`). 데몬은 빈 실행 자리가 있을 때만 poll 하고 받은 명령을 시작하며 ack하므로, 한 번에 여러 건을 주면 자리가 모자란 명령이 ack 없이 데몬에 묶여 다시 보내기·시간 초과와 엇갈린다. 없으면 **25초 대기**(`poll.ts:6`, `pollWaiters.wait`) 후 다시 조회하고, 그래도 없으면 204를 준다. 클라이언트 연결이 끊기면 abort한다. 꺼낸 뒤 연결이 끊겼거나 응답을 끝까지 쓰지 못하면 그 명령을 `pending`으로 되돌린다(봇이 이미 시간 초과로 알린 명령(`timeout_notified`)은 되돌리지 않는다). 응답을 다 쓴 뒤 데몬이 받지 못한 경우는 ack로 살린다: `POST /ack`를 한 번이라도 보냈거나 heartbeat의 `agentVersion`이 0.1.7 이상인(id로 중복을 거르는) 호스트에서, 전달된 뒤 15초 동안 ack도 결과도 없는 명령을 5초마다 훑어 `pending`으로 되돌리고 그 호스트의 poll을 깨운다. 한 명령은 2번까지 다시 보내고, 만료(60초)가 지나면 보내지 않는다(`services/redelivery.ts`, `routes/ack.ts`). 이 호스트 목록은 메모리에만 있어 릴레이를 다시 켜면 다음 heartbeat·ack 때 다시 켜진다. 재페어링하거나 heartbeat의 `agentVersion`이 0.1.7 미만이면 그 호스트를 목록에서 뺀다(재페어링은 hostId를 그대로 쓴다). 그 뒤 0.1.7 이상의 heartbeat나 ack가 다시 켠다. ack를 보내지 않는 예전 데몬에는 다시 보내지 않는다(id로 중복을 거르지 않아 두 번 실행될 수 있다). 봇은 결과를 55초 기다린다. 그때 아직 `pending`인 명령은 `timeout`으로 내려 늦게 전달되지 않게 하고 시간 초과로 답한다. 이미 전달된 명령은 다시 보내지 않는다. 그중 데몬이 실행을 시작했다고 알린(`acked`) 명령은 첫 서버 시작처럼 1분을 넘길 수 있어, 처음부터 10분까지 결과를 더 기다린다(디스코드 상호작용 토큰 15분 안). 한 상호작용에서 plan과 run_plan을 이어 보내는 슬래시·버튼 경로(`actionCommands.ts` `runCommandAction`, 확인 버튼)는 상호작용 시각 + 14분을 `deadline`으로 넘긴다. 연장 대기만 그 시각에서 멈추고 첫 55초는 그대로라, 최악이어도 상호작용 시각 + 14분 55초 안에 답한다. 더 기다리는 동안 15초마다 그 PC와의 연결을 보고, 호스트가 offline이거나 heartbeat가 3분 넘게 없거나 데몬 poll과 heartbeat가 함께 150초 넘게 없으면(heartbeat 한 번 실패는 끊김으로 보지 않는다)(실행 자리가 차면 poll만 멈추므로 poll 공백만으로는 판단하지 않는다. poll 시각은 릴레이 메모리에 있어, 다시 켠 뒤 poll을 아직 못 봤으면 이 기준은 건너뛴다) 기다림을 멈추고 연결이 끊겼다고 답한다(`HOST_LOST`, `cmd_host_lost`). 대기가 끝나는 순간 큐에 저장된 결과가 있으면 그 결과로 답한다(큐에 `oversized`로만 남은 큰 결과는 릴레이 메모리의 결과 버퍼에서 꺼낸다). 결과 없이 10분이나 `deadline`에 닿으면 연결을 한 번 더 보고, 살아 있으면 시간 초과가 아니라 아직 실행 중이니 잠시 뒤 확인하라고 답한다(`STILL_RUNNING`, `cmd_still_running`). 데몬이 받지 않은 명령만 시간 초과(`TIMEOUT`)다(`dispatch.ts` `sendToDaemon`). 같은 계정의 재페어링으로 토큰이 바뀌면(`hostReplaced`) 기다리던 poll을 깨워 401 `TOKEN_REPLACED`로 끝내고, 예전 토큰으로는 명령을 꺼내지 않는다. 잠자기는 길드 단위이고 릴레이가 그 길드의 명령을 받지 않는 것으로 처리한다(데몬 폴링은 멈추지 않는다). agent는 받은 명령을 4건까지 동시에 실행하고, 빈자리가 있는 동안에는 다음 poll을 계속 보낸다(`relay_agent.rs` `COMMANDS_IN_FLIGHT`). 4건이 모두 차거나 받아 두고 시작하지 못한 명령이 남아 있으면 poll을 보내지 않는다(heartbeat는 계속 보낸다). 그래서 오래 걸리는 명령 하나가 뒤 명령의 답을 막지 않고, 결과는 끝난 순서대로 `POST /result/:id`로 간다. 결과 전송이 연결 오류·5xx·408·429로 실패하면 1·2·4·8·16초 간격으로 다섯 번까지 다시 보내고(그동안 그 실행 자리를 쥔다), 그 밖의 4xx(릴레이가 그 명령을 모름, 너무 큼)는 다시 보내지 않는다(`relay_agent.rs` `post_result`, `RESULT_RETRIES`). 4건이 차면 새 명령은 빈자리가 날 때까지 기다린다. agent는 명령을 실행하기 시작할 때 그 id들로 `POST /ack {ids}`(50개씩)를 보내고, 릴레이가 404면(예전 릴레이) 그 세션에서는 보내지 않는다. 받은 명령 id는 대기·실행 중이면 끝날 때까지, 끝난 명령이면 끝난 뒤 10분 동안 1,000개까지 기억해서(시간·개수로는 끝난 명령만 잊는다), 같은 id가 다시 오면 실행하지 않는다: 아직 처리 중(대기 포함)이면 그대로 두고, 끝난 명령이면 기억해 둔 결과를 `/result/:id`로 다시 보낸다. 실행 중인 명령이 다시 오면(ack가 닿지 않았다) ack를 다시 보내고, 대기 중인 명령은 시작할 때 보낸다(`relay_agent.rs` `SeenCommands`, `post_ack`). 기억은 에이전트 메모리에 있어 다시 연결해도 이어지고(데몬을 다시 켜면 사라진다), 세션이 끝나면 받아 두고 시작하지 않은(ack하지 않은) 명령은 바로 잊어서 릴레이가 다음 연결로 다시 보내면 실행한다. 이미 시작한 명령은 세션이 끝나도 끝까지 실행하고 결과를 보낸다.
4. agent는 받은 명령을 action별로 처리한다(`relay_agent.rs` `handle_payload`). 0.1.11까지 있던 `raw_command`(문장을 바로 실행)는 0.1.12에서 없어졌고, 문장 명령은 아래 문장 계획으로만 온다. 문장 해석 규칙은 이렇다. 접두사·별명·길드별 설정은 daemon의 bot config에서 읽는다(`chat/api.rs`). 답 문구는 payload `locale`, 없으면 GUI 언어로 쓴다. 입력을 알아보지 못했으면(인스턴스를 못 찾음, 정의에 없는 명령, 모르는 낱말) 계획 없이 `{success:false, code:"INSTANCE_NOT_FOUND"|"UNKNOWN_COMMAND", text:<현지화 문구>, args:{name?, command?, help?}}`를 주고(정의에 없는 명령이면 `help`에 그 모듈의 명령 안내를 담아 릴레이가 덧붙인다), 릴레이는 이 코드를 보고 모델 해석기에 정확한 명령을 한 번 묻는다(`chat::Reply`). 모듈 이름만 쓰면 실패가 아니라 명령 안내다. 권한이 모자라면 `code:"PERMISSION_DENIED"`, `args:{need, level, via?}`다. 챗봇 경로(`via:'chatbot'`)에서 모듈이 `risk="danger"`로 선언한 명령(모르는 risk 값도 danger로 본다, `commands::risk_of`)을 물을지는 다른 명령처럼 문장 계획의 `needsConfirm`이 정한다(그 길드의 챗봇 `confirmLevel`, `none`이면 위험도 묻지 않는다, 사용자 결정 2026-10-28). 릴레이는 챗봇이 올린 확인 버튼을 요청자(`requestedBy`)가 눌렀을 때만 payload에 `confirmedBy:<누른 사람 Discord id>`를 싣고 같은 문장을 다시 보낸다. 데몬은 `confirmedBy`가 `requestedBy`와 같으면(`Requester::confirmed_by_requester`) 묻지 않는 계획을 만들고, 레벨·`chatbotCap` 판정은 그대로 한다. 확인이 필요한 계획을 확인 없이 `run_plan`하면 409 `confirm_required`다. 액션 경로(`server.command:*`)는 danger 명령도 챗봇 표면에 열려 있고 늘 확인 계획(`needsConfirm`)을 거친다(사용자 결정 2026-10-20). 권한·비밀값·`update.apply` 같은 챗봇 금지 액션은 그대로다. 챗봇 경로의 답은 로컬 정보를 뺀 뒤 IP와 비밀처럼 보이는 값도 가린다(`actions::mask_console`, `relay_agent.rs` `chat_json`). 액션 경로도 콘솔·모듈 조회·모듈 명령(`server.command:*`)의 결과를 챗봇에 같이 가린다(`actions::chatbot_masked`). 시작이 모듈 약관 동의를 기다리면 `code:"AGREEMENT_REQUIRED"`, `args:{agreements:[{id, label, url, accepted}]}`다(동의는 PC에서만 받는다, `chat::start`). 모르는 action(`raw_command` 포함)은 `{success:false, data:{error:"Unknown action: <action>"}}`다.
   - `{action:'plan'|'run_plan'|'query', id, input?, instance?, planId?, locale?, via, userName?, guildName?}` (P2·P3, `relay_agent.rs` `action_request`): 액션 카탈로그. `plan`에 `steps:[{id, instance?, input}]`가 있으면 여러 단계 계획(I1, 01 `POST /api/actions/plan`)이고 `run_plan`은 같다. `plan`에 `text`가 있으면 문장 계획이다(`actions::plan_text`): 채팅 처리기(`chat::interpret`)가 위 규칙(접두사·서버 낱말·별명·권한·danger는 서버 이름으로)으로 해석만 하고, 실행할 명령이면 `{planId, actionId(`server.start`·`server.stop`·`server.status`·`server.players`·`server.command:<이름>`), instance, risk, needsConfirm, summary:[]}`(`needsConfirm`은 액션 계획과 같은 `needs_confirm`, 요청자가 확인 버튼으로 다시 보낸 문장은 false), 실행할 것이 없으면(도움말·목록·모듈 안내·모르는 명령·거절) 계획 없이 `{success, text, code?, args?}`(`code`·`args`는 위와 같다)를 준다. 그 `run_plan` 결과는 `{success, actionId, instance, text, code?, args?, already_running?}`이고 `text`는 채팅 처리기의 답이다(`chat::execute`). `run_plan`은 문장을 다시 해석해 그때의 권한·서버 상태로 판정한다(거절이면 그 답, 다른 명령·서버를 가리키게 됐으면 404 `plan_expired`). 한 액션 계획과 문장 계획에 `autoRun:{except?:[액션 id]}`를 실으면(0.1.12~) 확인이 필요 없고(`needsConfirm:false`) `except`에 없는 액션은 데몬이 계획에 이어 실행하고 `run_plan`의 답(실패도)에 `autoRun:true`와 계획의 `planId`·`actionId`·`instance`를 붙여 준다. 확인이 필요하거나 실행할 것이 없으면 계획을 그대로 준다(`relay_agent.rs` `auto_run`). relay는 문장 명령(`dispatch.ts` `runText`)에 `except`로 켜고 끄는 액션(`server.start`·`server.restart`·`server.stop`)을 싣는다. 그 실행은 보내기 전에 "다 켜졌어요"·"다 꺼졌어요" 기다림을 걸어야 하기 때문이다. 그래서 그 밖의 문장 명령은 큐를 한 번만 왕복한다. `autoRun`을 모르는 데몬은 계획만 주고 relay는 지금처럼 `run_plan`을 보낸다. `success`는 명령이 해낸 것인지이며(정지 실패·모듈 실패 모양이면 false, 그래도 `text`가 답이다), 시작했는데 이미 켜져 있었으면 `already_running:true`와 그 문구(`server.already_running`)다. 챗봇 경로면 위처럼 IP·비밀처럼 보이는 값을 가린다. 그 실행 결과가 `running:true`이면 끝은 이벤트 `plan.done`(`runId`)으로 온다. 원격 설정 변경의 실행 결과에는 되돌리기 `undoPlanId`가 있고 `run_plan`으로 보낸다. 관리 실행 횟수를 넘으면 `rate_limited {args:{perHour, retryInSecs}}`. 판정·검증은 데몬이 한다(`crate::actions`). `via:'chatbot'`이면 액션 선언의 `surfaces`에 chatbot이 없을 때 레벨과 상관없이 `action_not_allowed`다. 확인이 필요한 액션(danger·관리)은 `plan` → `run_plan`만 받고, 바로 부르면 `confirm_required`다. `planId`는 만든 `guildId`·`requestedBy`에 묶여 10분 살고(`plan_not_yours`·`plan_expired`), 챗봇이 만든 계획은 확인한 사람이 보내도 챗봇 상한으로 판정한다. 챗봇이 만든 계획 중 확인이 필요한 것(`needsConfirm:true`, 챗봇 계획의 되돌리기 포함)은 요청자 본인이 버튼을 눌러 보낸 `run_plan`만 실행한다: relay는 확인·되돌리기 버튼으로 보내는 `run_plan`에 `confirmedBy:<누른 사람 Discord id>`를 싣고, 데몬은 그 값이 `requestedBy`와 같을 때만 통과시킨다. 없거나 다르면 409 `confirm_required`이고 계획은 쓰지 않고 남긴다(`actions::take_plan`, D-A1). `query`는 `kind=query` 액션(모듈 조회 `server.query:<이름>` 포함)만 받는다(`not_a_query`). 원격 요청에는 세 가지를 더 지킨다: 결과에서 비밀값(`*_password`·`*_token`·`*_secret`, 모듈 password 형식 필드)을 어느 깊이에서든 지운다. 결과의 PC 로컬 정보도 어느 깊이에서든 뺀다(I3, 알림 push와 같은 기준, `actions::strip_local_details`): `working_dir`·`executable_path`·`extra_args`·`extension_data`·`install_path` 키, 종료 근거 `evidence` 중 종료 코드·신호·메모리 상한이 아닌 것(콘솔 줄·크래시 파일 경로), `note_args.reason`(자동 재시작 실패 원문). 문자열 안의 절대 경로는 `<path>`로 바꾸고(따옴표로 싼 경로는 닫는 따옴표까지, 아니면 공백이 있을 수 있어 그 줄 끝까지), Python traceback은 마지막 줄만 남긴다. 파일로 첨부되는 결과(`fileName`이 있는 객체, 로그 내보내기 `server.logs.export`)의 `content`는 줄마다 경로만 가린다(traceback을 줄이지 않는다). 챗봇에 가는 로그 읽기·내보내기(`server.logs.read`·`server.logs.export`)는 콘솔과 같이 IP·비밀처럼 보이는 값도 가린다(`mask_console`). GET 액션의 입력(경로 칸이 아닌 것)은 밑 라우트의 쿼리로 간다(로그 `source`·`lines`·`before`·`since`·`until`). `instance.settings.set`·`instance.create` 입력은 비밀값과 실행 관련 키(`executable_path`·`working_dir`·`instance_dir`·`extra_args`·`extension_data`·`rest_host`·`memory_limit_mb`·`java_path`(모듈이 어떤 형식으로 선언하든), 모듈의 file 형식·path 형식 필드, 형식·정규식 없이 실행 인자가 되는 text 필드)를 어느 깊이에서든 `invalid_input`으로 거부한다. 길드에 `allowedInstances`가 있으면 그 밖의 인스턴스는 `NODE_NOT_ALLOWED`(`args.instance`)이고, 결과의 `servers`·`instances` 목록(어느 깊이든, 원소의 `id`. `instance.list`·`monitor.summary` 등)도 그 목록으로 거른다. 원격 실행 결과가 성공이면 데몬은 응답 최상위 `text`에 요청 `locale`의 사람용 요약(머리 줄 + 항목 10줄까지 + 남은 개수)을 싣는다: `instance.list`·`backup.list`(새것부터, 종류·시각·크기)·`instance.events`(새것부터)·`update.check`(업데이트가 있는 구성요소, 확인 실패면 없음)·`monitor.summary`(CPU·메모리, 실행 중 서버별), 모듈 조회 `server.query:*`(채팅 명령 결과와 같은 범용 포맷 `chat::format::format_response`). 시각은 PC 시간대다(모르면 `?`). 그 밖의 액션은 `text`가 없다(`actions/summary.rs`, 문구는 봇 locales `actions.summary.*`). 성공은 `{success, data:<plan·run 응답>}`(응답에 `text`(선택, 요청 `locale`로 쓴 사람용 요약)가 있으면 relay는 결과 JSON 대신 그 문구를 보인다, `actionResult.ts` `resultText`), 실패는 `{success:false, data:{code, error, args?, field?, reason?}}`. 문구는 `locale`로 만든다. 약관 동의 계약(데몬 쪽은 구현 중)에서 동의가 필요하면 `code:"agreement_required"`와 `data.agreements:[{id,label,url}]`(또는 `args.agreements`)를 싣기로 했다. relay는 동의를 대신 보내지 않고 "PC의 사바쨩에서 <이름>에 동의해야 켤 수 있어요"와 https 원문 링크를 보인다(문장 명령 결과도 같다, `dispatch.ts` `agreementText`). `run_plan`이 밑 라우트의 409를 `data.result.error_code`로 감싸 와도 같다(`actions.ts`).
   - 원격 MCP(`via:'mcp'`, §4.4 (l), `relay_agent.rs` `mcp_caller`): 같은 `plan`·`run_plan`·`query`와 액션 목록 `catalog {instance?}`를 받는다. 길드가 없고 `requestedBy`가 큐 항목의 `hostOwnerDiscordId`와 같을 때만 받고, 아니면 403 `PERMISSION_DENIED`다(`catalog`는 MCP로만 받는다). 요청자는 앱과 같은 표면(gui)의 주인 레벨이고(`actions::Caller::mcp`, 감사 출처 `mcp`), `catalog`는 앱 표면의 `GET /api/actions` 본문과 같다. 웹 원격·짝 맺은 PC처럼 PC에서만 하는 일(`gate::pc_only`, 403 `remote_local_only`)과 PC 전용 칸(403 `remote_field_blocked`)은 계획 때 막고, 실행 관련 설정 키는 다른 원격 요청과 같이 `invalid_input`이다. 되묻기는 앱과 같은 고정 규칙이고(`needs_confirm`), 확인이 필요한 계획은 `confirmedBy`가 요청자 본인일 때만 돈다. 길드를 받는 액션(챗봇·디스코드 설정, 켜짐 알림)은 길드가 없어 `invalid_input {field:'guild'}`다.
   - relay 쪽 결과 처리(P2 후속 계약, `bot/commands/actionResult.ts`): 여러 단계 계획 `{action:'plan', steps:[{id, instance?, input}]}`(1~8단계, `instance:"@N"`은 N번째 단계가 만들 서버)의 결과는 단계마다 ✅·❌(코드 문구)·⏭️ 한 줄로 보인다. `running:true`면 ⏳ 메시지를 보내고 `runId` → 그 메시지를 메모리에 계획이 가장 오래 걸릴 시간(8단계 × 관리형 정지 한 단계 상한 약 3725초(06 §6) + 1시간, 약 9시간) 동안 들고 있다가 `plan.done` 이벤트가 오면 고친다. 들고 있지 않으면(재시작) 그 길드 알림 채널에 되돌리기 없이 보내고, 이 호스트에 묶인 길드가 아니면 버린다(들고 있던 기억도 지우지 않는다, server-chan #142). 결과에 `undoPlanId`(한 액션) 또는 단계의 `undoPlanId`가 있으면 [되돌리기] 버튼을 붙이고, 요청한 사람만 누를 수 있으며 누르면 그 사람으로 `run_plan {planId: undoPlanId}`를 보내고 그 버튼 줄만 걷는다. 계획 요약의 `before`는 "이전 → 새 값"(`null`은 "없음")으로 보인다. `rate_limited`(`args.perHour`·`retryInSecs`)·`plan_running`·`provision_failed`·`provision_timeout`·`step_skipped`는 번역 문구가 있고, 틀린 단계의 `step`은 "N단계:"로 붙인다. 챗봇 도구 `plan_actions {steps:[{action, server, input}]}`(조회 단계는 받지 않는다)는 데몬 계획을 하나 만들고 늘 확인 버튼으로 돌린다(`chatbot/tools.ts`). 액션 결과가 `{fileName, bytes, truncated, content}`(로그 내보내기, 06 §3)이면 `content`를 파일로 첨부하고 모델에는 `{ok, fileName, bytes, truncated}`만 준다. 입력 칸에 `optionsFrom:{action, list, value, label?}`이 있으면(06 §1) 슬래시 옵션은 자동완성이고, 고를 때 그 조회 액션을 요청한 사람으로 불러 `result[list]` 항목의 `value`를 넣고 `label`을 보인다(25개, 3초 기한 안 2.5초, 사람·서버·칸별 30초 캐시, 진행 중인 조회는 함께 기다린다, `guildCommands.ts` `handleGuildAutocomplete`). 계획이 409 `server_running`이면(06 §1, 복원) [끄고 진행]·[취소]를 보이고, 요청한 사람이 누르면 `{steps:[server.stop, 원래 액션]}` 계획을 만들어 확인이 필요하면 다시 묻는다(`actionCommands.ts` `stopFirstMessage`). `server.players` 같은 액션 항목에 `modules:[…]`가 있으면 그 모듈의 서버에만 하위 명령을 만든다(`[]`면 어디에도, 없으면 모든 서버, `catalog.ts` `parseAction`).
   - `{action:'link_request', requestId, guildName?, userName?, expiresAt?}` (J1-b): 이미 페어링한 사람이 다른 길드에서 코드 없이 `/사바쨩 연결`을 쳤을 때 relay가 그 사람의 PC로 보낸다. 데몬은 이벤트 `relay.link_request`를 내서 GUI·CLI에 알리기만 하고 `{success:true, data:{notified:true}}`로 답한다(`requestId`·`guildId`가 없으면 `success:false`). 수락·거절은 PC에서 사람이 `POST /api/relay/link-requests/:id`로 한다(01 Relay 프록시 표).
   - `{action:'web_session'}` (사바쨩 웹): 주인이 받은 링크로 브라우저가 붙었는데 데몬이 `/node/ws`에 없다. 데몬은 `{success:true, data:{connecting:true}}`로 답하고 `<릴레이>/node/ws`에 노드 토큰으로 웹소켓을 연다. 웹소켓에서 주고받는 것과 데몬이 막는 범위는 01 §1.4.1.
   - `{action:'permission', op:'grant'|'revoke'|'default_level', discordId?, level?, via}`: 디스코드 `/사바쨩 권한` 명령. 고정된 주인이 직접(`via:'direct'`) 보낸 것만 받아 `nodeSettings`에 쓰고 `{success:true, data:{defaultLevel, members, chatbotCap, levels, commandLevels, ladder, permissionsAt}}`(heartbeat `permissions[guild]`와 같은 모양)를 돌려준다(`permissionsAt`은 저장을 마친 직후의 PC 시각 Unix ms). 아니면 `data.code` `NOT_OWNER`·`OWNER_FIXED`·`INVALID_LEVEL`·`UNKNOWN_OP`·`MISSING_GUILD`.
5. relay는 상태를 completed로 바꾸고 `resultWaiters.wake(id)`를 호출한다. bot은 `result.data.text`(최대 1950자)로 Discord에 reply한다.
6. agent의 재시도 백오프는 3초에서 시작해 최대 60초다(`relay_agent.rs:25-26`).
7. 알림 채널(I3): agent가 데몬 이벤트 버스 중 `instance.exit`(크래시·시작 실패·원인 모를 종료), `instance.started`·`instance.stopped`(켜고 끈 것과 시킨 쪽 `source`·`userName?`, 01 §`GET /api/events`), `backup.done`, `update.available`, `schedule.warn`, `plan.done`(뒤에서 마친 여러 단계 실행, 요청한 `guildId`가 있다), `instance.ready`(06 §4), `instance.update_notice`(01 §`GET /api/events`)를 `POST /events {events:[{id, type, data}]}`로 올린다(노드 서명, 20건씩). 경로·콘솔 줄·오류 원문은 데몬이 뺀다. relay가 404면 10분 쉬고 다시 알아본다. relay는 노드당 분당 60건까지 받고(넘으면 429, agent는 백오프 뒤 다시 보낸다), 잠든 길드에는 보내지 않는다. 배정 종류 `알림`과 길드별 전달은 relay가 한다. `instance.started`는 `unexpected:true`면 사바쨩 밖에서 켜졌다는 경고(`ev_started_external`, 늘 보낸다), 아니면 시킨 쪽을 붙인 한 줄(`ev_started`, 출처 이름은 `ev_source`, 모르는 출처는 그대로)이다. 이 줄은 그 길드가 그 서버의 켜짐 알림을 켰을 때만 보낸다(heartbeat `startNotice[guildId]`에 있을 때, 기본 꺼짐, 사용자 요청 2026-10-26). `instance.stopped`는 게임 안 정지(`ev_stopped_in_game`)나 시킨 쪽을 붙인 한 줄(`ev_stopped`)이다. 디스코드·말하는 사바쨩(`source` `discord`·`chatbot`)이 시킨 시작·정지는 시킨 채널에 결과가 이미 나가므로 알림 채널에 다시 보내지 않는다(`bot/notify.ts` `eventText`). 이 둘을 모르는 예전 relay는 버린다. 같은 경로의 `plan.done`은 알림이 아니라 그 실행의 결과 메시지를 고친다(위 relay 쪽 결과 처리). `instance.ready`도 알림 채널로 가지 않는다. 디스코드·말하는 사바쨩에서 시작·재시작을 시켜 성공한 채널(슬래시·호출어 문장·말하는 사바쨩의 모든 문장 명령은 `dispatchCommand`가 문장 계획 → `run_plan`으로 보내고 계획이 알려 준 `actionId`·`instance`로 기다리므로, 기다림은 이 액션 경로 한 곳뿐이다. 익스텐션 서버처럼 시작 성공과 함께 준비가 나가 결과보다 먼저 와도 응답 전 준비를 맡아 둔다, `server.start`·`server.restart` 단계가 든 계획의 `run_plan`. 여러 단계 실행이 끝났으면 단계 줄에서 시작을 마친(`status:"done"`, 새로 만든 서버 포함) 인스턴스마다, 단계 줄이 없거나 뒤에서 이어 실행 중(`running`)이면 계획의 기존 대상마다 기다리되, 결과가 실패이거나 `already_running:true`가 있으면 뺀다)을 인스턴스별로 15분 기억했다가, 그 채널에만 "다 켜졌어요" 또는 "켜지 못했어요 + 정해진 이유"(`code`만 문구로) 한 줄을 일반 알림과 같은 재시도로 보내고 기억을 지운다. 슬래시 명령·버튼처럼 시킨 답이 상호작용 답이면 새 메시지 대신 그 답에 그 줄을 덧붙이고(요청과 결과를 한 메시지로, `readyWatch.ts` `appendToReply`), 호출어 문장은 결과로 고친 받았다는 답(⏳)에, 말하는 사바쨩 확인 버튼 뒤의 실행은 그 결과 메시지에 붙인다(`resultLines`. 말하는 사바쨩이 바로 실행한 것은 모델 답과 따로 그 채널에 보낸다), 계획의 `run_plan`은 그 실행의 결과 메시지에 붙인다(`actionResult.ts` `resultLines`: 뒤에서 이어 실행 중이어도 `plan.done`이 결과로 고칠 때 붙은 줄을 남긴다, 확인 버튼 뒤의 결과도 그 메시지에). 서버 하나를 켜거나 끄는 계획이면 줄을 덧붙이지 않고 결과 문구("요청 완료")를 그 줄로 바꿔, 메시지 하나가 요청 완료에서 작업 끝으로 바뀐다(사용자 요청 2026-10-28, `actions.ts` `lineTo`). 여러 서버를 켜고 끄는 계획은 서버마다 덧붙인다. 확인 버튼(`actionCommands.ts` `handleActionButton`)을 누른 뒤의 결과(취소 포함)는 그 확인 메시지에 다른 버튼이 남지 않으면 새 답글 대신 그 메시지를 고쳐 쓰고, `[되돌리기]` 같은 다른 버튼이 남으면 새 메시지로 보낸다. 덧붙이지 못하면(상호작용 토큰 15분 만료, 2000자 초과 등) 그 채널에 새로 보낸다. 끄기도 같다: `server.stop` 단계가 든 계획의 `run_plan`(기본 명령 stop 포함)을 보내기 전에(정지가 응답보다 먼저 끝날 수 있다) 끄는 인스턴스마다 그 채널을 15분 기억하고(실패하면 거둔다. 한 액션 실행의 밑 라우트 실패도), `instance.stopped`가 오면 "다 꺼졌어요"(`ev_stop_done`)를 같은 방식으로 그 결과 메시지에 붙인다(`notify.ts` `sendStopped`). 알림 채널에는 여전히 보내지 않는다. 이벤트를 올린 호스트에 묶인 길드의 기억만 꺼내고 지운다(server-chan #142). 기억이 없으면(자동 재시작·PC 앱 시작) 보내지 않는다(`bot/state/readyWatch.ts`, `notify.ts` `sendReady`). `instance.update_notice`도 알림 채널로 가지 않고, 그 서버를 디스코드 상호작용(기본 명령 start, `server.start`·`server.restart` 단계가 든 계획의 `run_plan`)으로 켠 사람에게만 그 상호작용의 ephemeral followUp으로 보낸다(`ev_update_module`·`ev_update_server`). 켠 상호작용을 인스턴스별로 14분, 받은 안내를 2분 기억해 둘 중 나중에 온 쪽이 보내고(모듈 안내는 시작 답보다 먼저 올 수 있다), 같은 시작에 같은 종류는 한 번, 안내를 올린 PC의 길드에서 켠 것에만 보낸다. 시작 답을 쓰기 전에는 followUp 하지 않는다(미뤄 둔 답을 대신해 모두에게 보이게 된다). 메시지 명령·말하는 사바쨩으로 켠 것은 기억하지 않는다(`bot/state/startNotice.ts`).
   - 게임 채팅(0.1.12): 같은 `POST /events`로 `instance.chat {at, instanceId, instance, text}`도 올린다. `text`는 게임 채팅 전달을 켠 서버의 채팅을 데몬이 다 만든 한 줄이다(이름·본문의 디스코드 서식·멘션 문자는 데몬이 이스케이프, 02 §`[extensions.saba-core]` `chat_patterns`). relay는 알림 채널이 아니라 길드의 게임 채팅 채널(배정 종류 `게임 채팅`, `nodes.game_chat_channel_id`)로만 보내고(`bot/notify.ts` `sendChats`), 이 PC의 길드 중 그 채널을 배정했고 잠들지 않은 길드, 그 길드의 이 PC 서버(`instanceCheck`), `allowedInstances`에 목록이 있으면 그 서버만이다. 한 묶음의 줄은 줄바꿈으로 이어 2000자까지 한 메시지로 보내고(`packLines`, 넘는 한 줄은 자른다), 멘션은 하나도 울리지 않고(`allowedMentions: {parse: []}`) 링크 미리보기를 끈다(`SuppressEmbeds`). 같은 묶음의 다른 알림을 기다리게 하지 않는다. 디스코드에서 게임으로 보내는 역방향은 없다. 예전 relay는 모르는 종류로 버린다.

안내(`update_notice_host`)로 답한다(`coreService.ts` `update`). 입력 스키마 `properties.<필드>.title`(선택, 문자열 또는 `{<locale>:…}`)이 있으면 옵션 설명과 언어별 옵션 이름으로 쓴다)(`allowedInstances`는 `bot.node_settings[guild].allowedInstances` 목록이 있는 길드만, 없으면 제한 없음. `startNotice`는 `bot.node_settings[guild].startNotice`(켜짐 알림을 켠 서버)가 있는 길드만 싣는다. `serverWords`는 서버·명령을 부르는 낱말이 있는 인스턴스만 싣는다(낱말은 인스턴스에 딸려 어느 길드에서나 같다, id 순 200개까지, `chat::words::heartbeat`. 비어도 `{}`로 싣는다). 데몬이 원문을 해석하므로 relay는 이 낱말로 대상 서버와 명령을 찾아 자동완성·위험 확인(정식 명령 이름 기준)에 쓰면 된다. `permissions`는 `nodeSettings`에 있는 모든 길드(값이 없으면 `{defaultLevel:1, members:{}, chatbotCap:0, levels:{safe:0, caution:1, danger:2, admin:2}, commandLevels:{}, ladder:[{id:3},{id:2},{id:1},{id:0},{id:-1}]}`)이고, 릴레이는 이 값으로 자기 캐시의 데몬 행을 맞춘다. `chatbotCap`·`commandLevels`는 `NodePermissions` 값 그대로이고(`commandLevels` 키는 `<instanceId>/<명령·액션 id>` 또는 전역 액션 id), `levels`는 그 길드 프리셋으로 푼 risk별 요구 레벨(`NodePermissions::preset_need`, 가리키는 기본 단계를 지웠으면 더 엄한 쪽)과 관리 액션의 요구 레벨 `admin`(`admin_need`, strict면 3)이라 릴레이가 프리셋 표를 따로 들지 않는다. `commandLevels`는 길드당 키 순으로 200개까지 싣고, 넘으면 `commandLevelsTruncated:true`다(그 길드는 릴레이가 사전 검사를 하지 말고 데몬 판정에 맡긴다). 릴레이 사전 검사는 `actions::authorize`와 같은 순서로 요구 레벨을 센다: 모듈 명령(문장 명령)은 `commandLevels[<instanceId>/<명령>]` → 내장 명령(`start|stop|restart|status|players`)이면 `commandLevels[<instanceId>/server.<명령>]` → `levels[risk]`(데몬 `NodePermissions::required`와 같다, `chatbot/tools.ts` `requiredLevel`). 액션은 항목의 `level`(고정 레벨, 있으면 끝) → 내장 서버 액션(`server.start|stop|restart|status`)이면 `commandLevels[<instanceId>/<start|stop|restart|status>]` → `commandLevels[<instanceId>/<액션 id>]`(인스턴스가 없는 액션은 `commandLevels[<액션 id>]`) → `kind`가 `admin`이면 `levels.admin`, 아니면 `levels[risk]`. 실효 레벨은 `min(주인이면 3, 아니면 members[id] ?? defaultLevel, 챗봇 경로면 chatbotCap)`이다(`ladder` 순서로 낮은 쪽, `ladder`는 그 길드 단계 사다리로 높은 것부터). 릴레이는 이 값으로 미리 거절하지 않고, 요구 레벨이 chatbotCap보다 높을 때(누구든 챗봇으로는 닿지 못할 때)만 거절한다. 데몬이 고정한 주인(pin_owner)은 heartbeat에 없어 릴레이가 아는 주인과 다를 수 있고 스냅샷은 heartbeat 주기만큼 늦기 때문이다(chatbot/tools.ts surelyDenied). 사전 검사는 예측일 뿐이고, 통과해도 데몬이 거절할 수 있다. `levels.admin`이나 `chatbotCap`이 없는 heartbeat(예전 데몬)는 `commandLevelsTruncated`처럼 사전 검사를 건너뛰고 데몬 판정에 맡긴다. `actions` 항목의 `level`은 고정 요구 레벨이 있는 액션(`Def.discord_level`, 예: `update.apply` 3)에만 있다. 모듈이 지원해야 쓸 수 있는 고정 액션(지금은 `server.players`: 모듈 `[status] players`)의 항목에는 `modules:[이름]`(지원하는 모듈, 없으면 빈 배열)이 있고, 릴레이는 그 모듈의 서버에만 하위 명령(`플레이어`)을 만든다. heartbeat `actions`에 없는 액션(원격 메뉴에 싣지 않는 `chatbot.settings.*`·`discord.settings.set` 등 고정 레벨이 주인인 것)은 사전 검사를 하지 않는다. 사전 검사와 상관없이 데몬이 받은 문장 계획·`action`을 같은 규칙으로 다시 판정한다(`chat::permissions` `check`, `actions::authorize`). `permission` action 응답 `data`도 같은 모양에 `permissionsAt`을 더한다. `permissionsAt`은 권한을 읽기 직전의 PC 시각 Unix ms다. `permission` action 응답의 `permissionsAt`과 같은 PC 시계라, 늦게 온 heartbeat가 방금 바꾼 레벨을 되돌리지 않게 한다. 릴레이는 `hostId:guildId`별로 마지막에 반영한 `permissionsAt`을 메모리에 둔다. heartbeat `permissions`의 permissionsAt이 그 값보다 작거나 같고 차이가 5분 안쪽이면, 그 길드만 건너뛴다. 5분보다 오래된 값은 시계 보정으로 보고 받는다(`permissions.ts` `claimApply`). permission 응답보다 늦게 읽은 heartbeat를 이미 반영했으면 응답 스냅샷으로 다시 덮지 않는다. 값이 없으면(옛 데몬) 그대로 반영한다), `modules[]`는 `{name, module_aliases(게임명 `game_names` 뒤에 module.toml 별명), commands:{fields:[{name, label, description, risk, aliases?, titles?, descriptions?, inputs:[{name, label, type, required, min, max, options, titles?}]}]}, presets:[{id, label}]}`만(콘솔 템플릿·REST 엔드포인트는 싣지 않는다, `relay_command_entry`. `remote = false` 명령은 싣지 않는다. 봇 설정 `translateCommands`(기본 true)가 켜져 있으면 `titles`·`descriptions`·칸 `titles`에 모듈 locales `commands.<이름>.label`·`description`·`inputs.<칸>.label`을 `{<locale>: …}`로 싣는다. 문구가 없는 언어는 빠지고, 하나도 없으면 키가 없다. relay는 이것으로 모듈 명령 하위 명령의 언어별 이름·설명과 옵션 설명을 단다. `aliases`는 module.toml `[aliases.commands]`에 그 명령의 별칭이 있을 때만 싣는 문자열 목록으로, relay는 별칭으로 친 명령도 같은 위험도 확인을 거친다), 서버 목록의 각 줄은 relay가 읽는 `{id, name, module, status, usage?:{cpu, memMb}, players?:{online, max?}, statusLine?}`만 싣는다(설정값·경로·비밀번호는 싣지 않는다, `relay_agent.rs` `relay_server_entry`). `usage`는 실행 중일 때 하트비트마다 뜬 표본(`cpu`는 기계 전체 기준 %, 소수 한 자리), `players`는 실행 중이고 모듈이 `[status] players`로 알려 준 마지막 접속자 수(02 §1.2, 최대를 모르면 `max`가 없다), `statusLine`은 `handled:true`로 답한 익스텐션 `server.list_enrich` 결과의 `status_line`(제어 문자를 빼고 100자까지)이다(Q-5·X-1). 시작할 때 `GET /info`로 `minAgentVersion`을 비교한다(`relay_agent.rs:251-`).

**(d) Sleep/Wake**: 원본은 데몬 `nodeSettings[g].discord.sleeping`이다. 슬래시 `/사바쨩 코코낸내`/`기상`은 데몬 액션 `discord.settings.set`을 부르고, 데몬이 `PATCH /api/nodes/:g/settings {sleeping}`으로 relay의 `nodes.is_sleep`과 메모리 `_pausedGuilds`를 맞춘다(`bot/commands/discordSettings.ts` `applyNodeSettings`). 잠든 길드는 `/사바쨩` 하위 명령을 뺀 명령과 알림을 받지 않는다. 메시지는 모두 무시하고, 상호작용은 `/사바쨩` 하위 명령만 받으며 길드 서버 명령·버튼·모달에는 잠들어 있다는 안내만 보인다(`bot/gateway/gateway.ts`). 옛 데몬(액션을 모름)이면 relay에만 쓴다.

**(e) 슬래시 명령이 보이는 자리**: Discord 슬래시 목록은 길드마다 하나라서(사람마다 다르게 보일 수 없다) relay는 길드 상태로만 고른다. 전역 명령은 봇 DM에서만 보이는 `/사바쨩`(상태·연결·웹·도움말, `contexts:[BotDM]`)이다. 길드의 `/사바쨩`은 길드 명령으로, 서버 슬래시 루트와 같은 길드 범위 PUT에 담는다(`bot/commands/guildCommands.ts` `syncGuilds`). 자리는 노드가 없으면 `unbound`(연결·도움말), 있으면 `nodes.is_sleep`에 따라 `awake`(기상 뺀 전부)·`asleep`(코코낸내 뺀 전부)다. 연결된 길드의 `연결`은 내 PC를 붙인다(§4.4 (i)). 서브커맨드마다 `places`(기본 `awake`·`asleep`)로 보이는 자리를 정하고, 서브커맨드가 하나도 남지 않은 그룹은 뺀다(`bot/gateway/contract.ts` `SlashPlace`, `slash.ts` `buildRootCommand`). 잠든 길드도 서버 슬래시 루트는 그대로 둔다(지웠다 다시 만들면 Discord의 길드당 하루 200개 만들기 한도를 깎는다. `/사바쨩` 하위 명령만 바뀌는 것은 고치기라 한도와 상관없다). 잠든 동안 부르면 게이트웨이가 잠들어 있다는 안내만 한다. 연결·연결해제·옮기기·코코낸내·기상 뒤에 그 길드만 다시 맞추고, 놓친 변화는 5분 전체 맞추기가 잡는다. 길드마다 마지막으로 보낸 정의를 기억해 같으면 다시 보내지 않고, 봇이 길드에 들어오면(`guildCreate`, 추방 뒤 다시 초대 포함) 그 기억을 지워 다시 보낸다(추방되면 Discord가 길드 명령을 지운다). 등록한 길드만 다음 5분 주기에 한 번 Discord의 길드 명령 목록을 조회해 이름을 맞춰 보고(주기마다 5길드까지), 없으면 다시 등록한다. 3번 다시 등록해도 없으면 그 길드는 다시 초대되거나 재시작될 때까지 보지 않는다. 확인된 길드와 권한 없음(50001)으로 등록하지 못한 길드는 조회하지 않는다(`guildCommands.ts` `verifyGuilds`). `/사바쨩 도움말`도 그 자리의 목록만 보인다. 목록에 없는 옛 정의로 불러도 각 핸들러가 노드·권한을 다시 확인한다. 서비스는 `BotService.guildRoots(guildId)`로 특정 길드에만 루트 명령을 더할 수 있다. 같은 PUT에 담고(서버 루트 이름이 겹치면 다른 이름을 붙인다), 처리는 그 서비스의 `guildCommands`가 하며, 릴레이가 처리하는 명령이라 잠든 길드에서도 받는다. 지금은 운영 서버의 `/운영`(§4.4 (g))뿐이다.

**(f) 사바쨩 웹 중계** (`services/webHub.ts`, `routes/web.ts`, `bot/commands/webCommand.ts`): 메모리에만 둔다(단일 인스턴스, 재시작하면 다시 연다).

- `/사바쨩 내pc`(어디서나, 숨김): 친 사람의 PC 목록(최근 연결 순, 상태·버전·마지막 heartbeat). 앞의 5대에 이름 바꾸기(모달, 64자)·지우기(확인 한 번 더) 버튼. 지우면 그 호스트·대기 명령이 지워지고 토큰이 끊긴다. 그 PC가 대표인 길드는 다음 붙은 PC가 대표가 되고(없으면 노드를 지운다), 붙어 있던 길드에서는 빠진다(감사 `host_remove`, `services/hosts.ts`, `hostCommands.ts`). DM의 `/사바쨩 상태`는 PC가 여럿이면 이 목록을 보인다. 코드 없는 `/사바쨩 연결`은 켜진 PC가 여럿이면 고르는 버튼을 먼저 보인다.
- `/사바쨩 웹`(DM·연결한 길드): 친 사람의 켜진 호스트가 하나면(여럿이면 고르는 버튼을 먼저 보인다) 숨김 답으로 `https://saba-chan.online/remote/#<링크>`를 준다(`SELF_URL`은 컨테이너 안 주소라 쓰지 않는다). 링크는 nanoid 32자, sha256으로 두고 5분·한 번만 쓴다. 같은 PC의 예전 링크는 버린다. 호스트가 없으면 `status_no_host`, 오프라인이면 `cmd_host_offline`.
- `/사바쨩 에이전트`(DM·연결한 길드, `bot/commands/agentCommand.ts`): 친 사람 계정의 AI 에이전트 연결(원격 MCP, §4.4 (l))을 숨김 답으로 보인다. 연결이 있으면 클라이언트 이름(마크다운·멘션 문자를 뺀 한 줄)·마지막 사용과 끊기 버튼(`core-agent:unlink:<연결 id>`, 계정 버튼이라 잠든 길드에서도 받는다)을, 없으면 에이전트에 넣을 주소(`<issuer>/mcp`)를, 원격 MCP가 꺼져 있으면 그 안내를 보인다. 버튼은 누른 사람 자신의 연결이 그 id일 때만 끊는다(`revokeGrant`). 그 사이 다시 연결했거나 이미 끊겼으면 지금 상태를 다시 보인다.
- `GET /node/ws`(노드 토큰, 10/min, nginx는 `X-Saba-Client` 요구): 데몬 연결. PC 하나에 하나이고 새로 붙으면 예전 것을 4000 `replaced`로 닫는다. 붙은 뒤 재페어링으로 그 PC의 토큰이 바뀌었으면(`generation`) 그 연결은 쓰지 않는다: 재페어링 때 바로(그 뒤 쓰려 할 때도) 4003 `token_replaced`로 닫고 그 PC의 세션을 `host_gone`으로 끝내며, 새 세션은 `web_session`으로 데몬을 다시 깨운다. 붙으면 그 PC의 열린 세션을 `{t:'open'}`으로 다시 알린다.
- `GET /remote/ws`(허용 Origin만, 아니면 403. CORS 대상이 아니다. 20/min): 브라우저. 첫 프레임(10초 안, 4 KiB 이하. 넘으면 1009 `too_big`)은 `{t:'hello', link}` 또는 `{t:'resume', sid, key}`. 경로 판정(클라이언트 게이트 예외·CORS 제외)은 쿼리스트링을 뺀 경로로 한다. 데몬이 없으면 `web_session` 명령으로 깨우고 40초 기다린다. 열리면 `{t:'ready', sid, key, expiresAt, hostId}`, 못 열면 `{t:'error', code:'link_invalid'|'host_unreachable'|'session_gone'}` 뒤 1008로 닫는다.
- 브라우저 → 릴레이: `{t:'req', id, method, path, body?}`(id는 정수나 64자 이하 문자열, method는 GET·POST·PUT·PATCH·DELETE, path는 `/`로 시작하는 2048자 이하), `{t:'extend'}`, `{t:'bye'}`. 릴레이 → 브라우저: `{t:'res', id, status, body}`, `{t:'event', kind, data}`, `{t:'expiring', expiresAt}`(끝나기 2분 전), `{t:'extended', expiresAt}`, `{t:'closed', reason:'expired'|'left'|'replaced'|'host_gone'|'relay_closing'}`. 경로를 받을지는 데몬 문지기(01 §1.4.1)가 정한다.
- 세션은 15분이고 `extend`는 지금부터 15분으로 다시 잡는다. PC 하나에 세션 하나라 새 링크로 열면 예전 세션은 `replaced`. 브라우저가 1000·1001로 닫거나 `bye`면 바로 끝, 그 밖의 끊김은 30초 안에 `resume`(열쇠는 붙을 때마다 바뀐다. 새 열쇠를 받기 전에 또 끊길 수 있어, 브라우저가 프레임을 보낼 때까지 직전 열쇠도 받는다)으로 돌아올 수 있다. 데몬이 끊기면 답을 기다리던 요청은 502 `remote_host_gone`, 30초 안에 돌아오지 않으면 `host_gone`. 요청은 2분 안에 답이 없으면 504 `remote_timeout`, 세션마다 32건까지(넘으면 429 `remote_busy`). 프레임 한 개는 9 MiB까지. 받는 쪽이 읽지 않아 보낼 것이 16 MiB 넘게 쌓이면 그 소켓을 1013으로 닫는다(`routes/web.ts`). 양쪽 다 25초마다 ping한다.
- 감사: 열기·닫기를 `audit_logs` `action='web'`, `detail {event:'open'|'close', reason?}`로 남긴다. 요청 하나하나는 데몬 감사(source `web`)에 남는다.
- 화면은 nginx `/remote/`(정적, 없는 경로는 `/remote/index.html`, 볼륨 `../remote-web`. `deploy-remote.ps1`이 옆 저장소 `saba-chan/saba-chan-web`을 커밋한 그대로 빌드해 올리고 `release.sh`가 다른 관리 경로와 함께 교체·롤백한다. 이 경로만 CSP가 더 좁다: 스크립트는 `'self'`만, 그림은 `'self'`·`data:`·`https://cdn.discordapp.com`(프로필 사진), `Referrer-Policy: no-referrer`)이고, 두 웹소켓은 업그레이드 헤더와 함께 릴레이로 넘긴다(`test/nginxRoutes.test.ts`).

**(g) 차단 목록** (`services/blocklist.ts`, `bot/commands/operatorCommands.ts`): 악성 사용자를 디스코드 ID 하나로 막는다. 공개 저장소라 공식 바이너리인지는 가릴 수 없어 사람을 막는다.

**(i) 길드 하나에 여러 PC** (원격 데몬 R2, `services/guildHosts.ts`, `bot/commands/guildRouting.ts`, 사용자 결정 2026-10-25): 한 디스코드 서버에 여러 사람의 PC(같은 사람의 집 PC와 원격 PC 포함)가 함께 붙는다. PC를 여러 사람이 함께 소유하지는 않는다.
- 처음 연결한 PC가 대표(`nodes.host_id`)이고, 그 뒤에 연결한 PC는 `guild_hosts`에 붙는다. 길드 공통 설정(언어·접두사·잠자기·음악·챗봇·채널 배정)의 원본은 대표 PC 데몬이다. 붙은 PC는 그 길드의 설정·채널·디스코드 멤버를 읽기만 한다. 각 PC의 서버와 권한 사다리는 그 PC 주인의 것이고 판정은 그 PC 데몬이 한다(poll의 `ownerDiscordId`는 그 PC 주인). 릴레이의 미리 거르기(금지 멤버)는 대표 PC 사다리 캐시로 한다.
- 서버 목록은 PC들의 카탈로그를 대표 먼저 합친다(`catalog.ts` `mergeCatalogs`, `loadCatalog`·길드 슬래시 맞추기·도움말·챗봇이 같은 목록을 쓴다). 서버마다 `hostId`가 붙고, 이름이 겹치면(대소문자 무시) 나중 PC의 서버 이름 뒤에 `-<PC 이름>`(공백·기호를 뺀 16자, 없으면 PC id 앞 6자)을 붙인다. 같은 서버 id를 뒤 PC가 또 내면 먼저 든 PC 것만 남는다. 꺼진 PC의 서버 상태는 `unknown`이다. `/사바쨩 상태`는 길드의 PC마다 한 덩어리로 보인다.
- 명령은 `sendToDaemon` 한 곳에서 보낼 PC를 고른다: 문장 계획(`plan {text}`)은 첫 낱말의 서버가 있는 PC(서버 이름으로 불렀으면 첫 낱말을 서버 id로 바꾼다), 액션은 `instance`(계획이면 첫 단계의 `instance`)가 있는 PC, `run_plan`은 그 계획을 만든 PC(릴레이 메모리 10분)다. 서버를 가리키지 않는 길드 단위 명령(설정·권한·목록 등)은 대표 PC로 간다. PC가 하나인 길드는 payload를 바꾸지 않는다. 그래서 `목록`·`도움말`은 대표 PC의 서버만 답하고, 모듈 이름·별명으로 부르면 합친 목록에서 먼저 나오는 서버(대표 PC 쪽)로 간다. 한 PC가 돌려준 결과의 `planId`·`undoPlanId`(단계마다 포함)·`runId`도 그 PC로 기억한다(`rememberResultIds`).
- 붙은 PC가 보낸 알림·준비 이벤트·실행 결과(`plan.done`)도 그 길드의 알림 채널로 간다. PC가 여럿인 길드에서는 인스턴스가 있는 알림·준비·업데이트 알림을 합친 목록에서 그 PC의 서버일 때만 받고(`instanceCheck`), `plan.done`은 그 실행을 보낸 PC가 올렸을 때만 받는다.
- 붙은 PC가 길드 경로를 부를 때도 그 PC 주인이 길드를 떠났는지 보고, 떠났으면 그 PC만 뗀다. `/사바쨩 연결해제`는 금지된 멤버도 칠 수 있다(자기 PC만 빠진다).
- 대표 PC가 빠지면(연결해제·`/사바쨩 내pc` 지우기·주인이 서버를 떠남) 가장 먼저 붙은 PC가 대표가 되고, 옛 대표의 권한 캐시(`node_permissions`, `default_level`)는 비운다. 남은 PC가 없으면 노드를 지운다.
- 디스코드 서버 주인도 길드 공통 설정(언어·코코낸내·기상·음악 기능·채널 배정)을 바꾼다(R2b, 사용자 결정 2026-10-25 "처음 연결한 사람 + 서버 주인", `commandAccess.ts` `mayChangeGuildSettings`). 채널 배정은 릴레이가 바로 쓰고, 나머지는 대표 PC 데몬의 `discord.settings.set`이 `guildOwnerDiscordId`로 판정한다(01 §액션). 권한 사다리·업데이트·말하는 사바쨩 설정은 PC 주인만이다.
- 아직 없는 것: 계획 한 개에 여러 PC의 서버를 섞는 것(첫 단계의 PC로 간다).

**(j) 원격 데몬 직접 연결 중계** (원격 데몬 R4, `services/remoteConnect.ts`, `routes/remote.ts`, 사용자 결정 2026-10-25 "직접 TLS 연결, 릴레이는 연결될 때까지만 중계"): 같은 주인의 PC 끼리만 쓴다.
- 원격 PC(B)는 자기 직접 연결 주소와 TLS 인증서 SHA-256 지문을 올린다(`PUT /api/remote/endpoint`). 내 PC(A)는 `GET /api/remote/peers`로 같은 주인의 다른 PC와 주소를 본다.
- A는 B 앞으로 연결표를 받는다(`POST /api/remote/tickets`). 비밀은 32바이트이고 릴레이에는 SHA-256만 남는다. 2분 동안 한 번만 쓴다. 남의 PC는 있는지도 알리지 않는다(404).
- A는 B에 TLS로 붙어 받은 지문을 고정하고 연결표를 내민다. B는 그것을 릴레이에 한 번 확인하고(`redeem`, 대상 PC 토큰만) 누가 붙는지(`fromHostId`) 안다. 그 뒤의 접속 토큰은 B 데몬이 스스로 내고, 연결된 뒤에는 릴레이를 거치지 않는다.
- 원격 PC(B) 데몬 쪽(원격 포트, 주소 올리기, 짝 맺기와 토큰)은 01 §1.4.2(D1). 기본 포트 57480(사용자 확정 2026-10-26).
- 붙는 쪽 데몬(A)이 목록·연결표를 받아 원격 데몬에 붙고 요청을 중계하는 것은 01 §1.4.2 5~6(D1b). A는 원격 데몬에 닿지 못하면 `peers`의 지금 주소·지문으로 한 번 다시 붙는다.
- 공인 주소가 없는 PC(NAT 뒤)는 `address:null`로 올리고, A는 (k) 터널로 붙는다.

**(k) 공인 주소 없는 PC 터널** (원격 데몬 T1, `services/remoteTunnel.ts`, `routes/remoteTunnel.ts`, 사용자 결정 2026-10-26 "직접 연결 먼저, 안 되면 릴레이 터널"): 직접 연결이 안 되는 B 에 릴레이가 바이트를 이어 준다.
- A는 `/node/tunnel?to=<B>` 웹소켓을 연다. 릴레이는 B 앞으로 명령 `{action:'remote_tunnel', tunnelId}`를 큐에 넣고 poll을 깨운다(웹 원격 `web_session`과 같은 길). 넣지 못하면(B 오프라인 등) A를 4503으로 닫는다.
- B 데몬은 `/node/tunnel?accept=<tunnelId>`로 붙어 자기 원격 포트에 잇는다. 15초 안에 받지 않으면 A를 4408로 닫는다.
- 오가는 것은 A와 B의 TLS(지문 고정) 암호문이라 릴레이는 내용을 모른다. 바이너리 프레임만 넘기고 글자 프레임은 1003으로 닫는다. B가 받기 전에 A가 보낸 것은 256 KiB까지 모아 두었다가 넘긴다(넘으면 1009).
- 받는 쪽이 4 MiB 넘게 밀리면 보내는 쪽 읽기를 멈추고 512 KiB 아래로 줄면 다시 읽는다. 한 PC가 동시에 여는 터널 8개, 한 PC 앞으로 열린 터널 16개까지(429). 한쪽이 닫으면 다른 쪽도 닫는다. 25초 ping, 토큰이 바뀌었거나 차단되면 4503으로 닫는다. PC를 지우거나(`removeOwnHost`) 다시 페어링해 토큰이 바뀌거나 주인을 차단하면(`blockUser`) 그 PC가 낀 터널을 바로 닫는다(`TunnelHub.closeHost`, 4503 `host_gone`).
- 연결표·짝 맺기·접속 토큰은 (j)와 같다(터널 위의 TLS 안에서 한다). 데몬 쪽은 01 §1.4.2 9.
- 데몬은 두 쪽 모두 프록시 환경을 따른다(`tunnel::proxy_for`: wss는 `HTTPS_PROXY`, 그다음 `ALL_PROXY`, `NO_PROXY`와 루프백은 직접. http 프록시에 `CONNECT`로 연다. URL의 사용자명·암호는 `%XX`를 풀어 Basic 인증으로 보낸다). 웹소켓은 reqwest를 거치지 않아 따로 따른다.
- nginx `location = /node/tunnel`(노드 경로라 `X-Saba-Client` 필요). 상태는 릴레이 메모리에만 있어 다시 켜면 열린 터널이 닫히고 A가 다시 연다.


**(l) 원격 MCP** (`mcp/`, 설계 https://claude.ai/artifact/P7M94HpbN7dtAB28VwSKX4, 사용자 결정 2026-10-28): 사용자의 AI 에이전트(ChatGPT·Claude·Gemini 등)가 `<issuer>/mcp` 하나로 붙어, 디스코드 계정이 주인인 모든 PC를 주인 권한으로 다룬다.
- 연결은 디스코드 계정마다 하나다(`mcp_grants.discord_id` 고유). 새로 허가하면 예전 연결과 토큰을 지운다. 끊는 길은 앱·CLI(`/api/mcp/grant` DELETE, 데몬 `/api/relay/mcp/grant`), 디스코드 `/사바쨩 에이전트`, `/oauth/revoke`, 개인정보 지우기, 90일 미사용.
- 인가: 릴레이가 OAuth 2.1 인가 서버다. 공개 클라이언트·PKCE S256만 받는다. 클라이언트 등록은 CIMD(표준)와 DCR(폐지 예정이지만 받는다). 사람 확인은 디스코드 로그인(`identify`, 비밀값 `DISCORD_CLIENT_SECRET`)이고, 동의 화면에서 허용하면 인가 코드(60초, 한 번. 다시 쓰이면 그 연결째 지운다)를 낸다. 흐름을 시작한 브라우저에 쿠키(`saba_mcp_*`, `Path=/oauth`, 10분)를 두고 콜백·동의에서 확인한다. CIMD 문서는 이름 주소만 받고(IP로 쓴 주소는 거절) 붙는 순간의 주소가 사설·루프백이면 받지 않는다. 토큰 엔드포인트는 CIMD를 다시 받지 않고 코드·연결의 client_id만 맞춘다. 인가 응답에는 늘 `iss`를 붙인다(RFC 9207).
- 토큰은 무작위 값이고 DB에는 해시만 둔다. 갱신 토큰은 쓸 때마다 새 쌍으로 바꾼다. 같은 갱신 토큰이 10초 안에 다시 오면 같은 쌍을 돌려주고(응답을 못 받은 재시도), 그 뒤에 오면 도난으로 보고 연결을 지운다. 회전은 `rotated_at IS NULL` 조건으로 한 번만 한다. 차단 목록의 계정은 접근·갱신 토큰이 바로 막힌다.
- 도구(`/mcp`, `mcp/tools.ts`): `list_pcs`(계정이 주인인 PC), `list_servers {pc?}`(heartbeat 서버 목록), `list_actions {pc?, server?}`(데몬 `catalog {instance?}`, 서버를 주면 그 서버의 모듈 명령·조회까지), `run_action {pc?, action, server?, input?}`, `run_steps {pc?, steps[1..8]}`, `confirm {confirm_id, approve}`. `pc`는 id나 이름이고 PC가 하나면 생략한다. `server`는 heartbeat 목록의 id와 정확히 같으면 그 id, 아니면 이름(대소문자 무시)으로 인스턴스 id를 찾고, 모르는 값은 그대로 넘긴다. 다만 `list_actions`는 목록에 없는 서버면 `server_not_found`다(데몬 카탈로그는 모르는 서버에 공통 액션만 준다). 결과는 에이전트가 읽는 JSON이고, 실패는 `isError`와 코드(`HOST_OFFLINE`·`AGENT_TOO_OLD`·`pc_required`·`confirm_not_found`·`rate_limited` 등, 데몬 실패는 그 `code`와 `reason`. 실행이 밑 라우트 실패를 `result`로 감싸 오면 `result.error_code`를 코드로 쓰고, 약관 동의가 필요하면(코드 대소문자 무시) 코드 `agreement_required`와 `agreements:[{id, label, url?}]`(봇과 같은 `dispatch.ts` `agreementItems`: https 링크만, 5개까지)를 함께 준다. 여러 단계 실행이 멈추면 멈춘 단계의 코드를 쓰고 `steps:[{action, status, code?}]`와 `stoppedAt`(1부터)을 함께 준다)다.
- 데몬으로는 기존 명령 대기열에 길드 없이 그 PC로 넣는다(`mcp/daemon.ts` `sendToHost`, payload `via:'mcp'`, `locale`(PC 앱 언어 `metadata.language`), `userName`(계정 이름)). `run_action`은 먼저 `query`로 보내고, 데몬이 `not_a_query`라고 하면 `plan` → 확인이 필요 없으면 `run_plan`이다. `run_steps`는 `plan {steps}`이고 늘 확인을 받는다. 도구 호출 하나는 데몬을 50초까지 기다리고(넘으면 `STILL_RUNNING`), 코드 없이 `Unknown action`으로 답하는 옛 데몬은 `unsupported`다.
- 되묻기(사용자 결정 2026-10-28, 디스코드 DM 경로는 없다): 데몬 계획이 `needsConfirm`이면 묻는다. 2026-07-28 요청이고 요청 봉투의 클라이언트 능력 `elicitation`이 폼을 지원하면(빈 객체 또는 `form`, 링크(`url`)만이면 글로 묻는다) 화면 안 폼(`input_required`, `requestState` = 확인 번호, 문구 locales `mcp.confirmPrompt`)으로 묻고 같은 도구의 재시도로 답을 받는다. 아니면 `{status:'confirm_required', confirm_id, summary, expires_in}`을 돌려주고 에이전트가 대화창에서 물은 뒤 `confirm`을 부른다. 확인 번호는 그 연결의 그 계획 하나에 한 번, 10분이고, 화면 안 폼으로 물은 번호는 그 재시도로만, 글로 물은 번호는 `confirm`으로만 꺼낸다. 연결마다 20개까지(넘치면 그 연결의 오래된 것부터 버린다), 전체 1000개(차면 `busy`)이다(메모리, `mcp/confirm.ts`). 요약은 데몬 계획의 `summary` 줄을 `라벨: 값`으로 편 것이다(`actionResult.ts` `summaryLines`). 동의하면 `run_plan`에 `confirmedBy`(계정 본인)를 싣는다. 에이전트가 묻지 않고 동의를 보낼 수 있다는 한계가 있다(설계 문서).
- 한도: 연결마다 도구 호출 분당 60번·동시 4건(`mcp/limits.ts`, 메모리), 넘으면 `rate_limited`·`busy`.
- 동의 화면과 오류 화면은 릴레이가 그리는 정적 HTML(CSP `default-src 'none'`, `form-action 'self' <에이전트 출처>`, `frame-ancestors 'none'`)이고 문구는 릴레이 locales(`src/locales/*.ts`의 `mcp`) 10개 언어다.

| GET `/api/relay/node/:guild/members` | GET `/api/nodes/:g/discord-members`, 503이면 `/api/nodes/:g/members` | 노드 토큰 | ✓ |

- 기능 목록(전역 하한과 따로): 전역 최소 버전 `MIN_AGENT_VERSION`은 인증·서명·큐 모양처럼 옛 데몬과 함께 쓸 수 없는 변화에만 올린다. 그 밖에 옛 데몬과 다르게 다뤄야 하는 변화가 생기면, 데몬은 heartbeat `metadata.features`에 기능 이름을 더하고(`relay_agent.rs` `FEATURES`) relay는 버전 번호 대신 그 이름으로 가른다(`catalog.ts` `DAEMON_FEATURES`·`hasFeature`). 그 기능이 없는 PC에서 그 기능만 막거나 예전 방식으로 다루고, 나머지 명령은 계속 받는다. 길드에 PC가 여럿이면 모두 가진 기능만 있다고 본다(`mergeCatalogs`). 하한이 그 기능이 들어간 버전을 넘으면 이름과 relay 분기를 함께 지운다. 지금 목록: `confirm_by_daemon`(0.1.12, 되묻기를 데몬이 정한다). 새 필드를 무시해도 옛 데몬이 예전처럼 답하는 변화(예: `autoRun`, `metadataHash`)는 목록에 넣지 않는다.
- 데몬은 노드 요청에 `x-request-timestamp`·`x-request-nonce`·`x-request-signature`(`METHOD\npath\nts\nnonce\nbody` HMAC)를 붙이지만, relay는 Bearer 토큰만 검증한다(§4.1).
- 서명하는 프록시(host status·nodes·members)와 페어링·bot-invite는 `signed_base`를 거쳐, 요청한 주소가 설정된 릴레이와 같거나 루프백(모의 릴레이)일 때만 따르고 아니면 설정된 릴레이로 보낸다(`relay.rs` `signed_base`, 59a93b8).
- `/poll`, `/ack`, `/heartbeat`, `/result`, `/events`는 daemon 안의 relay agent가 부른다. 릴레이 주소는 bot config의 `cloud.relayUrl`, 토큰은 `config.json`의 `node.token`에서 읽는다(`relay_agent.rs`).
- bot config(접두사·별명)는 GUI가 daemon에만 저장하고 agent heartbeat의 `botConfig`로 relay에 간다. relay는 heartbeat metadata를 `hosts.metadata`에 저장하고 봇이 거기서 prefix를 읽는다(`heartbeat.ts`, `bot/state/nodeState.ts`). 언어·botConfig·allowedInstances처럼 키 하나만 쓰는 곳은 `metadata->'<키>'`만 읽는다.
- 인스턴스별 사용자 낱말: heartbeat metadata `serverWords?:{<instance id>:{words:[낱말], commands:{<명령 이름>:[낱말]}}}`(낱말이 있는 인스턴스만, 200개까지. 넘으면 heartbeat를 400으로 거절하고, 낱말 규칙 1~32자·공백 없음·10개에 맞지 않는 낱말은 버린다, `schemas.ts`·`catalog.ts` `userWords`). 낱말은 인스턴스에 딸려 어느 길드에서나 같다. relay는 접두사 명령을 원문 그대로 데몬에 보내고(별명 치환을 하지 않는다), 낱말은 위험 명령 확인과 챗봇 채널의 서버 명령 인식에만 쓴다. 대상은 서버 이름·ID → 서버 낱말 → 모듈 이름·별명 순으로 찾고, 명령 낱말은 그 인스턴스 명령의 `aliases` 앞에 붙는다(`findCommandTarget`·`commandsFor`·`riskOf`). `serverWords`가 없는 0.1.10 데몬은 길드별 `instanceWords?:{<guildId>:{<instance id>:{words, commands}}}`(길드 50·길드당 인스턴스 50까지)를, 둘 다 없는 옛 데몬은 `botConfig.moduleAliases`·`commandAliases`를 같은 자리에 쓴다.
- `/사바쨩 상태`는 호스트가 온라인이면 heartbeat `servers`(길드는 `allowedInstances`로 거른 것, 20개까지)를 한 줄씩 붙인다. 각 줄에는 실행 여부, `players`(👥 접속/최대), `usage`(CPU %·RAM MB), `statusLine`을 마크다운·멘션·가린 링크 문자를 빼고 넣는다(`bot/commands/coreService.ts`). PC 전체 자원 줄(`monitor.summary`)은 붙이지 않는다(사용자 결정 2026-10-20). 끝에는 heartbeat `metadata.onboarding {steps:[{id, done, optional}], next}`(J1-a)로 다음 단계 한 줄을 붙인다: `next`가 `module`·`server`면 그 안내, `next`가 null인데 `chatbot` 단계가 안 됐으면 API 키 선택 안내.
- `/사바쨩 설정`(노드 소유자, 본인에게만 보임)은 이 길드의 챗봇 설정 일부를 바꾼다. `query chatbot.settings.get`으로 읽고 켜기·끼어들기·기억 토글, 실행 전 확인 단계(누를 때마다 all→caution→danger), 도구 토글과 호출어 모달을 보인다. 데몬이 `tools`를 주면(0.1.12) 도구를 카테고리마다 한 줄(버튼 한 행)로 보이고 누르면 `tools`에서 넣거나 뺀다. 데몬의 공통 `allowedTools`에 없는 도구는 막힘으로 보이고 버튼을 끈다. 운영 키·제공사 때문에 못 쓰는 도구는 그렇다고 덧붙인다. `tools`가 없는 옛 데몬에는 예전처럼 웹 검색 토글과 `disabledTools` 묶음 토글을 보인다. 누르면 데몬의 지금 값에서 뒤집어 `plan chatbot.settings.set` → (`needsConfirm`이 false면) 같은 요청자로 `run_plan`을 보내고 다시 읽어 고친다. API 키·채널은 다루지 않는다(`bot/commands/chatbotSettings.ts`).
- 챗봇 판단 입력(`chatbot/transcript.ts`): 모델에는 상황 자료 JSON 뒤에 대화록을 붙인다. 대화록은 `지금:` 줄, `[이전 대화]`(최근 30개), `[새 메시지]`이고 한 줄이 `#번호 시각 이름(나·오너·봇 표시) ↪답장대상: 본문 [첨부 표시]`다. 디스코드 id는 모델에 보내지 않는다: 릴레이가 판단마다 번호표(`#N`↔메시지 id)와 이름표(표시 이름↔사용자 id, 같은 이름은 `(2)`)를 만들어 `reply_to`·도구 인자를 실제 id로, 도구 결과·기억·payload의 id를 번호·이름으로 바꾼다. 도구가 보낸 진행·결과 알림은 `[자동 알림]`으로 적는다(메모리 기록, 재시작하면 잊는다). 시각의 시간대는 길드마다 하나로 모델이 `set_time_zone`으로 정하고(`chatbot_records` kind `time_zone`), 정하기 전에는 노드 언어로 추정한다(`toolkit/clock.ts`). 한 번짜리 예약은 릴레이가 들고 있다(`chatbot/reminders.ts`, `chatbot_records` kind `reminder`, 길드마다 20개, 1분 뒤~30일 안). 글 알림은 `set_reminder`로 걸고 그 시각에 건 사람을 멘션해 보낸다. 서버 명령은 `run_command`의 `at_unix`로 걸고, 지금 실행할 때와 같은 확인 규칙을 거친다: 확인이 필요하면 버튼을 누를 때 예약되고(요청자가 누르면 `confirmedBy`를 함께 저장), 그 시각에 요청자 이름으로 `via` chatbot 명령을 보낸다(권한은 그때 데몬이 판정). `list_reminders`로 보고 `cancel_reminder`는 건 사람이나 노드 주인만 한다. 릴레이가 15초마다 때가 된 것을 지우면서 꺼내고, 한 시간 넘게 밀렸거나 그 채널의 챗봇이 꺼졌거나 재우는 중이면 보내지 않고 버린다. 지침은 세 겹이다(`chatbot/prompt.ts`): 매번 같은 전체 지침 `assets/chatbot/saba.md`(+서버 프롬프트. HTML 주석과 안내 주석만 품고 있던 제목은 모델에 보내지 않는다(처음부터 아래 글이 없던 제목은 남긴다), `memoForModel`. 앱의 기본 틀 안내 줄이 주석이다), 대화록 뒤에 붙는 상황 지침 `assets/chatbot/situations/`(분명한 부름 `must_respond`·호출 감지·대화 이어짐·정기 수신 중 하나와 공통 당부), 도구 묶음(`ToolModule.name`, 서버 조작은 `game_servers`)의 결과 지침 `assets/chatbot/guides/<이름>.md`다. 결과 지침은 판단(모델 대화)마다 그 묶음의 도구를 처음 부를 때 결과의 `guide`로 붙는다. 자기 그림 레퍼런스는 `assets/chatbot/references/`(`reference:saba-sheet` 설정화·`saba-front`·`saba-side`)다. 그림 모델에는 레퍼런스(있으면), 요청 메시지까지의 최근 대화(이름과 본문만, 12줄, 자동 알림 제외), 모델이 쓴 요청문 순서로 넘기고 요청문을 우선한다(`toolkit/images.ts`).
- 게임 관련 검색 도구(0.1.12, `chatbot/toolkit/`): 롤(`lol.ts`, Riot API), 배그(`pubg.ts`, PUBG 공식 API `api.pubg.com`, `PUBG_API_KEY`), 메이플(`maplestory.ts`, 넥슨 Open API, 한국 서버만, `NEXON_API_KEY`). 운영 키가 없으면 그 묶음을 붙이지 않는다. 배그는 키 전체로 분당 9회(공식 한도 10회)를 넘기지 않고 429면 `Retry-After` 동안 보내지 않으며, 길드마다 분당 2번 조회한다. 메이플은 키 전체로 초당 4회, 길드마다 시간당 20번 조회한다. 둘 다 결과를 캐시하고, 롤처럼 디스코드 사용자 ↔ 게임 계정 연결을 노드별 `chatbot_records`(`pubg_account`·`maplestory_character`)에 기억한다(`toolkit/accounts.ts`).
- 크레딧 소진(`chatbot/index.ts` `notifyFailure`): 모델이 `quota`로 실패하면 부르지 않은 판단이어도 그 채널에 `⚠️` 한 줄(`chatbot/locales.ts` `quotaExhausted`)을 길드마다 24시간에 한 번 보낸다. 보낸 뒤에 마지막 알림 시각을 메모리와 `chatbot_records` kind `notice`, key `quota`에 둔다(재시작해도 하루 한 번, 보내지 못하면 다른 채널이 알릴 수 있다). 그 뒤 부른 판단에는 평소 오류(`error.quota`, 채널마다 5분에 한 번)로 답한다. 켠 도구(`enabledTools`)에 `game_servers`가 없으면 서버 조작 도구를 붙이지 않는다.
- 챗봇·음악 사용 한도(relay 메모리 기록, 재시작하면 비운다): 챗봇은 판단으로 가는 메시지(호출·세션 중 후속)를 사람마다 분당 12개, 판단을 길드마다 분당 20회·시간당 300회까지 받고 넘친 것은 답하지 않는다(`chatbot/callLimit.ts`). 운영 공용 키 도구는 길드마다 몫이 있다: 종목 조회(Alpha Vantage) 하루 8회(캐시 적중은 세지 않는다, 넘으면 `guild_quota`), Riot 2분에 요약 2번·계정 조회 20번(`riot_guild_quota`, 요약 한 번이 Riot 호출 40여 회라 따로 센다). `read_webpage`는 사람이 이번 새 메시지에 그대로 적은 주소만 읽는다(아니면 `url_not_from_user`, `toolkit/research.ts`). 음악은 길드마다 분당 10회에 더해 사람마다 모든 길드를 합쳐 분당 10회이고(`music_user_rate_limited`. 둘 다 통과할 때만 세고, 볼륨 버튼은 길드·사람 모두 따로 센다), 재생을 바꾸는 명령·버튼·대기열 메뉴(건너뛰기·정지·일시정지·볼륨·셔플·반복 등)는 봇이 음성 채널에 있으면 그 채널에 있는 사람만 쓴다(`music_not_listening`, 숨김 답. 곡 추가·조회는 누구나, `bot/music/handlers.ts` `admitMusic`).
- 권한 판정의 주체는 데몬이다(`chat/permissions.rs`, 01 문서 BotConfig 절). 금지(-1) 멤버는 relay 게이트웨이가 음악·챗봇을 포함한 봇 기능 전체에서 먼저 막는다. 슬래시·버튼에는 숨김 답으로, 봇에게 한 메시지에는 10분에 한 번 짧은 안내로 답한다(`bot/gateway/gateway.ts`, `commandAccess.ts` `isBanned`). 설정이 없는 길드도 기본 레벨(유저)로 판정한다. relay의 `node_permissions`·`nodes.default_level`은 데몬 값의 캐시이고 relay 바깥 검사(`commandAccess.ts`)에 쓴다. `/사바쨩 권한` 명령은 `permission` action으로 데몬에 보낸다. `부여`·`기본`의 레벨 칸은 문자열 자동완성이다: heartbeat `permissions[길드].ladder`에서 소유자를 뺀 단계를 사다리 순서로(더한 단계는 그 이름) 보이고, 값은 단계 id다. 직접 친 이름도 받고(배포 직후 옛 정수 칸 값도 받는다), 그 서버에 없는 값이나 `부여`에서 비운 칸의 기본값(유저)이 그 서버에 없으면 `perm_invalid_level`로 답한다(`coreService.ts` `levelChoicesFor`·`parseLevelChoice`). 릴레이가 레벨을 견줄 때는 사다리 순서를 쓴다(`catalog.ts` `levelAtLeast`, 사다리가 없는 옛 데몬은 기본 단계 숫자로 견주고 10 이상은 모자란 것으로 본다). 거부 문구는 need가 소유자면 `cmd_needs_owner`, 관리자면 `cmd_needs_admin`, 더한 단계면 그 이름을 넣은 `cmd_needs_level`, 그 밖은 `cmd_no_permission`이다(사다리에서 관리자보다 위로 옮긴 단계도 관리자 문구가 아니다, `dispatch.ts` `deniedOutcome`). 카탈로그에서 risk가 danger인 prefix·길드 슬래시 명령은 바로 보내지 않고 확인 버튼을 띄운다. 요청한 사람만 누를 수 있고, 누른 사람 이름으로 같은 문장의 계획(`plan {text}`)을 보낸다. 레벨이 모자라면 확인 없이 거부 문구다(`actionCommands.ts` `dangerConfirm`). 챗봇 도구(`run_command`·`run_action`·`plan_actions`)는 모델이 도구를 부르게 한 새 메시지(`request_message_id`, 모델에는 대화록 번호 `#N`, 아래 판단 입력 줄)만 받고, 요청자는 릴레이가 그 메시지의 실제 작성자로 넣는다(문맥 메시지·봇 메시지는 `current_human_request_required`). `run_command`·`run_action`의 확인: danger와 관리 액션(`kind` admin)은 늘 확인, 그 밖은 챗봇 설정 `confirmLevel`을 따른다: `all`은 모두, `caution`은 caution 이상, `danger`는 danger와 관리 액션만 확인한다(`chatbot/tools.ts` `chatbotAsks`. 금지 명령은 단계와 상관없이 금지다. 액션은 데몬의 `needsConfirm`도 따르고, 조회는 확인 없이 실행한다). 확인 없이 실행하는 것은 요청 글이 사바쨩을 불렀고(멘션·호출어·답장) 모델이 읽은 문맥·새 글이 모두 요청자 본인 것이며(링크 미리보기·첨부 사진은 본인 글에 붙어 있어도 남의 자료로 본다) 이번 판단에서 기억·외부 자료 도구·조회·로그·명령 결과를 읽지 않았고 저장 자료(눈치 메모 `social_notes`, 롤 계정 `lol_accounts`, 도구 묶음의 `payloadExternal`)가 판단에 실리지 않았을 때뿐이다. 아니면 요청자 확인 버튼을 거친다. `plan_actions`는 늘 확인이다. 이번 묶음에 글을 쓴 사람이 여럿이면 위험도와 상관없이 확인을 거치고(조회는 `multiple_requesters`로 거절), 버튼은 요청자만 누른다. heartbeat `permissions[길드]`에 `chatbotCap`·`levels`가 있으면 릴레이는 요구 레벨((c)의 모듈 명령 순서: `commandLevels["<인스턴스>/<명령>"]`, 내장 명령이면 `commandLevels["<인스턴스>/server.<명령>"]`, 없으면 `levels[risk]`)을 `chatbotCap`과 비교해(`commandLevelsTruncated`이거나 `levels.admin`·`chatbotCap`이 없는 길드는 비교하지 않는다. `run_action`과 `plan_actions`의 단계도 (c)의 액션 순서로 세고, 앞 단계가 만들 서버 `@N`은 세지 않는다) 요구 레벨이 `chatbotCap`보다 높은 요청(누구든 챗봇으로는 닿지 못하는 요청)만 보내지 않고 `permission_denied`로 돌려주며(작성자 레벨이 모자란 요청은 데몬이 거절한다, (c)의 RA9 줄), 이 값을 모델에도 보인다(`describe_commands`의 `required_level`, payload `requester_levels`). 최종 판정은 데몬이다(`chatbot/tools.ts`).

### 6.1 소유자 프레이밍("daemon이 주인, 인터페이스는 무력") 위반

1. ~~**GUI가 업데이트 주기를 직접 돌린다**~~ → 해결: daemon이 주기 확인을 한다(`src/ipc/updates.rs:256-283`). GUI는 캐시된 상태만 10분마다 읽는다(`saba-chan-gui/src-tauri/src/lifecycle.rs:539-581`).

3. ~~**GUI가 relay를 직접 호출한다**(`PATCH /api/hosts/:id/bot-config`)~~ → 해결: GUI는 bot config를 daemon에 저장하고, relay 동기화는 agent heartbeat가 맡는다(`saba-chan-gui/src/api/createApi.js:865-874`, `relay_agent.rs:381-395`).
4. ~~**GUI가 Discord bot 실행 명령을 조립한다**, 실행 경로가 두 개~~ → 해결: 로컬 Discord bot이 없어졌다. relay agent는 daemon 안에서 노드 토큰이 있으면 기동 때 자동으로 시작한다(`relay_agent.rs:178-189`, `ipc/mod.rs:860-866`).
5. GUI가 daemon을 `--spawned`로 spawn하고(Tauri 셸 `saba-chan-gui/src-tauri/src/lifecycle.rs:158-218`) installer를 `--uninstall`로 실행한다(`native.rs:149-184`). 인터페이스가 프로세스 감독 역할을 맡고 있다.
6. ~~**extensions 용어 충돌**(`discord_bot/extensions/*.js`, `music.js`가 Python 익스텐션을 직접 spawn)~~ → 해결: `discord_bot/`이 저장소에서 없어졌다.
7. **server-chan과 프레이밍의 관계**
   - relay는 프레이밍에 맞는다. Discord를 향하는 bot은 server-chan 쪽 하나뿐이고, saba-chan은 daemon 안의 relay agent로 실행기 역할만 한다. "server-chan이 bot에 추가 기능을 준다"기보다는 **server-chan이 bot 그 자체**다.
   - music-server는 relay bot의 부가 기능이지만 소스가 없다.
   - chatbot-server는 daemon과도 relay와도 연결이 없는 **별개의 bot**이라 프레이밍을 벗어난다.
   - 업데이트도 relay가 SSOT다(§1.3-1.4). server-chan은 bot 지원을 넘어 배포 인프라(서명된 릴리즈 manifest 제공)까지 맡는다.
