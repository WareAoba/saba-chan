# 04. 클라이언트 계층: GUI · CLI · Discord Bot (server-chan) · 공유 상수 · 로케일

> 이 문서는 코드에서 직접 도출했다. 기존 docs/README는 신뢰하지 않았고, 코드와 어긋나는 주석이나 문서는 각 항목에서 따로 표시했다.
> 기준 원칙(프로젝트 오너): **daemon(saba-core)이 서비스의 주인이며 모든 기능은 daemon을 거친다. 인터페이스(GUI/CLI)는 혼자서 아무것도 하면 안 되고, 파일 편집도 daemon API를 거쳐야 한다.** modules는 Python 게임 서버 매뉴얼, plugins(=extensions)는 Python으로 작성되어 인터페이스에 컴포넌트를 주입하고, server-chan은 중앙 relay에서 Discord 봇을 돌리고 daemon은 relay 에이전트로 붙는다.
> 이 원칙을 어기는 지점은 모두 **§7 "daemon 우회 지점 전수 목록"**에 정리했다. 이 문서에서 가장 중요한 결과물이다.

Daemon 라우터의 기준 위치: `src/ipc/mod.rs:639-817`(`router()`, 인증 미들웨어 `auth::auth_middleware`는 `:816`), `src/ipc/updates.rs:106-119`(`/api/updates/*`, 인증 layer **이전**에 `.merge()`로 붙어 같이 인증된다, `src/ipc/mod.rs:812-816`).

## 1. GUI (saba-chan-gui, Tauri)

> 2026-10-18 기준 Tauri 2(플러그인 dialog·opener·notification), Vite 6.4, Vitest 5. Electron 메인 프로세스(main.js·preload.js)는 0.1.5에서 Tauri 셸로 바뀌었다. 프런트 빌드에는 여전히 Node `>=22.12`가 필요하다(`saba-chan-gui/package.json` `engines`). 산출물은 프런트(`build/`)를 넣은 exe 하나 `saba-chan-gui.exe`(Unix `saba-chan-gui`)다(`src-tauri/Cargo.toml` `[features] default = ["custom-protocol"]`, `tauri.conf.json` `bundle.active false`). Windows는 WebView2로 화면을 띄운다. 개발 실행은 `npm start`(vite 5173 + `cargo run -p saba-chan-gui --no-default-features`).

구성은 둘이다.
- **Tauri 셸** `saba-chan-gui/src-tauri/src`(Rust): 창·트레이·데몬 기동·토큰·이벤트 스트림 같은 네이티브 일만 한다(`lib.rs:1-4`).
- **브리지** `saba-chan-gui/src/api`: `window.api` 하나를 만든다(`install.ts`, `createApi.ts`). 창 제어·외부 주소 열기·언어도 `window.api`에 있다(예전 Electron 시절의 두 번째 브리지 `window.electron`은 없앴다). `window.__TAURI__`가 있고 `window.api`가 없을 때만 설치하므로 테스트 mock과 브라우저 개발 mock(`src/dev`)은 그대로다(`install.ts:12`). `src/index.tsx`가 가장 먼저 import한다. 데몬 응답 가공(상태별 오류 문구)은 브리지가 한다. 데몬 호출은 실패해도 던지지 않고 실패 본문 하나로 돌려준다(`daemon.ts` `call`·`failureBody`): 데몬이 준 오류 본문에 `error`(없으면 `message`나 오류 문구)와 `error_code`(연결 실패면 `ECONNREFUSED` 같은 연결 오류 코드)를 채운다. 2xx 본문은 그대로다. 데몬 본문은 경로마다 `ok:false`·`success:false` 중 하나를 싣거나 `error`만 싣으므로 화면은 `utils/apiResult.ts` `failed()` 하나(`!res`·`ok:false`·`success:false`·`error`·`error_code`)로 실패를 판정한다(웹도 같은 것을 쓴다). 따로 정하지 않은 데몬 호출은 30초를 기다린다.
- **타입** `saba-chan-gui/src/types`: 데몬 응답 모양(`daemon.ts`, 칸마다 기준인 Rust 구조체 이름을 적었다)과 window 전역(`global.d.ts`). `window.api`의 타입은 구현에서 뽑은 `SabaApi`(`createApi.ts` 끝)이다. 서버·모듈·익스텐션 목록과 GUI 설정은 칸까지 적었고, 나머지 응답은 공통 오류 칸만 적은 `ApiBody`로 받는다. 타입 검사는 `npm run typecheck`(TypeScript 7 `tsc`, `tsconfig.json` strict)이고 CI GUI 작업이 돌린다. JS에서 옮기는 동안은 `allowJs`로 남은 `.js`를 함께 묶되 검사하지 않고(`checkJs: false`), `.js` 안의 JSX는 `vite.config.js`의 `saba-jsx-in-js` 플러그인이 변환한다.

### 1.5 사바쨩 웹 (`saba-chan-web`, React + Vite)

PC 주인이 폰 브라우저로 서버·인스턴스를 관리하는 원격 화면이다. PC 없는 사람도 같은 링크로 디스코드 서버 설정을 관리한다(`hostId` null 세션). 디스코드 `/사바쨩 웹`(길드·DM·`/내사바쨩`)이 준 일회용 링크(`https://<릴레이>/remote/#<토큰>`)로 열고, 릴레이 웹소켓 `/remote/ws`로 데몬에 요청을 보낸다. 릴레이 쪽 계약은 05 §4.4(f), 데몬 쪽 문지기는 01 §1.4.1.

- 배포: server-chan `deploy/deploy-remote.ps1`이 이 디렉터리를 `npx vite build`해 `dist/`를 서버의 `remote-web`으로 올리고, Caddy(server-chan `deploy/caddy/Caddyfile`)가 `/remote/`로 낸다(`base: '/remote/'`). 이 디렉터리나 함께 빌드되는 `saba-chan-gui/src`·`public`, `locales`에 커밋하지 않은 변경이 있으면 배포를 멈추고, 빌드한 커밋은 배포 복구 자료의 `sha`에 남는다.
- 세션(`src/session.ts`): `hello{link}` → `ready{sid,key,expiresAt,hostId}`. 끊기면 25초 안에 `resume{sid,key}`로 다시 붙고(릴레이 유예 30초), 페이지를 떠나면(`pagehide`) `bye`. 요청은 `req{id,method,path,body}` → `res{id,status,body}`, 130초가 지나면 `remote_timeout`으로 끝낸다. 연장은 `extend`.
- 브리지(`src/api.ts`): GUI `createApi({invoke, hub}).api`를 그대로 쓰고 `invoke('daemon_request')`만 세션 요청으로 바꾼다. 다른 Tauri 명령(창·파일 대화상자·프로세스)은 `not_supported`로 막는다. 응답 가공과 오류 문구는 GUI와 같다. 릴레이 `event{kind,data}`는 `onDaemonEvent`로 `{type,data}`가 되어 온다.
- 릴레이 API(`src/relay.ts` `createRelay(session)`): 같은 세션으로 `/relay/*`(05 §4.4(f))를 부른다. 답은 `{ok, data}` 또는 `{ok:false, status, error}`(릴레이 오류 코드, 연결 실패는 `status` 0). PC 없는 서버의 디스코드 설정·배정·말하는 사바쨩·서버 관리에 쓴다.
- GUI에서 가져오는 것은 `createApi`, `events`, `serverView`, `localizedText`, `commandRisk`, `portCheck`, 새 서버 칸 `installFields`, 예약 작업 초안·검사 `utils/schedule`(GUI 백업·예약 탭과 같은 순수 함수), 활동 기록 한 건의 문구 `utils/audit`(`auditRange`·`auditWhat`·`auditWho`·`auditResult`, GUI 작업 기록과 같다), 언어 목록 `utils/languages`, 권한 단계 계산 `components/discord/levels`(멤버 찾기 `searchMembers`, 레벨 요약 `levelSummary`, 칩 색 `chipTone` 포함), 앱과 같은 상태를 쓰는 화면 없는 훅 `components/discord/useLadderDraft`(레벨 편집)·`useStairsDraft`(명령 계단 초안)·`useMemberSearch`(멤버 찾기)와 칩 움직임 `flip`·끌기 `pointerDrag`, 서버 관리 기간 문구와 고르기 값 `components/discord/modDuration`(gui `discord.mod.dur_*`), `tokens.css`, 아이콘 `components/Icon`, 드롭다운 `components/CustomDropdown`(웹 `components/Dropdown.tsx`가 감싼다)뿐이다(`src/test/guiImports.test.ts`). 화면은 따로 만든다. GUI에 없는 아이콘만 `src/components/icons.tsx`에 둔다. 로고·사바쨩 그림은 GUI `public/`의 파일을 `@art` 별칭으로 가져온다(`src/art.ts`의 목록만 빌드에 들어간다).
- 주기 읽기(서버 목록 4초, 콘솔 1.5초, PC 사용량·데몬 로그 3초, 설치 진행 2초)는 `components/poll.ts` `startPoll`로 한다: 앞 요청이 끝난 뒤에 다음을 잡고, 탭이 숨어 있으면 쉬었다가 보이면 바로 읽는다. 콘솔·데몬 로그 상자는 맨 아래에 있을 때만 새 줄을 따라 내려가고, 위로 올려 읽는 중이면 그 자리에 둔다(`components/useStickToBottom.ts`, 맨 아래 24px 안이면 다시 따라간다).

## 3. CLI (saba-chan-cli, Rust)

> 이 절은 CLI 리메이크(PR #6, 브랜치 `claude/cli-remake-b1wszk`) 기준이다. 예전 TUI(`tui/`, `process.rs`, `config.rs`, `gui_config.rs`, `cli_config.rs`, `module_registry.rs`)는 이 리메이크에서 모두 지워졌다.

### 3.1 쓰는 방법 세 가지
- **한 번 실행하는 하위 명령**: clap 기반(`cli.rs`). `status`, `start|stop|restart <서버>`, `console`, `run <서버> <게임 명령>`, `server …`(list, info, add, remove, commands, send, chat(게임 채팅으로 `--name 이름 본문`), settings, set, properties, rest, update, history, validate, diagnose, agree, reset, rename, reorder 등), `daemon …`, `module …`, `extension …`, `bot …`, `backup …`, `schedule …`, `chatbot …`(show, set, key, clear, models, credit, tools, template, forget)`, `update …`, `config …`, `chat <문장>`, `monitor [--watch] [--interval 초]`, `version`, `shell`, `tui [--server <서버>]`, `gui [서버]`(GUI로 전환: `POST /api/clients/launch {kind:'gui'}`로 그 서버를 연 GUI를 띄운다), `completions <셸>`·`completions --install [--shell 셸]` (`cli.rs:41-138`). 콘솔에 한 줄을 그대로 보내는 명령은 `server send`다(`rcon` 하위 명령은 없다). `GET /api/servers`의 `port_conflict_stops`(데몬에 10분 남는 알림)는 `status`만 `?notices_after=<이 실행에서 본 마지막 id>`로 받아 보여 준다. 새 실행은 0부터라 남은 알림을 언제 일인지와 함께 다시 보이고, 셸 안에서 다시 부르면 본 것 뒤만 보인다(L50). 서버 목록·상태 대기 같은 나머지 호출은 `?notices=keep`이다(`client.rs` `servers`). `schedule add`는 `start|stop|restart|save|backup|announce|update|command`와 때(`--every` 또는 `--at`에 `--every-days N [--from 날]`·`--on mon,fri`·`--date 날` 중 하나, `edit`의 `--daily`는 날 규칙을 지운다), `--warn`(restart·update·stop), `--command 이름 --arg 이름=값`(command)을 받는다. `risk = "danger"`인 게임 명령은 저장 전에 한 번 더 묻는다(`confirm_danger`, GUI와 같다). `schedule show`는 데몬의 `next_runs`를 이 PC 시간으로 보이고, 데몬 PC와 시간대가 다르면 알린다. `schedule`의 추가·고치기·지우기·켜기·끄기·보관 수는 읽을 때 받은 `revision`을 PUT에 실어, 그사이 다른 곳에서 바뀐 일정이면 409 `schedule_changed` 안내로 끝난다(`schedule clear`만 싣지 않는다, `cmd/schedule.rs` `save_body`). 저장 응답의 `warnings`(`date_passed`: 이미 지난 한 번 작업)는 경고로 보인다. `schedule edit --command`는 게임 명령을 바꾸고, 다른 명령이면 `--arg`를 주지 않는 한 옛 인자를 버린다.
- **무인 설치**: `saba-chan-cli install [--dir 폴더] [--components-dir 폴더] [--modules a,b] [--channel stable|rc|beta] [--gui|--no-gui]`는 데몬이 아직 없는 PC에 창 없이 설치한다(`cmd/install.rs`). `--channel`을 주면 그 채널의 최신 판을 받고 설치 뒤 `config.json`의 `updates.channel`에 적어 이후 업데이트도 그 채널로 받는다(없으면 이 CLI 빌드의 채널로 받고 설정은 건드리지 않는다, 05 §2). 데몬 API 대신 창 인스톨러와 같은 `saba-chan-installer-core`를 부른다(05 §2). 화면이 없으면(리눅스는 `SSH_CONNECTION`이 있거나(`ssh -X`의 전달된 화면은 서버의 데스크톱이 아니다) `DISPLAY`·`WAYLAND_DISPLAY`가 모두 없음, 맥은 `SSH_CONNECTION`이 있음(맥 데스크톱에는 `DISPLAY`가 없다), Windows는 Server Core(레지스트리 `InstallationType`)이거나 `SSH_CONNECTION`이 있거나 `SESSIONNAME`이 없음) 헤드리스 구성, 있으면 데스크톱 구성이고 `--gui`·`--no-gui`가 감지보다 먼저다. 이 PC에 설치본이 이미 있으면(`existing_install`) 환경을 보지 않고 그 설치의 구성(`install-profile.json`)을 그대로 따른다(데스크톱으로 깐 PC에 SSH로 들어와 다시 깔 때나 다른 PC의 앱이 `remote install`로 다시 깔 때 GUI를 지우지 않게. 원격 설치는 `--no-gui`를 붙이지 않는다, 01 §1.4.2 12). 구성을 바꾸려면 `--gui`·`--no-gui`를 준다. 폴더와 모듈은 인자가 없으면 묻고, 요약을 한 번 확인한 뒤 설치한다(`--yes`·`--json-stream`). 설치는 대상 폴더의 CLI를 모두 끄므로, 그 폴더 안에서 실행된 CLI는 시작 전에 사용법 오류로 거절한다. 다른 폴더에 설치본이 이미 있으면(05 §2 설치 위치) 그 폴더를 알리고 사용법 오류로 거절한다. 쓸 수 없는 설치 폴더(`check_install_dir`)와 모듈·익스텐션 위치(`--components-dir`, `check_components_dir`)도 받기 전에 사용법 오류로 거절한다. 어느 설치의 것인지 모르는 데몬이 떠 있으면 끄지 않고 먼저 끄라고 안내하며 멈춘다. 받을 릴리스는 실행한 플랫폼 것(`relay::current_platform`)이다. `windows-x64`와(0.1.11부터) `linux-x64`(헤드리스, 0.1.12부터 GUI까지 든 데스크톱 구성도), (0.1.12부터) `linux-arm64`(헤드리스, 0.1.12 두 번째 베타부터 GUI까지)를 게시하므로(05 §1.3, §3.1) 그 밖의 플랫폼에서는 받기 단계에서 "게시된 릴리스 없음"으로 끝난다. 창 앱을 게시하지 않는 플랫폼(`APP_PLATFORMS`인 `windows-x64`·`linux-x64`·`linux-arm64`·`macos-arm64` 밖. `macos-arm64`는 아직 게시하지 않는다(05 U10). 새 플랫폼은 창 앱을 싣기 시작할 때 이 목록에 넣는다)에서 받은 manifest에 `gui`가 없으면 `--gui`를 주지 않은 데스크톱 구성은 헤드리스로 바꿔 설치하고 그렇다고 알린다(`fit_profile`, `install.no_gui_build`). `--gui`를 줬거나 앱을 게시하는 플랫폼이면 바꾸지 않고 필수 컴포넌트가 없다고 멈춘다(잘못 나온 릴리스로 있던 데스크톱 설치의 GUI를 지우지 않게). 리눅스는 한 줄 설치(`install.sh`, 05 §3.1)가 이 명령을 부른다. 리눅스에서는 설치가 `~/.local/bin/saba-chan`·`saba-chan-cli` 링크도 건다(`user_path::add`→`link_cli`. install.sh를 거치지 않아도 명령이 생긴다. 셸 설정은 건드리지 않고, 링크가 아닌 같은 이름의 파일은 덮지 않는다. install.sh도 같은 링크를 건다: 이 변경 전 릴리스의 CLI를 받는 동안 필요하다). 리눅스 데스크톱 구성은 시작 메뉴 대신 앱 메뉴 항목(`~/.local/share/applications/saba-chan.desktop`, 05 §2)을 만든다. 맥은 기본 폴더가 `~/Applications/Saba-chan.app/Contents/MacOS`이고 데스크톱 구성이면 앱 묶음 정보·아이콘을 놓고, 끝나면 묶음을 `open`으로 열라고 안내한다(`install.next_mac_app`, 05 §2 10단계). 실패하면 설치 라이브러리 기록을 창 인스톨러와 같은 파일(`log_file_path`)에 덧붙이고 그 경로를 안내한다(파일을 열지 못하면 경로를 안내하지 않는다). 끝나면 데몬을 켜는 명령을 붙여 넣어 실행할 수 있는 꼴로 보인다(Windows는 `pushd "폴더"`와 `.\saba-chan-cli daemon start` 두 줄). 리눅스 데스크톱 구성은 앱이 데몬을 켜므로 대신 앱 메뉴에서 열거나 `'<폴더>/saba-chan-gui' &`로 열라고 안내한다(`install.next_app`).
- **제거**: `saba-chan-cli uninstall [--remove-settings] [--remove-instances]`는 이 CLI가 든 설치 폴더의 사바쨩을 명령창에서 지운다(`cmd/uninstall.rs`). 창 제거기와 같은 `saba-chan-installer-core` `uninstall::do_uninstall`을 부르므로 지우는 범위와 남기는 규칙(05 §2 제거)이 같다. 아무것도 붙이지 않으면 설정과 게임 서버를 남긴다. 한 번 확인한 뒤 지우고(`--yes`로 건너뜀), 지우지 못한 항목이 있으면 그 경로와 함께 실패로 끝난다. 설치 폴더에서 실행된 CLI가 아니면 지울 것이 없다고 알린다. 창에서 고르는 화면은 없다(실행 방식은 부르는 쪽이 정한다).
- **전체 화면 메뉴(TUI)**: 인자 없이 터미널에서 실행하면 열린다(`saba-chan-cli tui`도 같다, `tui/`). `tui --server <id>`는 그 서버를 골라 연다(GUI의 "CLI로 전환"이 붙인다). 쪽은 다섯이다: 서버·디스코드·모듈·익스텐션·업데이트·앱 설정(`tui/app.rs` `Page`, 숫자 키 1~5). 서버·디스코드 쪽은 왼쪽 목록과 오른쪽 상세이고, 상세는 탭 줄(오른쪽 끝에 그 탭의 버튼, 드문 것은 [더 보기])과 그 아래 내용이다. 서버 상세 탭은 콘솔·설정·접속자·백업·예약·기록, 디스코드 서버 상세 탭은 권한·사다리·명령 별명·노래·읽어주기·서버 관리·알림·말하는 사바쨩, 모듈·익스텐션 쪽은 두 탭, 앱 설정 쪽은 앱 설정 폼·데몬 로그다(`Page::tabs`). 모듈·익스텐션 상세는 판(업데이트 확인 결과에 지금 판과 다른 새 판이 있으면 함께)·쓰는 서버·출처와 그 뜻을 보이고, 버튼은 새 판이 있을 때만 [업데이트](모듈은 `update download module-X` 뒤 `update apply module-X`, 익스텐션은 `extension update`)와 [이 게임으로 새 서버](그 게임을 골라 새 서버 창을 연다)다. 모듈·익스텐션만 적용하는 `update apply`는 업데이터를 띄우지 않으므로 메뉴 안에서 돈다. 앱 설정 폼은 데몬·CLI가 쓰는 칸만 묶음별로 보인다(연결: 언어·IPC 포트, 게임 서버: 새 서버 기본값·비밀번호 자동 생성·포트 충돌 검사, 콘솔: 시각 표시, 저장 공간: 활동 기록 보관, `data.rs` `config_form`). 창 모양·소리 같은 GUI 설정은 GUI에서만 바꾼다. 채운 칸은 화살표가 움직일 곳 하나이고, 고른 탭은 강조색 밑줄로 보인다. `bot pair`는 코드를 보일 때 OSC 52로 터미널 클립보드에도 넣는다(`output::copy_to_clipboard`, 메뉴가 마우스를 잡아 드래그로 고를 수 없어서). 탭 내용은 데몬 API로 읽어 폼·표로 그리거나(`data.rs` `PaneWant`: 서버 설정은 `server settings --json`과 같은 `cmd::server::load_settings`, 권한은 `GET /api/permissions/:guild`·`/commands`, 노래·읽어주기는 디스코드 서버 설정, 앱 설정은 `config show`와 같은 값), 같은 뜻의 CLI 명령을 안에서 실행해 그 출력을 그대로 보인다(`Load::Capture`: 예약·사다리·명령 별명·서버 관리·알림·말하는 사바쨩). 내용 아래 줄에 같은 일을 하는 명령(`같은 명령: saba-chan …`)을 보인다. 설정 폼(`tui/form.rs`)은 켜기/끄기·선택은 ←→·Space, 글·숫자는 Enter로 고치고, `/`로 칸을 찾으며(한글 초성도), 바뀐 칸은 노란 표시와 저장 막대로 보이고 Ctrl+S가 바뀐 칸만 CLI 명령으로 저장한다(`Saver`: `server set`, `config set`, `bot music|tts`, `perm command|grant`). 메뉴는 명령을 직접 부르지 않고 모든 저장·버튼이 명령 한 줄이다. 새 서버(n, `+ 새 서버`)는 방식·게임·이름·프리셋·확인 단계 창으로 `server add … [--preset] [--accept] [--start]` 한 줄을 만든다(`tui/wizard.rs`, 약관은 확인 단계에서 받는다). Ctrl+K "무엇이든 찾기"는 쪽·탭·서버·디스코드 서버·읽어 둔 설정 칸·CLI 명령을 이름·초성으로 찾고, Enter는 그 화면·칸으로 가고 Tab은 같은 명령을 명령 줄에 채운다(`tui/palette.rs`, `tui/search.rs`). 콘솔 탭은 첫 낱말을 치는 동안 그 서버의 게임 명령(`catalog`)을 이름·별명·초성으로 제안하고 ↑↓·Tab으로 고른다. 키: Tab은 칸 옮기기, Esc는 언제나 한 단계 뒤(고치기 취소 → 찾기 지우기 → 바뀐 칸 되돌리기 → 상세 탭 → 목록 → 쪽 탭), 서버 쪽 s 시작/정지·r 재시작·n 새 서버(글을 치는 중이 아닐 때). 폭 100칸 미만이면 목록과 상세를 한 번에 하나씩 보이고 상세 위에 `‹ 서버 목록 Esc` 줄을 둔다. 창(묻기·찾기·더 보기·도움말)이 뜨면 뒤를 어둡게 한다. 콘솔 입력은 `console` 연결과 같이 게임 명령 표를 거쳐 보낸다. 모든 명령은 `:`(또는 `/`) 명령 줄에서 Tab 완성과 함께 돈다. 한 줄 결과는 아래 알림 줄에, 여러 줄은 결과 서랍(F2)에 보인다. 출력(`output` 창구), 진행(`progress` 창구), 확인 질문(`prompt` 창구)을 바꿔 끼워 결과 서랍(또는 그 탭), 아래 작업 줄, 화면 안 대화상자에 그린다. 데몬 상태·서버 목록은 3초마다, 보고 있는 서버 콘솔(`GET /api/instance/:id/console?spans=1`)이나 데몬 로그(`GET /api/daemon/console?spans=1`)는 1초마다 끝 300줄을 읽어 데몬이 준 토큰으로 칠한다(`tui/highlight.rs`, 토큰 색은 `console` 명령과 같다). 접속자 탭도 열려 있는 동안 다시 읽는다. `GET /api/clients/launch`의 `gui`가 true면 "GUI로 전환"(F9)이 보이고, 고른 서버로 GUI를 띄운 뒤 메뉴를 닫는다. Ctrl+C는 실행 중인 명령을 멈춘다(대화상자·찾기·새 서버 창에서는 닫기, 명령 줄에서는 줄 지우기). 화면을 통째로 쓰거나 프로그램을 끝내는 명령(`shell`, `tui`, `gui`, `completions`, `install`, `monitor --watch`, 모듈·익스텐션 밖의 `update apply`)은 안에서 돌리지 않고, `console`·`server console`은 `--follow`로 읽기만 한다. 이 판단은 줄을 명령 표로 읽은 결과로 하므로 별칭이나 앞에 둔 전역 옵션도 같다(`tui/app.rs` `refuse`·`adapt`). 명령 작업이 패닉하면 결과 서랍에 알리고 실행 중 표시를 푼다. 터미널이 아니거나 `--json`이면 열지 않는다(인자 없으면 `status`, `tui`로 부르면 사용법 오류, `main.rs` `default_cmd`). 폭 60칸 미만이면 넓혀 달라는 안내만 보이고, 명령이 묻는 중이면 질문은 그린다. 명령 처리는 디버그 빌드에서 스택을 많이 써서 16MB 스택 스레드에서 돈다(`main.rs` `STACK`, Windows 주 스레드 기본 1MB).
- **대화형 셸**: `saba-chan-cli shell`, 또는 `SABA_NO_TUI=1`로 인자 없이 터미널에서 실행하면 열린다(`main.rs`, `shell.rs`). 한 줄이 명령 하나이고 Tab으로 명령·서버 이름·게임 명령을 채운다(게임 명령은 `catalog`에서, `shell.rs:109`). 첫 단어가 명령이 아니면 디스코드와 같은 채팅 처리기로 보낸다(`shell.rs:1-5, 187`). 셸을 닫아도 데몬과 서버는 계속 돈다.
- **스크립트용 `--json`**: stdout에는 JSON 문서 하나만 나가고, 안내와 진행 표시는 stderr로 간다(`output.rs:1-6`). 종료 코드: 0 성공, 1 실패, 2 사용법·모호함, 3 데몬 응답 없음, 4 대상 없음, 130 취소(`error.rs`의 `EXIT_CODES`). `help --json [명령…]`은 명령 트리(경로·별칭·설명), 인자(이름·플래그·위치·필수·값·선택지), 전역 옵션, 종료 코드 표를 JSON 하나로 낸다(`cli::schema`). 데몬 없이 되고, 별칭으로 찾아도 경로는 본 이름이다. 맨 위 `help`는 이 명령이라 clap의 하위 `help`는 꺼지고, `server help start`처럼 하위 자리에 온 `help`는 `cli::parse`가 맨 앞으로 옮겨 읽는다. 사람용 출력은 모두 `output::write_line` 한 창구(`say!`·`tell!`)를 지난다. 명령 코드가 `println!`으로 직접 찍지 않는 것은 시험이 지킨다(`no_command_talks_to_the_terminal_directly`). 진행 표시(`progress::Progress`)와 질문(`prompt::Asker`)도 같은 방식으로 바꿔 끼울 수 있고, `indicatif`·`dialoguer`는 각 파일 밖에서 쓰지 않는다. TUI가 이 창구들을 바꿔 끼워 명령 결과는 패널에, 진행은 작업 줄에, 질문은 대화상자에 그린다. `--json-stream`은 `--json`을 포함하고, 진행 표시를 막대 대신 stdout에 `{type:"progress", id, kind?, message?, position?, length?, done?}` 한 줄씩 내며(같은 막대의 위치는 250ms 간격, `progress::stream_lines`), `events`·`audit -f`의 줄에는 `type:"event"`가 붙고, 마지막 줄에 `{type:"result", data}`로 `--json`과 같은 문서(실패면 `{ok:false, error, error_code}`)를 싣는다. 전역 옵션은 `--json`, `--json-stream`, `--yes`, `--lang`, `--port`, `--no-color`, `--daemon <이름>`(`SABA_DAEMON`: 저장한 원격 데몬을 고른다. 요청마다 `X-Saba-Target`을 실어 이 PC의 데몬이 중계한다, 01 §1.4.2 7. 데몬 신원 확인 `/health`에는 싣지 않는다).
- **로컬 AI 에이전트(MCP)**: `saba-chan mcp`는 이 PC의 Claude Code·Codex가 띄우는 stdio MCP 서버다(`cmd/mcp.rs`, 공식 Rust SDK `rmcp`). 원격 MCP(릴레이, 액션 카탈로그만, 05 §4.4 (l))와 달리 CLI의 모든 명령을 쓴다: 이 PC에서 CLI를 실행할 수 있으면(IPC 토큰 파일을 읽을 수 있으면) PC 주인으로 본다. 도구는 둘이다. `saba_help {command?}`는 `help --json`과 같은 명령 트리를 자식 없이 돌려준다. `saba_run {args, confirm?, timeout_secs?}`는 같은 CLI를 자식으로 `--json <args>`로 실행하고(입력 없음, `SABA_NO_TUI=1`, `SABA_AGENT=1`, Windows는 창 없이) 종료 코드와 출력 JSON을 돌려준다. 기다림은 기본 300초, 최대 3600초이고 넘으면 자식을 끝내고 상태를 먼저 보라고 한다. 출력은 20만 자에서 자른다. 확인 질문은 사람이 한다: 인자에 확인 생략(`--yes`·`-y`, `-ys`처럼 묶은 것도 CLI 파서로 읽어)이 있으면 거절하고, 자식이 비대화형이라 묻지 못하면(`error_code: needs_confirm`, 종료 코드 2, `question`에 묻던 말) 실행하지 않았다는 것과 그 질문을 돌려준다. 에이전트가 사람에게 묻고 동의를 받으면 `confirm: true`로 다시 부르고, 그때만 `--yes`가 붙는다. 약관 동의는 `--yes`로도 대신하지 않고, 인자의 `--accept`도 거절한다(사람이 터미널·앱에서 한다). `mcp`·`shell`·`tui`는 돌리지 않는다. `saba-chan --daemon X mcp`처럼 띄울 때 고른 `--daemon`·`--port`·`--lang`은 호출이 같은 옵션을 주지 않으면 자식에 붙인다. 자식의 요청은 `X-Saba-Client: agent`라 작업 기록 출처가 `agent`다(`client.rs` `client_name`).

### 3.2 구조
- `client.rs`: 데몬 HTTP 클라이언트. 토큰 파일을 읽어 `X-Saba-Token`을 보내고, 401이면 토큰을 다시 읽어 1회 재시도한다(`client.rs:28-33, 97-106`). 업데이터 실행도 데몬 API로 요청한다(`launch_updater` `:785-789`).
- `bootstrap.rs`: 데몬이 뜨기 전에 필요한 것만 직접 한다. `config.json`의 `gui.ipcPort`·`gui.language` 읽기(포트는 `SABA_IPC_PORT` > 파일 > 기본값, 언어는 `--lang` > `SABA_LANG` > 파일 > 시스템 로캘 > en, `:18-46`. `--lang`이나 `SABA_LANG`으로 직접 골랐을 때만 그 언어를 요청마다 `Accept-Language`로 실어(`client.rs` `Api::new`) 데몬 문구와 그 요청이 부르는 모듈도 같은 언어로 오게 한다. 고르지 않았으면 싣지 않아 데몬이 앱 설정 언어를 따른다), 설정 포트에 데몬이 없을 때 실행 중인 데몬이 남긴 `<dataDir>/daemon.lock.owner`(`src/instance_lock.rs`)의 포트에서 그 데몬(같은 pid)이 토큰 없는 `/health`로 답하면 그 데몬에 붙기(`live_port`: 포트를 바꾸고 데몬을 아직 다시 켜지 않았을 때 그 데몬을 끄고 새 포트로 다시 켤 수 있게 한다. 새 데몬은 언제나 `--port` 또는 설정 포트로 띄운다. 셸은 `--port` 없이 열었으면 줄마다 설정 포트와 붙을 포트를 다시 찾고, 한 줄에 준 `--port`는 그 줄의 붙을 곳과 띄울 곳 모두에 쓴다), `saba-core` 실행 파일 찾기와 분리 실행(`saba_chan_updater_lib::process::spawn_detached`. 띄운 데몬이 응답 전에 끝나면 시간 초과를 기다리지 않고 종료 코드를 알린다. 자동 실행 항목이 이 설치의 `saba-core`를 서비스로 돌리고(리눅스 `saba-chan.service`, 맥 LaunchAgent) 붙을 포트가 설정 파일의 포트이며 `SABA_DATA_DIR`가 없으면 직접 띄우지 않고 `systemctl --user start saba-chan.service`(맥 `launchctl kickstart gui/<uid>/com.saba-chan.autostart`)로 켠다(`autostart::service_start`). 그 명령이 실패하면 직접 띄운다), 정상 종료가 안 될 때 **그 PID만** 강제 종료(`:92`).
- `ctx.rs`: 데몬이 필요한 명령 앞에서 `ensure_daemon`이 데몬을 확인한다. 꺼져 있으면 물을 수 있을 때(대화형, `--yes` 아님) 켤지 묻고 `start_daemon`으로 띄운다(`:22-41, 43-61`).
- `catalog.rs`: 게임 명령을 하드코딩하지 않는다. `GET /api/modules`의 `commands`·`command_aliases`와 `GET /api/instance/:id/commands`로 목록·사용법·입력 칸을 만든다(`:1-9`). 인자 검사의 최종 판단은 데몬이 한다. 명령의 `method`는 데몬이 준 값을 그대로 보여 줄 뿐 분기하지 않는다(`server commands --json`, `cmd/server.rs:983`). 데몬은 콘솔 명령의 method를 `console`(`console_template`)이라 부르고 예전 이름 `rcon`·`rcon_template`도 별칭으로 받는다(09b8e4f, 02 §1.2).
- `slots.rs`: 데이터 slot(03-extensions 4.3)을 출력만 한다. 서버의 `slots`(`ServerCard.badge`, `ServerDetail.status`)와 익스텐션의 `slots["AddServer.options"]`를 읽고, 답은 서버를 만들 때 `extension_data`로 보낸다.
- `i18n.rs`: 설치 폴더의 `locales/<lang>/cli.json`을 먼저 읽고, 없으면 바이너리에 넣어 둔 en/ko를 쓴다(`:11-12, 36-52`). clap 도움말은 `help.cmd.*`·`help.arg.*` 키가 있으면 그 문구로 바꿔 끼운다(`cli.rs:811-839`).
- 모듈이 구현하지 않은 기능(MK1): `GET /api/modules`의 `functions`가 배열이면 빠진 선택 함수를 쓰는 명령(`cmd/module.rs` `OPTIONAL`: `server reset`·`server version`·`server diagnose`·`server validate`·`server properties [set|reset]`·`module versions`·`module install-files`)을 `module info`·`server info`의 "지원하지 않음" 줄로 보이고(`server info --json`은 `unsupported`), `server reset`·`server properties reset`은 확인을 묻기 전에 `not_supported`로 멈춘다. 데몬의 `not_supported` 답에는 안내 한 줄이 붙는다(`error.rs` `api_hint`). `functions`가 null이거나 없으면 아무것도 숨기지 않는다.
- 실행 파일 이름(MK7): `module install-files --executable FILE`(예전 `--jar`는 별칭)은 `POST /api/module/:name/install`에 `server_executable`로 보낸다. 시작 실패의 `action_required`(`client.rs` `check`)는 `error_code`가 없을 때 오류 코드가 되고, `executable_not_found`(옛 `server_jar_not_found`)에는 다시 설치하라는 안내가 붙는다(`error.rs` `api_hint`).
- 스키마 2 설정(MK2·MK8, 06 §7·§8): `server set`은 `list` 설정 값을 쉼표로 나누거나 JSON 배열로 받아 문자열 배열로 보내고(선택지가 있으면 항목마다 맞춘다, 빈 값은 빈 목록), `multiline` 값의 `\n`을 줄바꿈으로, `\\`를 `\`로 바꿔 보낸다. `server settings`는 `GET /api/instance/:id`의 `hidden`에 든 설정을 빼고 그 이름을 끝에 한 줄로 보이며, 목록은 쉼표로, 여러 줄은 ⏎로 이어 보이고, `restart_required` 설정에 "바꾸면 다시 시작"을 붙인다(서버가 켜져 있을 때만). `--json` 문서의 칸은 `key`·`label`·`type`·`group`·`value`·`default`·`options`·`option_labels`(모듈 locales의 선택지 이름)·`description`·`min`·`max`·`hidden`·`restart_required`다(`cmd/server.rs` `SettingsData::doc`, TUI 설정 탭도 이 문서를 쓴다). 저장 응답의 `restart_required`가 비어 있지 않으면 그 이름과 재시작 명령을 보인다(키가 없는 옛 데몬이면 켜져 있을 때 늘 안내). `module list`는 `failed[]`의 `module_schema_invalid`면 "읽지 못했어요"와 `problems`를 한 줄씩, `module_schema_unsupported`면 필요한 형식 `required`를 보인다.
- 원격 데몬 포트(D1, 01 §1.4.2): `remote status`·`remote set [--on|--off] [--remote-port N] [--address 주소]`(준 것만 `PUT /api/remote/settings`로 보낸다, 빈 주소는 지움)·`remote clients`·`remote revoke <PC id>`, 붙는 쪽(D1b) `remote peers`·`remote connect <PC id>`·`remote daemons`·`remote forget <PC id>`·`remote rename <PC id> <이름>`(`PUT /api/remote/peers/:id/name`, 이 PC도 된다), 리눅스에 설치·코드로 붙이기 `remote install <계정@주소> [--ssh-port N] [--linger] [--steam-libs]`(전역 `--port`는 데몬 포트라 이름을 따로 쓴다)(물음은 터미널에서 받고, 비밀번호는 화면에 보이지 않게 받는다)·`remote claim <코드>`, 지우기 `remote remove <PC id> [--uninstall [--remove-settings] [--remove-instances]] [--from-relay]`, 원격 업데이트 `remote update <PC id> [--auto on|off]`(`--auto`가 없으면 바로 업데이트)(01 §1.4.2 11~14), 합쳐 보기(G1c) `remote servers`(데몬마다 서버 표, 닿지 않는 데몬은 이유)(`cmd/remote.rs`). 다른 명령을 원격 데몬에 보내려면 전역 `--daemon`을 쓴다(G1a). GUI는 설정 > 연결의 원격 데몬 절과 상단 바 데몬 고르기다(§1.1·§1.2, G1b).
- 사람이 직접 하는 동의(약관 `server agree`·`server add`, 격리 없이 돌리기·익스텐션 GUI `sandbox allow`)는 `prompt.rs` `agreed`·`consent`로만 받는다. `--yes`·`--json`은 동의가 아니고, 물을 수 없으면 터미널에서 하라는 오류다. 묻지 않고 동의하는 길은 읽은 약관 id를 대는 `server add --accept ID`뿐이다.
- 이름으로 대상 찾기(`resolve.rs`): 정확히 같음 → 대소문자 무시 → 앞부분 → 포함 순서로 찾는다. 지우기·초기화(`server remove`·`server reset`·`module remove`·`extension remove`)와 권한 대상 멤버(`perm`)는 앞의 두 단계만 쓴다(`find_exact`). 앞부분·포함으로만 맞는 이름은 고르지 않고 제안으로 보인다. 이 명령들은 이름 없이 물을 수 없으면(`--json`, 파이프) 대상이 하나뿐이어도 고르지 않고 이름을 대라고 한다.
- 일부만 된 결과: 데몬이 2xx에 `ok`/`success: false`와 결과만 싣는 응답(`update download`·`update apply`의 `errors`, `chatbot forget`의 `sync`, `server set`·`server add --set`의 `synced: false`)은 `client::partial`로 본문을 받아 된 것과 실패한 것을 보이고 `partial`(종료 코드 1)로 끝낸다. 구성요소를 고르지 않은 받기가 `errors` 없이 `{ok:false, error}`로 실패해도 실패로 끝낸다. 적용에 실패한 구성요소가 있어도 코어 업데이트가 있으면 GUI처럼 경고하고 업데이터를 띄우며, 종료 코드 1로 실패를 남긴다. 업데이터를 띄운 뒤에는 `GET /api/updates/last-result`가 적용 전과 다른 결과(시각)를 줄 때까지 2초마다 묻고(최대 15분, 그 사이 데몬이 꺼져 있는 오류는 기다림의 일부다) 결과와 패치노트를 보인 뒤 끝낸다. 결과가 실패이거나 15분이 지나면 종료 코드 1이다(`cmd/update.rs` `wait_for_result`, 06 §9). `monitor --watch --json`은 표본마다 JSON 한 줄을 낸다(`events`와 같다).
- `cmd/`: 명령 갈래마다 파일 하나(backup, bot, chatbot, config, console, daemon, extension, module, schedule, server, status, update).
- 콘솔 색: 터미널이 색을 쓸 때만 `?spans=1`을 붙여(`client.rs` `console`) 데몬이 준 토큰 구간을 토큰별 ANSI 스타일로 칠하고, 나머지는 줄 `level` 색을 쓴다(`cmd/console.rs` `format_line`, `token_style`). 토큰은 02 §`HighlightRuleToml`. 앱 설정 `consoleTimestamps`(`24h`·`12h`)·`consoleTimestampDate`를 켰으면 GUI 콘솔처럼 줄 앞에 줄 시각을 흐리게 붙인다(`console::Stamp`, `console`·TUI를 열 때 `GET /api/config/gui`로 한 번 읽는다).

- `bot pair [--relay-url URL]`: 페어링 코드를 받아 보여 주고(디스코드 `/사바쨩 연결`·`/saba connect`에 넣는다) claimed까지 기다린다. 데몬은 설정한 릴레이와만 페어링하므로, `--relay-url`이 설정과 다르면 봇 설정 `cloud.relayUrl`을 먼저 바꾼 뒤 페어링한다. `--json`만 주면 코드만 내고 끝, `--yes`면 기다린다.
- `bot channels GUILD [--chatbot 이름,…] [--no-chatbot] [--music 이름] [--no-music] [--notify 이름] [--no-notify] [--game-chat 이름,…] [--no-game-chat] [--board 이름,…] [--no-board]`: 채널 이름이나 id를 GET 응답의 `channels`로 id로 바꿔 PUT한다. `--notify`는 알림 채널(I3: 크래시·백업·업데이트·예약 예고), `--game-chat`은 게임 채팅 채널들(`gameChat`, 게임 채팅 전달), `--board`는 상황판 채널들(`board`)이다. `--chatbot`처럼 쉼표로 여럿을 주면 지금 목록을 바꾼다. 서버마다 무엇을 보낼지는 `server set 서버 game_chat=off|all|keyword game_chat_keyword=단어`(인스턴스 공통 칸 `INSTANCE_FIELDS`)로 정한다. 음악 채널을 새로 정할 때는 메시지가 지워진다고 확인을 받는다.

- `config autostart [off|daemon|full]`: 모드 없이 부르면 `GET /api/system/autostart`의 지금 값을, 있으면 `PUT`으로 바꾼다(GUI 설정 > 일반과 같다). 실패 코드 `autostart_*`는 `err.hint.autostart_*` 문구로 보인다. 서비스로 등록됐으면(`service`, 화면 없는 리눅스·맥) 그렇다고 알리고(맥은 `config.autostart.service_mac`), `lingering:false`면 `sudo loginctl enable-linger $USER`를 안내한다.
- `config export FILE [--secrets]`·`config import FILE [--dry-run] [--overwrite]`(A9): 경로를 절대 경로로 바꿔 `/api/migration/*`에 넘긴다. 파일은 데몬이 읽고 쓴다.

- `completions --install [--shell 셸]`(`cmd/completions.rs`, 데몬을 깨우지 않는다): 쓰는 셸(`SHELL`, Windows는 PowerShell)이 스스로 읽는 이 사용자의 자리에 `saba-chan`·`saba-chan-cli` 두 이름의 완성 스크립트를 쓴다(bash `$XDG_DATA_HOME/bash-completion/completions/<이름>`, zsh `~/.zfunc/_saba-chan` 한 파일에 `#compdef saba-chan saba-chan-cli`, fish `$XDG_CONFIG_HOME/fish/completions/<이름>.fish`). PATH와 셸 설정 파일은 고치지 않는다: zsh는 `.zshrc`(`ZDOTDIR`)나 내보낸 `FPATH`에 `~/.zfunc`가 없으면 넣을 한 줄만 알리고, 설정 파일을 고쳐야만 읽는 PowerShell·elvish는 파일 없이 넣을 한 줄(`completions <셸>` 출력을 실행)을 알린다. `completions <셸>` 출력도 두 이름에 붙는다(zsh는 설치하는 파일과 같은 `#compdef` 두 이름 한 본문, 나머지는 이름마다 이어 붙인다). `install.sh`는 로그인 셸이 bash·zsh·fish일 때만 설치 끝에 한 번 부른다(그 밖의 셸은 조용히 건너뛴다).
- `update repair`: 점검 중 표시 뒤 `GET /api/updates/repair`의 요약(`update integrity`와 같은 줄)과 다시 받을 구성요소를 보이고(받을 수 없는 것은 경고), 없으면 "고칠 게 없어요"로 끝낸다. 있으면 `POST /api/updates/repair`를 부르며 다운로드 진행률로 받기 시작한 구성요소를 한 줄씩(이름과 설치된 판) 보이고, 고친 것을 알린다. 답이 `requires_updater`면 `update apply`와 같은 길(다시 시작을 묻고 `launch-updater`, 다시 뜬 데몬의 결과를 보인다, `hand_to_updater`)로 간다. 고치지 못한 것이 있으면 일부 실패(`partial`)로 끝난다. TUI 안에서는 받지 않는다.
- `update rollback`: `GET /api/updates/rollback`으로 되돌릴 판(돌아갈 판, 지금 판, 업데이트한 때)을 보이고, `needs_newer_core`가 있으면 그 판에서 쓸 수 없게 될 모듈·익스텐션을 경고한 뒤 한 번 묻고(`--yes`면 건너뛴다) `POST /api/updates/rollback {relaunch:[saba-core, --spawned]}`를 부르고 끝난다(데몬이 업데이터를 띄우고 꺼진다, 결과는 `update last`). 남긴 판이 없으면 그렇게 알린다. TUI 안에서는 받지 않는다(`refuse`).

사용자 안내서는 `saba-chan-cli/README.md`에 있다.

## 4. 디스코드 연동 (데몬 쪽)

> 로컬 Discord 봇 실행(`discord_bot/`, Node, ext-process)은 레거시이며 L1(7b5102f)에서 지웠다. 디스코드 봇 자체는 클라우드 릴레이에서 돌고, 그 쪽(게이트웨이·음악·챗봇)은 지금 server-chan에서 다시 만드는 중이라 여기서 다루지 않는다. 이 절은 데몬 쪽의 안정된 계약만 적는다.

### 4.1 구조

```
Discord ─ 릴레이의 사바쨩 봇 ─(롱폴링, HMAC 서명)─ 데몬 relay_agent ─ 채팅 처리기(crate::chat) ─ 데몬 내부 API
```

- 데몬이 먼저 릴레이로 나가서 연결한다. 데몬은 들어오는 연결을 받지 않는다.
- 페어링으로 받은 노드 토큰(`sbn_<id>.<secret>`)이 있어야 에이전트가 뜬다. 페어링은 `/api/relay/pair/initiate`, `POST /api/relay/pair/status`(01 §4 Relay 프록시)로 하고, 토큰은 `/api/config/node-token`으로 다룬다.
- AI 챗봇 설정의 원본은 데몬 config.json `chatbot`이다. `GET/PUT/DELETE /api/chatbot`, `DELETE /api/chatbot/memory?guildId=`로 다루고, 바뀔 때마다와 에이전트가 연결될 때 이 호스트의 길드마다 릴레이에 PUT해서 맞춘다. 릴레이 PUT은 받은 키만 합치므로 데몬은 늘 전체 설정을 보내고, 지운 키는 릴레이 기본값으로 채운다(`handlers/chatbot.rs:31-65`). DELETE가 릴레이에 닿지 못하면 `pendingRelayDelete: true`로 답하고 다음 연결 때 다시 지운다(`:218-238, 240-255, 287-295`). API 키는 데몬과 릴레이만 알고, 클라이언트에는 `hasApiKey`만 준다(`handlers/chatbot.rs:1-15`, `mod.rs:643-644`).

### 4.2 릴레이 에이전트 (`src/relay_agent.rs`)

| 단계 | 요청 | 내용 |
|---|---|---|
| 버전 확인 | `GET /info` | 릴레이가 요구하는 최소 에이전트 버전 확인 |
| 하트비트 | `POST /heartbeat` (60초) | `agentVersion`, `os`, `metadata`(서버·모듈·봇 설정). 릴레이가 `UPDATE_REQUIRED`를 주면 경고 로그를 남긴다(`relay_agent.rs:281-327`). 지금 릴레이는 경고 대신 426 `AGENT_TOO_OLD`로 거부하고(05 §3 `/heartbeat`), 데몬은 이를 하트비트 오류로 남긴다. 잠자기는 길드 설정(I2)이라 폴링은 쉬지 않는다. 게임 서버 비밀번호(`rcon_password`, `rest_password`)는 메타데이터에서 뺀다(273-276) |
| 명령 받기 | `GET /poll` (롱폴링) | 디스코드에서 온 명령. `payload.action`은 `plan`(문장 계획 `text`, 한 액션 `id`, 여러 단계 `steps`)·`run_plan`·`query`·`catalog`(원격 MCP만)·`permission`·`web_session`·`remote_tunnel` 등이다(05 §4.4) |
| 결과 보내기 | `POST /result/:id` | 채팅 처리기의 응답 `{success, data:{text}}` (`:505-567`) |

- 모든 요청은 노드 토큰으로 HMAC 서명하고 `X-Saba-Client: 1` 헤더를 붙인다(`relay_agent.rs:197-201, 215-229`, `handlers/relay.rs:117` `signed_headers`). 노드 토큰을 싣는 프록시 요청(`/api/relay/host/*`, `/node/*`)은 `?relayUrl=`이 설정된 릴레이와 같거나 루프백일 때만 따르고, 아니면 설정된 릴레이로 보낸다(`handlers/relay.rs:46-67`).
- 데몬이 뜨면 `auto_start`가 에이전트를 켠다(토큰이 없으면 info 로그만 남기고 건너뜀, `ipc/mod.rs:860-866`, `relay_agent.rs:178-189`). 에이전트가 연결되면 첫 하트비트 응답을 처리한 뒤 AI 챗봇 설정도 릴레이에 맞춘다(`relay_agent.rs` `chatbot_sync_due`, 01 디스코드 길드 설정).
- 상태 `GET /api/relay/agent`: `{running, relay_url, has_token, agent_version, last_heartbeat_at, last_error, commands_handled}` (`relay_agent.rs:43-55`). 켜고 끄기는 `POST /api/relay/agent/start`, `/stop`.
- 새 명령 종류는 `handle_payload`의 action 분기에 더한다.

### 4.3 채팅 처리기 (`src/chat/`)

- 디스코드 명령과 CLI `chat`, `POST /api/chat/command {text, guild_id?, user_id?} → {reply, code, args}`가 모두 같은 처리기를 쓴다(`handlers/chat.rs:9-16`).
- 문장은 `<서버> <명령> [덧붙이는 말]`이다. 서버와 명령은 띄어 쓴 말이어도 되고, 앞에서부터 가장 많은 낱말이 맞는 것을 고른다(대소문자와 공백 칸 수는 가리지 않는다, `chat/mod.rs` `longest_phrase`). 서버 후보는 인스턴스 이름·id·서버 낱말·모듈 이름·게임명·별명, 명령 후보는 그 서버의 명령 낱말 → 별명·명령 이름 → 내장 명령(start·stop·status·players)과 답하는 언어의 이름(`actions.server.<명령>.name`) → 답하는 언어로 보이는 명령 이름(모듈 locales `commands.<명령>.label`, 없으면 영어, 그것도 없으면 module.toml `label`) 순이다. 게임명·별명은 module.toml의 언어 없는 낱말과 답하는 언어의 locales 낱말만이다(02 §`[aliases]`). 최상위 말은 `help`·`list`와 답하는 언어의 `top_level_words.help`·`list`(bot.json, 쉼표로 나눈 목록. 지금은 ko만 `도움, 도움말`·`목록`)다. 서버 이름과 낱말에는 쉼표를 둘 수 없다.
- 비밀 액션(부른 사람에게만 답하는 것, `server.address`)의 이름은 문장으로 실행하지 않고 `errors.slash_only`로 슬래시 명령을 안내한다(`actions` `slash_only`). 답이 채널 모두에게 보이기 때문이다.
- 도움말은 서버마다 그 서버를 부르는 말을, 서버만 부르면 그 서버에서 칠 수 있는 말(응답 언어의 명령 이름·칸 이름·설명)을 보인다. 상태 답은 상태·접속자(모듈이 지원할 때)·켜진 시간이고, 시작 중에 접속자를 물으면 `server.still_starting`으로 답한다.
- 대상 서버 찾기: 인스턴스 이름·id → 그 서버를 부르는 낱말(`serverWords[id].words`) → 모듈 이름·게임명(답하는 언어 모듈 locales `module.display_name`)·별명 순이다. 같은 게임 서버가 여럿인데 하나로 좁혀지지 않으면 `errors.multiple_instances`로 답한다. 위험 명령은 모듈 이름·게임명·별명으로 부르면 `errors.danger_needs_name`으로 거절한다(`chat/mod.rs` `named_servers`·`find_server`, 01 §4).
- 명령 낱말은 그 길드·서버의 `commands`, 그다음 module.toml 별명과 답하는 언어의 locales 별명이고, 접두사는 `prefixes`다. 맞춰 볼 때 대소문자를 가리지 않고 긴 것부터 보며, 접두사 뒤가 공백·쉼표·쌍점이거나 글 끝이어야 한다. 도움말에는 첫 접두사를, 비어 있으면 언어별 `default_prefix`(bot.json)를 쓴다. 응답 문구는 설치 폴더 `locales/<lang>/bot.json`을 부를 때마다 읽고(그래서 업데이터가 번역을 바꾸면 다음 응답부터 새 문구), 없으면 바이너리에 넣은 사본을 쓴다(`chat/i18n.rs`).
- 노드(디스코드 서버)별 허용 인스턴스와 권한(멤버 레벨, 명령별 레벨)은 `nodeSettings`에 있다. 레벨은 누적이다(01 §4.4 `nodeSettings`).

### 4.4 봇 초대

- `GET /api/relay/bot-invite`(query `relayUrl?`)가 릴레이의 공개 `/api/bot-invite` 응답 `{url}`을 그대로 돌려준다. 공개 엔드포인트라 서명하지 않지만, 주소는 서명 요청과 같이 설정한 릴레이나 루프백만 쓴다(`handlers/relay.rs:428-450`).

## 7. ★ Daemon 우회 지점 전수 목록 (GUI · CLI)

> 기준: "인터페이스는 혼자서 아무것도 못 한다. 파일 편집도 daemon API를 거친다."
> 분류: **[FS-R]** 직접 파일 읽기 / **[FS-W]** 직접 파일·디렉터리 쓰기 / **[PROC]** 프로세스 spawn·kill / **[EXT]** 외부 서비스 직접 호출 / **[CFG]** 설정 파일 직접 편집 / **[OS]** OS 레지스트리·셸
> "불가피" 표시는 부트스트랩상 daemon 없이는 할 수 없는 항목이다. 그래도 목록에는 포함했다.

### 7.4 디스코드 봇
로컬 봇이 없어져 이 목록(B1~B11)은 사라졌다. 릴레이와의 통신은 데몬의 relay_agent만 한다(§4).

### 7.5 요약 판정
- **원칙 위반 정도가 가장 큰 항목**:
  - G2: GUI가 daemon 상태와 상관없이 config.json `gui`를 직접 읽는다. 쓰기(G3, G4)는 daemon이 응답하지 않을 때만 하므로 부트스트랩 범위로 줄었다.
- **부트스트랩상 불가피한 항목**(토큰 파일, ipcPort, daemon 최초 spawn): G1, G7, C1, C2, C9. daemon **종료**(G8, G11)는 이제 `/api/daemon/shutdown`을 먼저 쓰고, 강제 종료는 자기가 띄운 PID에만 한다(G12도 같다).
- **daemon에 API가 없어서 우회하는 항목**: daemon 재기동(G10), 언인스톨러(G16).
